# Farmboy — Spec Roadmap

Living, non-binding map of planned work. The entries below record the agreed initial local feature breakdown; their implementation details remain subject to specification and review. Foundations: the [constitution](constitution.md) and [project direction](../../docs/direction.md).

Status legend: **undecided** · **needs-info** · **planned** · **specced** · **in-progress** · **implemented** · **verified** · **deferred** · **abandoned**.

## Vision & End States

- Reduce human toil by composing existing Spec Kit capabilities into three prescribed, human-driven workflow segments.
- Deliver portable workflows with genuine input/review stops and understandable artifacts, then use them for later Farmboy development.

## Constraints & Decisions

- **C-01 — Governing rules:** Preserve feature-scoped flow-back and historical immutability at integration merge. Simplicity and understandable review material follow the constitution.
- **C-02 — Single-session baseline:** Use one Codex session with its existing model and effort. No per-step subagent roles, model routing or configuration feature; reconsider delegation/configuration only for a demonstrated need.
- **C-03 — Thin composition:** Compose existing commands in thin skills. No custom controller/framework by default. Extra infrastructure needs a concrete current requirement or observed failure, not speculative recovery or future orchestration needs.
- **C-04 — Bounded continuation:** Verify Codex Goals compatibility with explicit input/review stops; do not claim it already works. Resume from current artifacts and pending input rather than build a universal recovery system. Routine authorized work continues without repeated approvals; genuine blockers and required input stop affected work.
- **C-05 — Portability and dogfooding:** Demonstrate portability in a disposable Spec Kit project; adoption in a second live project is not required. Bootstrap the earliest workflow manually, then dogfood each delivered segment in later development.
- **C-06 — Explain infrastructure at plan review:** The agent explains any new infrastructure/subsystems, the concrete rationale, simpler alternatives and its recommendation. The operator decides approval or simplification at the full-plan gate before implementation.

## Planned Specs

### 001 — Prepare specification [status: planned]

- **Description:** Compose roadmap selection, relevant wiki context, specification authoring and interactive clarification into the first human-driven workflow.
- **Outcome:** The selected feature has a coherent specification and real clarification answers, then execution stops for explicit specification review.
- **Scope (in):** Select a named roadmap feature or identify eligible work; query relevant project knowledge; specify; clarify with genuine waits for user answers; stop at specification review. Preserve current feature identity, unresolved input and artifact-based interruption/resume. Verify any native Goals behavior used rather than assume it.
- **Scope (out):** Planning, tasks, implementation, invented answers, automatic acceptance, per-step delegation/configuration and custom orchestration infrastructure.
- **Depends on:** none.
- **Governed by:** C-01–C-05.
- **Notes:** Bootstrap this workflow manually. Demonstrate its behavior and portability in a disposable Spec Kit project, then use it to prepare specifications for later features. Detailed command mappings and eligibility rules belong in its reviewed spec; this entry creates no spec directory.

### 002 — Prepare implementation plan [status: planned]

- **Description:** From an approved specification, compose planning, task generation and analysis/repair into the second human-driven workflow.
- **Outcome:** Plan and tasks pass fresh analysis, and execution stops for full-plan review. The operator can understand and decide whether to approve or simplify the proposed implementation.
- **Scope (in):** Require the approved spec; plan and generate tasks; run read-only analysis; repair accepted findings in affected artifacts and repeat until a fresh pass. At the full-plan gate, explain new infrastructure/subsystems, concrete need, simpler alternatives and the agent’s recommendation. Preserve required input stops, bounded Goals compatibility checks and artifact-based resume.
- **Scope (out):** Implementation before review, automatic approval, universal recovery, model routing or a new controller/framework by default.
- **Depends on:** 001.
- **Governed by:** C-01–C-06.
- **Notes:** Dogfood the delivered specification workflow in this feature’s development; apply the planning workflow to later development once delivered. Demonstrate portability in a disposable Spec Kit project. A passing analysis is not human full-plan approval.

### 003 — Deliver approved plan through closeout [status: planned]

- **Description:** From an approved plan, compose implementation, convergence/repair and closeout into a bounded workflow ending at human result review.
- **Outcome:** Eligible approved work is implemented and converged, artifacts are reconciled, closeout is completed with a local commit, and actual results are presented for final review.
- **Scope (in):** Implement eligible tasks; converge, implement follow-up tasks and reassess until clean; reconcile specification, plan, tasks and implementation through merge-bounded flow-back; debrief; ingest and lint wiki knowledge; make the prescribed local commit; stop for result review. Continue routine authorized steps without repeated OKs, stopping for genuine blockers/input. Verify bounded Goals behavior and preserve artifact-based interruption/resume.
- **Scope (out):** Remote push, automatic merge/acceptance, Diagram integration, autonomous workers, universal recovery and extra configuration/delegation infrastructure without demonstrated need.
- **Depends on:** 002.
- **Governed by:** C-01–C-06.
- **Notes:** Dogfood the delivered specification and planning segments in this feature’s development. Demonstrate the complete local lifecycle and portability in a disposable Spec Kit project, including genuine questions, review stops, repair and interruption/resume. A local commit is a reconciliation checkpoint, not the integration-merge persistence boundary.

## Open Questions

- **Q1 — Command composition:** Which exact supported commands and minimal artifact checks express each prescribed segment, including completion recording and local closeout?
- **Q2 — Goals compatibility:** What activation, continuation and pause/resume behavior is demonstrated in the target Codex session, especially at genuine input and review boundaries?
- **Q3 — Infrastructure review:** Does any proposed additional subsystem solve a concrete current requirement or observed failure better than simpler composition? Explain alternatives at full-plan review; do not preselect infrastructure here.

## Cross-Cutting Notes

- These three entries are the agreed initial local workflow features, not the three broader product delivery stages. Diagram integration and autonomous execution remain later direction only.
- Preserve contextual knowledge and rationale in the wiki; track feature/task progress in roadmap/spec artifacts, without a parallel wiki status inventory.
- No feature is activated by this amendment. Specifications, plans, tasks and implementation require their separately selected work and human checkpoints.
