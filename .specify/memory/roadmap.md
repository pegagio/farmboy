# Farmboy — Spec Roadmap

Living, non-binding map of planned work. The entries below record the agreed initial local features and a later contract-alignment follow-up; their implementation details remain subject to specification and review. Foundations: the [constitution](constitution.md) and [project direction](../../docs/direction.md).

Status legend: **undecided** · **needs-info** · **planned** · **specced** · **in-progress** · **implemented** · **verified** · **deferred** · **abandoned**.

## Vision & End States

- Reduce human toil by composing existing Spec Kit capabilities into three prescribed, human-driven workflow segments.
- Deliver portable workflows with genuine input/review stops and understandable artifacts, then use them for later Farmboy development.

## Constraints & Decisions

- **C-01 — Governing rules:** Preserve feature-scoped flow-back and historical immutability at integration merge. Simplicity and understandable review material follow the constitution.
- **C-02 — Single-session baseline:** Use one Codex session with its existing model and effort. No per-step subagent roles, model routing or configuration feature; reconsider delegation/configuration only for a demonstrated need.
- **C-03 — Thin composition:** Compose existing commands in thin skills. No custom controller/framework by default. Extra infrastructure needs a concrete current requirement or observed failure, not speculative recovery or future orchestration needs.
- **C-04 — Bounded continuation:** Verify Codex Goals compatibility with explicit input/review stops; do not claim it already works. Resume from current artifacts and pending input rather than build a universal recovery system. Routine authorized work continues without repeated approvals; genuine blockers and required input stop affected work.
- **C-05 — Portability and dogfooding:** Demonstrate portability in a disposable Spec Kit project; adoption in a second live project is not required. Bootstrap the earliest workflow manually, then dogfood each delivered segment in later development.
- **C-06 — Explain infrastructure at plan review:** The agent explains any new infrastructure/subsystems, the concrete rationale, simpler alternatives and its recommendation. The operator decides approval or simplification at the full-plan gate before implementation.

## Planned Specs

### 001 — Prepare specification [status: verified]

- **Description:** Automate roadmap selection, relevant context and a saved specification draft/handoff; reuse ordinary interactive clarification before separate human specification approval.
- **Outcome:** Automated preparation succeeds at a usable saved draft and clarification/review handoff. Its native Goal ends there; ordinary clarification handles real answers, and explicit human spec approval gates planning.
- **Scope (in):** Select named/eligible work; query cited context; prepare the draft through existing templates/setup and preserve findings/unresolved topics. Complete the automated Goal at the saved handoff to ordinary core clarify or human review. Reuse existing interactive clarify with genuine waits outside that Goal; clarification completion is not approval. Preserve identity/current artifacts and explicit human spec approval before planning, at the operator’s chosen review depth. Verify actual native completion rather than infer it.
- **Scope (out):** Planning without explicit spec approval, later workflow phases, invented answers, automatic acceptance, a live Goal waiting through clarification/review, extra clarification skill, per-step delegation/configuration and new controller/persistence infrastructure.
- **Depends on:** none.
- **Governed by:** C-01–C-05.
- **Spec dir:** specs/001-prepare-specification/
- **Notes:** Bootstrap this workflow manually. Demonstrate its behavior and portability in a disposable Spec Kit project, then use it to prepare specifications for later features. Detailed command mappings and eligibility rules belong in its reviewed spec; this entry creates no spec directory.

### 002 — Prepare implementation plan [status: verified]

- **Description:** From an approved specification, compose planning, task generation and analysis/repair into the second human-driven workflow.
- **Outcome:** Plan and tasks pass fresh analysis, and execution stops for full-plan review. The operator can understand and decide whether to approve or simplify the proposed implementation.
- **Scope (in):** Require the approved spec; plan and generate tasks; run read-only analysis; repair accepted findings in affected artifacts and repeat until a fresh pass. At the full-plan gate, explain new infrastructure/subsystems, concrete need, simpler alternatives and the agent’s recommendation. Preserve required input stops, bounded Goals compatibility checks and artifact-based resume.
- **Scope (out):** Implementation before review, automatic approval, universal recovery, model routing or a new controller/framework by default.
- **Depends on:** 001.
- **Governed by:** C-01–C-06.
- **Spec dir:** specs/002-prepare-implementation-plan/
- **Notes:** Dogfood the delivered specification workflow in this feature’s development; apply the planning workflow to later development once delivered. Demonstrate portability in a disposable Spec Kit project. A passing analysis is not human full-plan approval.

### 003 — Deliver approved plan through closeout [status: verified]

- **Description:** From an approved plan, compose implementation, convergence/repair and closeout into a bounded workflow ending at human result review.
- **Outcome:** Eligible approved work is implemented, verified and converged; coherent artifacts and delivery documentation are closed out with the prescribed local commit, and the delivery candidate is presented for human result review.
- **Scope (in):** Implement eligible tasks; run applicable verification; converge, implement follow-up tasks and reassess until clean; reconcile specification, plan, tasks and implementation through merge-bounded flow-back; complete delivery documentation, debrief, and wiki ingestion/lint; make the prescribed local commit; stop for result review. Continue routine authorized steps without repeated OKs, stopping for genuine blockers/input. Verify bounded Goals behavior and preserve artifact-based interruption/resume.
- **Scope (out):** Project-specific integration, declaring the feature integrated or complete, remote push, automatic acceptance, Diagram integration, autonomous workers, universal recovery and extra configuration/delegation infrastructure without demonstrated need.
- **Depends on:** 002.
- **Governed by:** C-01–C-06.
- **Spec dir:** specs/003-deliver-approved-plan/
- **Notes:** Dogfood the delivered specification and planning segments in this feature’s development. Demonstrate the complete local lifecycle and portability in a disposable Spec Kit project, including genuine questions, review stops, repair and interruption/resume. Delivery documentation closeout requires neither integration nor an undefined final feature-completion operation. A local delivery commit is a reconciliation checkpoint; only a later, separately authorized integration merge freezes the feature’s historical meaning.

### 004 — Align workflow contracts with Diagram handoffs [status: verified]

- **Description:** Define an explicit externally selected execution boundary for standalone Farmboy workflows and align their contracts with Diagram-owned coordination, building on the local lifecycle rather than bundling a Diagram implementation.
- **Outcome:** Reviewed contracts distinguish coordination from canonical Git artifacts, define feature ownership and checkpoint/review handoffs, and separate delivery of a verified candidate from authorized integration under project policy. Standalone and externally selected entry paths have explicit request/result boundaries without competing work selection.
- **Scope (in):** Align the delivered local workflow contracts and any necessary workflow boundaries with feature-level metadata, exact Git checkpoint references, one active agent per feature with sequential owner handoffs, historical approval versus latest accepted handoff, human UAT/final-result review authorizing integration, and a separate integration stage governed by project branch/target/check policy. Preserve merge-bounded history and no implicit push; keep integration receipts in Diagram’s database without recursive project commits. Surface missing/conflicting policy and retain executor placement as undecided. Keep core Farmboy workflows usable without Diagram. Define inputs for externally selected feature identity, request, artifact references and requested segment; that entry path must not repeat roadmap selection or activation. Define the appropriate authoritative context/fit source when the roadmap queue is retired, and return result/handoff data including artifact/evidence references, outcome, remaining input or blockers and next review. Diagram retains queue, eligibility, ownership, approvals and handoff records; Farmboy returns execution data across this boundary.
- **Scope (out):** Re-doing the direction/wiki alignment documented now; a full Diagram adapter or optional bridge implementation; imposing bridge packaging; implementing or selecting an integration executor; a concurrency platform, scheduler or worker pool; Git execution or remote push in this feature’s roadmap amendment; changing current feature 001.
- **Depends on:** 003.
- **Governed by:** C-01–C-06; docs/direction.md (eventual Diagram integration direction).
- **Spec dir:** specs/004-align-diagram-handoffs/
- **Notes:** Documentation alignment is recorded now. This future feature aligns the completed local lifecycle’s contracts/workflow boundaries after 003, inheriting its 002 → 001 dependency chain. It creates no specification or active-feature mapping and does not activate any work. Independent-feature concurrency is a contract boundary, not a platform implementation requirement; material changes retain the affected review gate. An optional, separately scoped bridge may acquire Diagram work, supply Farmboy context and report outcomes. Its implementation is a later separate deliverable; packaging remains undecided and need not be a Spec Kit extension.
