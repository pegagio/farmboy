# Operator contract: Deliver approved plan

This human-facing skill contract defines the proposed standalone workflow. It is not a Feature 004 external request/result API or a new serialized protocol. No skill source is implemented by this planning artifact.

## Entry and authority

Example invocation: “Use $farmboy-deliver-approved-plan for the currently selected approved feature; implement, verify, converge and close out locally, then stop for result review.” The skill uses the existing session model/effort and delegates no steps. It requires the selected contained spec/plan/tasks, matching pointer, verified prerequisites and explicit applicable specification/full-plan approval. Missing approval/capability, identity conflict or governing uncertainty stops dependent effects; it does not select another feature.

Selection authorizes the prescribed implementation, verification, useful convergence/repair and delivery documentation closeout, the bounded local delivery commit and narrow implemented write only. It does not authorize verified, scope/dependency/governance amendments, acceptance, integration, merge or push. Optional hooks retain their owning command's contract; the composition explicitly prescribes debrief/wiki closeout independently and avoids repeating an operation whose current result is already valid. Required hooks are actually run; missing capability or required input is not skipped.

## Sequence and outcomes

Implement through the installed capability; verify; converge only after implementation; separately repair current-scope divergence and implement appended follow-ups; reassess to zero actionable gaps/unmet obligations. Complete coherent documentation, attributable roadmap-debrief, relevant wiki-ingest/lint and in-scope correction. Include the narrow implemented update with all scoped delivery artifacts in the final scoped local commit, protecting unrelated work. Report successful delivery only after the actual commit succeeds; if Git errors, report the ordinary error honestly without a success claim.

Successful example: “Awaiting result review. Roadmap implemented and included with the scoped delivery artifacts in local commit: actual Git identity. Spec/plan/tasks, validation, debrief and wiki results: actual links. Limitations/optional suggestions: actual facts. No verified, acceptance, integration, merge or push.” This is an example, not execution evidence.

Required-input example: “INCOMPLETE delivery. Required input: exact product question. Current artifacts: actual paths. Work/attempts completed and issues remaining: actual facts. Next action: answer and separately select ordinary continuation.” With a matching bounded Goal, save/read this first, complete/read native status before asking, and distinguish successful automation handoff from incomplete delivery. Unknown failures/unmet delivery-only objectives do not qualify.

## Failure, resume and later acceptance

Resume inspects existing artifacts/Git/roadmap and approvals, preserves answers/task identities and acts only on missing/affected work. Valid pending result review is presented without duplicate effects. Missing trustworthy debrief boundary or unsafe commit scope is a specific blocker, not permission to invent evidence or include unrelated changes.

Only later explicit applicable human result acceptance authorizes a separate ordinary implemented→verified action; success of checks/debrief or silence cannot replace acceptance. Material scope/meaning changes require affected human review. The delivery skill ends at its saved result/input handoff and never starts another workflow or Goal.
