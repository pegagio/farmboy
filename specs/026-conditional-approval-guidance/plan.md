## Design

State the conditional rule beside later acquisition: when the applicable approval has review conditions, assessment.conditions must contain a meaningful current assessment. Explain actual artifact/phase checks, distinguish historical invocation limits from separately authorized later work and stop on unresolved applicability. Do not require one record per condition or fixed wording. An approval without conditions does not need synthetic evidence.

Provide one small, internally consistent TEST ONLY fixture example with current approval/handoff/revision/artifact facts and meaningful applicability text. Real callers replace illustrative values with verified current data; copying fixture IDs or text never grants authority. Pin Request.approval_id and assessment.approval_id to the same applicable historical spec decision; do not invent a plan approval. Show the read-only planning-offer request and the precise additions for acquisition: workspace/branch/segment/purpose and discovery_selected only when that actual route applies. Those acquire-only fields must not leak into the offer, whose command requires --request-file. Keep the example JSON parseable and consistent with the native action allowlists; do not create a reusable serializer/report builder.

A read-only offer can expose a malformed request before the first acquire. It grants no run. A definitive rejected acquire still ends a launcher invocation immediately; even a confirmed absent operation does not authorize resubmission. Uncertain results require inspection, never assumed ownership or automatic recovery.
