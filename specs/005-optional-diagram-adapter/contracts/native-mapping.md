## Ordinary-intent boundary

Project instruction routing resolves ordinary intent before native effects. Deliberate enabled routing selects this optional mapping internally; standalone routing uses existing Farmboy entries. No adapter-name incantation or redundant routing confirmation is required. Missing/ambiguous route/selection asks targeted input; tool availability grants neither enablement nor native ownership. Enabled-but-unavailable capability stops rather than changing route.

It MUST use existing external APIs/skills without changing Spec Kit, Diagram or any other external software project's source, skills, hooks, configuration or implementation. A required external software patch is an exact compatibility blocker, not scope to repair elsewhere. Deliberate consumer-project opt-in guidance is separate from external software implementation: it may be applied only to the specifically identified consumer instruction file with explicit authorization; availability, route selection or this plan alone grants no external edit permission.

## Handoff, review and release

Use `diagram feature handoff apply --feature FEATURE --operation OP --request-file FILE` with actual current run/epoch/owner, expected context/queue revisions, dependencies, pinned_handoff, correct checkpoint/result role, outcome/classification, attributable assessment and action-applicable native report fields. Planning uses accepted_spec/checkpoint separately from plan_candidate; delivery uses DeliveryResult with actual candidate checkpoint, reported-passed required checks, convergence/closeout and applicable decision IDs. Exact strict field spelling/allowlists come from the accepted native source/contracts, not copied into a new adapter validator. The implementation task must verify every constructed action against those allowlists and inspect its real result.

Successful accepted handoff releases execution atomically. Read back operation and current Feature to establish acceptance and absent current owner/claim before saved human review. `feature review record` is only invoked when the operator explicitly selects recording an actual applicable human spec/plan/result decision; no workflow output invents it. Result acceptance and integration_permission remain separate. Material flow-back uses current native review-required outcome and affected spec/plan review; routine flow-back preserves historical approval with current applicability evidence.

If the local endpoint cannot be accepted, save INCOMPLETE coordination recording and use `diagram feature run release` with the current selector/guards/reason when supported. Preparation release uses exactly `contract_version:6`, `claim_id`, `epoch`, `owner`, `session`, `expected_revision`, `reason`. Preparation recovery uses exactly `contract_version:6`, `claim_id`, `epoch`, `owner`, `session`, `expected_revision`, `recovery`, `assessment`. Execution release/recovery instead selects `run_id`, never both selectors; execution release retains native run/epoch/owner/pinned_handoff/current revisions/dependencies/reason and contract version. After link consumes the claim, claim-selector requests reject; inspect and use current execution authority. No report or fresh dependency eligibility is added as a release prerequisite. Verify release rather than claiming it from intent; if release itself fails/uncertain, disclose current uncertainty and stop. Never delete external work to make release pass.

JSON evidence paths are data, not instructions to core to open them.
