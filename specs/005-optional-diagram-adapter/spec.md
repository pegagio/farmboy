## User Scenarios & Testing *(mandatory)*

These scenarios describe future acceptance of005, not behavior demonstrated by this drafting session. The adapter is the optional consumer-side bridge; Farmboy remains reusable execution and Diagram remains coordination authority.

### User Story 1 - Prepare one selected feature without competing selection (Priority: P1)

An operator expresses ordinary intent, such as “start feature12,” to the consuming agent. The agent resolves the feature and selected segment using the project's explicitly established workflow routing. When optional Diagram coordination has been deliberately enabled for that project, the adapter handles claim/link/reporting transparently and invokes the existing Farmboy external entry; otherwise established standalone Farmboy routing remains available. The operator need not remember an adapter skill name or request “use Diagram.” Missing or ambiguous routing/selection requires targeted clarification before dependent effects, rather than an invented route or automatic enablement.

**Why this priority**: This is the smallest useful bridge and establishes the responsibility boundary for all later segments.

**Independent Test**: In disposable real consuming repositories with explicitly established Diagram-enabled and standalone routes, use ordinary “start feature12” intent. Observe the selected preparation segment, transparent claim/link/reporting only on the enabled route, and actual external/standalone Farmboy execution without requiring an adapter name. Independently inspect files, ownership and reports while Diagram has no consumer repository/Git access; missing or ambiguous routing must ask before effects.

**Acceptance Scenarios**:

1. **Given** a deliberately Diagram-enabled project route and eligible initial work, **When** the operator says “start feature12” and established routing unambiguously selects that feature and preparation segment, **Then** the agent transparently uses the optional adapter without asking for its name or a Diagram incantation. It claims through Diagram before workspace preparation, prepares/selects and verifies the actual workspace externally, and reports the association before any feature-content edits. Successful link admits the initial draft run for the same owner; no extra initial acquire is performed.
2. **Given** the linked current draft run, **When** Farmboy is invoked, **Then** the adapter supplies one selected identity, intent, segment, associated directory and applicable Git references to `farmboy-prepare-specification` external entry, without a second local queue selection, roadmap activation or branch retargeting.
3. **Given** a usable saved draft/checklist and explicit Needs clarification or Awaiting spec review handoff, **When** preparation ends, **Then** the adapter records the actual result and releases current execution authority through supported Diagram operations before waiting for human input. Successful native Goal completion is established separately through supported completion and readback.
4. **Given** missing association, contradictory identity or a helper that would rewrite the caller's pointer, **When** dependent execution is considered, **Then** the adapter stops for the specific conventional preparation needed, preserves existing work and performs no silent retargeting or core-tool patch.

5. **Given** missing or ambiguous project routing, feature identity or segment selection, **When** ordinary intent is received, **Then** the agent asks only for the unresolved routing/selection input before dependent effects; it does not guess, enable Diagram, or repeat an already settled routing choice.

### User Story 2 - Continue through genuine questions and explicit reviews (Priority: P1)

The operator can clarify the saved draft, review the whole specification, prepare and review the full plan, and review a delivered candidate. Each action has current authority and ends at its prescribed boundary.

**Why this priority**: Reduced toil is useful only if actual human decisions remain authoritative.

**Independent Test**: Exercise one complete disposable feature with genuine answer waits, explicit specification/full-plan/result decisions and an affected-artifact repair. Observe each stop and separate continuation.

**Acceptance Scenarios**:

1. **Given** Needs clarification, **When** the operator separately requests clarification in ordinary language through the established project route, **Then** the adapter obtains current clarification authority before edits, retains it while actively clarifying between questions, integrates genuine answers and releases at the saved human-review handoff. The completed preparation Goal is not resumed to answer questions.
2. **Given** resolved questions, **When** clarification ends, **Then** the result is Awaiting spec review. Only explicit applicable whole-spec approval establishes Ready for planning; review can instead return to Needs clarification.
3. **Given** applicable explicit specification approval and a deliberately Diagram-enabled project route, **When** the operator says “plan this feature” with unambiguous feature context and segment selection, **Then** the agent transparently uses the adapter, without requiring its skill name or an extra routing confirmation. The adapter invokes `farmboy-prepare-implementation-plan` external entry and returns the complete plan/tasks and fresh analysis for human full-plan review. It does not start delivery or silently approve new machinery.
4. **Given** applicable spec and full-plan approval plus separately selected delivery, **When** `farmboy-deliver-approved-plan` external entry succeeds, **Then** the result is an actually verified/converged local candidate with coherent artifacts and a scoped local commit, Awaiting result review. Check the actual commit after it exists; a failed commit is incomplete delivery.
5. **Given** any successful check, Goal or saved report, **When** a later segment or integration is considered, **Then** none substitutes for the required explicit selection, applicable human decision or current Diagram authority.

### User Story 3 - Resume safely with current evidence (Priority: P1)

An operator can resume interrupted work without losing answers or repeating accepted effects. Changed upstream input and changed meaning return to responsible checks and reviews.

**Why this priority**: Stale authority and replay can corrupt otherwise correct workflow execution.

**Independent Test**: Interrupt before and after accepted association/handoff, lose one operation response, and change an upstream accepted input. Inspect preservation, current authority and affected reassessment before continuation.

**Acceptance Scenarios**:

1. **Given** an uncertain Diagram response, **When** the adapter continues, **Then** it inspects the supported operation outcome before retrying. An accepted historical replay neither repeats Farmboy/Git effects nor restores old authority; unresolved inspection remains uncertainty.
2. **Given** saved answers, performed work or a valid pending review, **When** work resumes, **Then** the adapter presents that handoff or performs only missing/affected work under current authority, without duplicate selection or activation.
3. **Given** stale owner/revision, changed accepted upstream input or changed binding, **When** dependent work or submission is attempted, **Then** the adapter stops dependent effects, inspects actual local facts and current recorded authority, and follows supported reassessment/release/reclaim rules. It does not silently rebase a claim or assume semantic independence.
4. **Given** routine in-scope flow-back, **When** artifacts are reconciled, **Then** historical approval remains historical and applicable unchanged work is not reapproved. A material meaning change requires the affected review again; the reviewed checkpoint stays distinct from the latest accepted handoff.

### User Story 4 - Preserve independence and integration limits (Priority: P2)

A project can use standalone Farmboy without Diagram, or optionally coordinate independent features through Diagram without coupling core execution to the bridge or granting integration implicitly.

**Why this priority**: The optional bridge must preserve portability and project-specific policy.

**Independent Test**: Exercise ordinary intent and direct invocation of each of the three Farmboy-owned entries under enabled, standalone, missing/ambiguous and enabled-but-unavailable routing. Independently observe route checks before effects, first adapter entry versus verified current adapter context, rejected stale/foreign context, no recursion or duplicate claims/reports, and correct ownership duration. Run standalone without Diagram, then isolated-feature/conflicting-owner cases and result review without integration. These are observed agent behaviors, not a claimed absolute runtime interception mechanism.

**Acceptance Scenarios**:

1. **Given** an explicitly established standalone project route with optional Diagram coordination disabled or absent, **When** ordinary intent or direct skill invocation selects one of the three Farmboy segments, **Then** the agent uses the corresponding standalone entry with its existing local selection/context, approvals and endpoint, without an adapter or Diagram dependency.
2. **Given** one active owner for a feature, **When** another owner attempts conflicting work, **Then** it receives no authority. Independent features may proceed in isolated branches/worktrees; sequential ownership requires an authorized handoff.
3. **Given** accepted delivery, **When** integration has not been explicitly authorized, **Then** the adapter performs no merge/push. Later integration requires current project branch/target/check/instruction policy and a separately authorized external executor; missing/conflicting policy stops dependent integration.
4. **Given** destination instruction/policy changes require human review, **When** later integration is prepared, **Then** that review precedes their effect. Diagram serializes recorded repository/target keys and owns integration receipts referencing actual Git checkpoints, without receipt-only commits.

5. **Given** Diagram or its adapter is installed/available but has not been deliberately enabled for this project, **When** ordinary intent is received, **Then** availability alone grants no routing, segment, ownership or integration authority. An established standalone route remains standalone; missing/ambiguous routing requires targeted input. A deliberately enabled route with unavailable capability reports that limitation rather than silently enabling, installing or falling back to another route.

6. **Given** ordinary-intent routing would require a patch to Spec Kit, Diagram or another external software project, **When** the agent assesses capability, **Then** it reports the exact incompatibility and stops affected work rather than editing that software. Consumer opt-in guidance is a separate, specifically authorized instruction-file action; a segment launch or this plan does not authorize arbitrary external edits.

7. **Given** any of the three Farmboy entries is invoked directly or reached through ordinary-intent routing, **When** execution is considered, **Then** that entry checks the explicitly established project route before effects. An enabled Diagram route enters the adapter if no current adapter context exists; adapter-invoked inner execution continues only with verified current feature/segment/owner/input context. It does not recursively re-enter the adapter or duplicate claims/reports. Stale or foreign claimed context stops dependent effects for current verification. Standalone stays standalone; missing/ambiguous routing asks targeted input and enabled-but-unavailable routing stops without fallback.

### Edge Cases

The adapter must preserve work and distinguish unavailable evidence from authority or success in these cases:

- A preparation claim exists but no workspace location is recorded; unknown location does not mean no external files exist.
- A Farmboy entry is invoked directly, or an inner invocation claims old/foreign adapter context; route checks still precede effects and no unverified wrapper flag grants authority. Existing current context must not cause recursive adapter entry, duplicate claims/reports or premature release/completion.
- Diagram is available but not deliberately enabled, project routing is missing/conflicting, or “this feature” is ambiguous; tool presence never decides authority. An enabled route with missing capability stops affected work rather than silently switching to standalone.
- Workspace preparation fails or input/binding changes before link; no content edits or automatic external cleanup follow.
- A necessary checkpoint encounters an explicit no-commit restriction, unrelated staged/unstaged/untracked changes or inseparable shared-file edits; only safe feature-scoped commits are permitted, otherwise preserve all work and request targeted input.
- Reported identity is internally consistent but physically false; consumer verification must detect what Diagram cannot independently inspect.
- Explicit feature, standard pointer and effective environment directory disagree, including equivalent aliases whose literal persistence would rewrite the pointer.
- A technical/native failure interrupts drafting or a delivery-only objective is unmet; neither becomes a successful human-input endpoint.
- An incomplete-for-input planning handoff meets its bounded automation objective while the feature and delivery remain incomplete.
- Old accepted operation evidence exists after ownership changed; historical replay grants no current authority.
- Dependency eligibility becomes unavailable while the owner needs to release; truthful release must remain possible.
- A replacement owner needs stopped-writer confirmation and preservation of committed, dirty and untracked work; elapsed time is not takeover authority.
- Work may legitimately specify/plan ahead of upstream integration; changed accepted input still requires reassessment, without a new blanket upstream-integrated gate.

**Checkpoint authority clarification**: The operator approved the disclosed segment-launch commit rule in FR-010. This clarification does not approve the full plan, start implementation or authorize a commit in this planning/editing task. Existing spec approval remains applicable outside this clarification.

## Requirements *(mandatory)*

The following requirements constrain observable behavior. Exact transport and adapter placement are planning choices, not a new coordination model.

### Functional Requirements

- **FR-001**: The adapter MUST be optional, with deliberate installation/enabling for a project; availability alone MUST NOT enable Diagram coordination or grant runtime authority. All three existing standalone Farmboy entries MUST retain their prescribed local behavior without Diagram, an adapter runtime dependency or a replacement writable queue.
- **FR-002**: Diagram MUST remain authoritative for selection/eligibility/dependencies, claims/current recorded ownership, approvals/transitions, accepted handoffs and report consistency. Git MUST remain canonical for specifications, plans, tasks, implementation and evidence. The consuming agent/adapter MUST own repository/Git/workspace/artifact verification; accepted reports MUST NOT be described as independent physical verification by Diagram.
- **FR-003**: For an initial specification run, the adapter MUST use current supported claim → external preparation/verification → report-based link → full draft authority. A claim permits setup only. Link success MUST supply full content authority for the same owner without a redundant initial acquire. Queue presence, intended paths and project registration alone MUST NOT authorize feature-content edits.
- **FR-004**: Before linking or invoking helpers, the adapter MUST verify actual repository/worktree identity, full symbolic branch, relevant HEAD/checkpoint, required cleanliness, declarations, artifact paths/digests and applicable consumer instructions. It MUST establish the existing contained feature directory and standard pointer; explicit identity, pointer and effective environment MUST agree. Helper persistence MUST already equal the pointer's literal value. Missing/conflicting preparation MUST stop dependent work, without pointer tricks or core-tool changes.
- **FR-005**: The consuming agent MUST resolve the selected feature/segment and available project context through established routing rather than requiring the operator to construct an adapter invocation. On a deliberately Diagram-enabled route, the adapter MUST invoke the three existing external entries for the selected segment with enough current identity, intent, applicable approvals, Git context and artifacts to execute. Farmboy MUST NOT repeat local roadmap selection/activation, require a retired queue/absent wiki, or infer a later segment. Relevant authorized wiki context MAY be used. No fixed new authority packet/store is required.
- **FR-006**: Draft preparation MUST end at a usable saved spec/checklist and explicit Needs clarification or Awaiting spec review handoff. Material product questions MUST remain visible for separately invoked ordinary clarification, never fabricated answers or a preparation Goal awaiting human answers. No material question means direct human review, not manufactured clarification.
- **FR-007**: Ordinary clarification MUST obtain separately current Diagram authority before edits, use genuine answer waits and retain authority while active between questions. Saved human handoffs MUST record the actual outcome and release executing authority before waiting; no consumed preparation claim may remain as an extra lock. Farmboy returns handoff data; the adapter uses Diagram operations for ownership effects.
- **FR-008**: Explicit applicable whole-spec approval MUST gate planning; explicit full-plan review/approval MUST gate delivery. Resolved questions, passing analysis and native completion MUST NOT approve artifacts. Changed meaning MUST return to affected review, while unchanged applicable approval is retained.
- **FR-009**: Planning MUST preserve plan/task generation, read-only analysis and separately authorized repair through a fresh passing result or truthful prescribed input/blocker handoff. Full-plan review MUST explain concrete new infrastructure, simpler alternatives and recommendation; the operator decides. Delivery MUST preserve verification/convergence, flow-back, documentation and actual scoped local commit before result review.
- **FR-010**: The adapter MUST disclose that explicitly launching the selected segment authorizes necessary feature-scoped checkpoint commits with normal project hooks, subject to explicit user restrictions/overrides; merely selecting or viewing a feature MUST NOT grant this authority. It MUST reconcile affected artifacts, stage and verify only selected feature changes, preserve unrelated staged/unstaged/untracked work, and never sweep the entire workspace or infer merge/push permission. If a restriction prevents a required commit or safe isolation cannot be established, it MUST preserve work and stop for targeted input; failed hooks/commits remain truthful blockers. Every return MUST identify the selected work/segment, actual successful/incomplete/blocked/interrupted outcome, artifact/evidence references, checkpoint/current working state, remaining input/blockers and next review/action. Uncommitted artifacts MUST disclose base revision and dirty state; only an actual revision may be called a committed checkpoint. Local execution and accepted Diagram recording MUST be distinguished.
- **FR-011**: A native Goal MUST complete only when its entire bounded objective is actually met, using exposed supported completion and readback before human waiting. A permitted saved input handoff can finish automation while delivery stays incomplete; unknown technical failures and unmet delivery-only objectives cannot. Goal completion MUST NOT imply feature completion, approval, accepted result, integration or permission for continuation. Unavailable native controls MUST be reported as a compatibility limitation.
- **FR-012**: Before dependent effects and submission, the adapter MUST inspect current Diagram authority/input/dependency/approval conditions and verify applicable local facts. It MUST reject stale/superseded authority and reassess changed upstream accepted input with affected flow-back. Permitted asynchronous specification/planning MUST NOT acquire an invented upstream-integrated prerequisite.
- **FR-013**: Uncertain mutation responses MUST remain uncertain until supported inspection resolves them. Exact accepted retries MUST NOT repeat external effects; conflicting operation reuse and stale authority MUST not be bypassed. Resume MUST preserve answers/work and valid pending review, reassessing only missing/affected work. Recovery/replacement MUST use existing explicit stopped-writer, preservation and fencing rules, with no timeout takeover, process control or cleanup framework.
- **FR-014**: One active agent per feature MUST hold across segments. Independent features MAY run concurrently only in isolated workspaces/branches. Sequential owners MUST receive current coordinator authority after authorized handoff; Farmboy MUST NOT add an ownership service.
- **FR-015**: Successful delivery MUST stop for explicit human result acceptance. Integration permission MUST remain a distinct explicit decision governed by actual project branch/target/check/instruction policy and separately authorized executor. The adapter MUST NOT choose executor placement, perform integration merely because review passed, or imply push authority. Required destination-policy review MUST precede effect. Diagram owns serialized integration records/receipts; only integration merge freezes feature meaning.
- **FR-016**: The adapter MUST consume supported current Diagram contracts and attributable report semantics, without redesigning029 interfaces, assuming unfinished028 behavior works, or introducing a competing lifecycle/store. Before dependent implementation/acceptance, final028 delivered behavior and versions MUST be reconciled with this specification and actual supported capabilities. Draft authoring and review MUST NOT be blocked on that future runtime proof.
- **FR-017**: Acceptance MUST include an actual installed adapter/agent run independently observed by a separate executing/evaluating session, using disposable real repositories, Git and coordination state. It MUST cover all three external entries, ordinary clarification and explicit human gates/repair, all three standalone regressions, one-owner/isolation, stale authority/input, changed approvals, missing context, interruption/replay and release/current-authority continuation. Simulations alone MUST NOT establish acceptance; test-driver answers/approvals MUST be labelled TEST ONLY and authorize no real work.
- **FR-018**: Acceptance evidence MUST distinguish actual consumer verification, Diagram consistency checks, observed/simulated/excluded/unobserved cases and actual native outcomes. Committed delivery MUST be verified after the commit exists. No production reset, live integration or push is implied by acceptance requirements. No scheduler/fleet, attestation/ledger/accounting/recovery framework or automatic workflow expansion is included.

- **FR-019**: The agent MUST accept ordinary intent such as “start feature12” or “plan this feature” through the project's explicitly established workflow routing, preserving one explicitly selected feature/segment and all applicable authority/review conditions. When Diagram coordination is deliberately enabled, it MUST transparently use the optional adapter for claim/link/reporting; otherwise it MUST retain the established standalone Farmboy route. Operators MUST NOT be required to remember an adapter skill name, say “use Diagram,” or reconfirm an unambiguous established route. The agent MUST ask targeted routing/selection questions only when that information is missing or ambiguous, without replacing required product questions or human review/input boundaries. Routing MUST NOT silently grant authority, enable/install coordination from tool presence, launch a later segment, or fall back from an enabled but unavailable route. No background watcher, automatic dispatch or new configuration framework is included. The exact project-instruction/routing mechanism belongs to later plan design.

- **FR-020**: 005 implementation MUST remain within Farmboy's optional adapter, minimal routing checks in its three own entries, its own documentation/guidance and focused acceptance fixtures. It MUST use existing external APIs/skills without changing Spec Kit, Diagram or any other external software project's source, skills, hooks, configuration or implementation. A required external software patch is an exact compatibility blocker, not scope to repair elsewhere. Deliberate consumer-project opt-in guidance is separate from external software implementation: it may be applied only to the specifically identified consumer instruction file with explicit authorization; availability, route selection or this plan alone grants no external edit permission.

- **FR-021**: Each of the three Farmboy-owned entries MUST check explicitly established project routing before effects, for both ordinary-intent and direct skill invocation. A deliberately enabled Diagram route MUST enter the optional adapter or continue inner execution only with verified current adapter context for the selected feature/segment, current owner/authority and applicable input. Mere presence of a wrapper flag or historical context MUST NOT establish authority; stale, foreign or unverified context MUST stop dependent effects for current verification. Existing current context MUST NOT trigger recursive adapter entry or duplicate claims/reports. One adapter invocation MUST retain responsibility for its whole segment and actual handoff/release; inner commands MUST NOT prematurely release ownership or complete a wider Goal. An established standalone route MUST stay standalone without a Diagram dependency; missing/ambiguous routing MUST ask targeted input and enabled-but-unavailable routing MUST stop without fallback. This supersedes the prior plan choice that all core entries remain unchanged: only small Farmboy-owned routing checks are proposed. These are agent behavior requirements requiring real independent tests, not an absolute runtime interception guarantee or a mandate for Spec Kit hooks.

### Key Entities *(include if feature involves data)*

These are existing semantic concepts, not proposals for new persistence.

- **Selected request**: One Diagram feature, intended segment and applicable current input/context; selection is not approval.
- **Current authority**: Diagram's exclusive claim or fully linked executing run, with current owner/session and revision/fencing facts. Historical responses are evidence, not renewed authority.
- **Workspace association**: Consumer-verified repository/worktree/branch/checkpoint and artifact facts reported to Diagram; recorded locators do not prove current physical availability.
- **Human decision and reviewed checkpoint**: Explicit applicable specification, full-plan, result or integration decision, distinct from the latest accepted handoff checkpoint.
- **Saved handoff**: Durable canonical artifacts, truthful outcome/evidence and required next action, enabling prescribed recording/release without approving the next step.
