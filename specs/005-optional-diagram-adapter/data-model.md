# Data model: Reuse native coordination facts

The adapter introduces no database, durable runtime schema, ownership store, approval register or event journal. This document names semantic inputs/results already present in native Diagram and canonical Git. Temporary JSON is native transport, not a second source of truth.

## Selected invocation

Ordinary operator intent plus explicitly established project guidance resolves selected store/config, project/feature, one segment, owner/session and accessible consumer context. The agent supplies internal adapter arguments; the operator need not name a skill or say “use Diagram.” A deliberately enabled Diagram route uses the optional adapter; an established standalone route uses standalone Farmboy. Missing/ambiguous routing asks targeted input; installed tools alone grant no route and unavailable enabled routing never silently falls back. This is existing instruction context, not a new configuration schema. Required rule: **One selected feature and one explicitly requested segment.** Supported segments are preparation, ordinary clarification, planning and delivery; integration/worker/fleet execution rejects. These are documentation labels, not new persisted enum values. Project/feature identity must agree with returned native records; an offer/queue read grants no ownership. Explicitly launching one adapter segment includes disclosed authorization for necessary feature-scoped checkpoint commits with normal project hooks. Merely selecting or viewing a feature grants no commit authority. Explicit user restrictions/overrides remain controlling; this authority grants no merge or push. Stage only the selected feature changes: preserve unrelated staged, unstaged and untracked work, never sweep the entire workspace, and stop for targeted input if safe isolation cannot be established.

## Entry routing and current context

Each of the three Farmboy-owned entries checks the established route before effects. Direct enabled entry without an active adapter invocation enters it once and propagates the result; already-current inner context continues only after the adapter/reference verifies selected project/feature/segment, native owner/session/run/epoch, applicable input/approvals and association. These are existing facts and ordinary invocation evidence, not a new serialized envelope, callback API, persisted marker or authority register. Flag-only/historical/foreign context is insufficient. No recursive wrapping, second claim/report, early release or premature completion of the whole adapter Goal follows an inner return. Explicit standalone routing requires no Diagram/reference dependency.

## Authority and input

Native current claim/run, owner/session, revision/epoch, current queue/dependency pins, applicable decision IDs and accepted input are used unchanged. Required rule: **Historical operation replay grants no current authority.** Initial claim permits setup only; successful link consumes it and admits exactly one full draft run, with no initial acquire. Later segment acquisition uses current native gates. Recovery preserves original input; no silent repin, takeover or transfer.

## Consumer association and observations

Reuse native `repository_id`, `instance_id`, `worktree_key`, absolute workspace locator, full `refs/heads/` branch, expected HEAD, role-specific checkpoint/artifact digests, attributable assessment and action-required cleanliness. Required rule: **Explicit identity, pointer and effective directory agree; helper persistence equals the existing pointer's literal value.** The consuming agent derives actual physical facts under consumer instructions; Diagram only validates recorded/report consistency. Do not require historical reviewed checkpoints to equal current result HEAD. Handoff/recovery may preserve dirty work under native rules, while clean-required admission/review must satisfy actual cleanliness.

## Result and review

Existing Farmboy return distinguishes successful/incomplete/blocked/interrupted, selected segment, paths/evidence, remaining input and next action. Required rule: **Only an existing verified commit is a committed checkpoint.** Dirty state is paired with actual base/current working facts. Diagram accepted handoff is a distinct fact requiring native acceptance/readback; failure/uncertainty never becomes success. Human decisions identify exact applicable reviewed content and remain separate from latest accepted handoff. Native Goal state is separately observed using supported controls and never stored as a replacement feature outcome.

## Retention and transitions

Existing spec/plan/tasks/validation/delivery notes retain durable work and exact missing input/operation identity when needed. No new mandatory manifest/history format is introduced. Native operation IDs retain their existing replay purpose; repeated external effects are not a retry strategy. Temporary transport files contain only required native action fields and use normal project/temporary-file permissions; preserve needed unresolved transport/evidence under authorized existing notes rather than invent a journal. No secrets or private machine identities enter project artifacts.

The flow is explicit selection → current claim → consumer setup/verification → link/full draft run → saved local result → actual native handoff/release → ordinary human review. Later selected clarification/planning/delivery obtains current authority and returns to its own saved human boundary. These arrows describe native operations, not a new adapter state machine or automatic phase dispatcher.

## External software boundary

005 implementation MUST remain within Farmboy's optional adapter, minimal routing checks in its three own entries, its own documentation/guidance and focused acceptance fixtures. It MUST use existing external APIs/skills without changing Spec Kit, Diagram or any other external software project's source, skills, hooks, configuration or implementation. A required external software patch is an exact compatibility blocker, not scope to repair elsewhere. Deliberate consumer-project opt-in guidance is separate from external software implementation: it may be applied only to the specifically identified consumer instruction file with explicit authorization; availability, route selection or this plan alone grants no external edit permission. Consumer opt-in is a separate bounded `AGENTS.md` instruction edit described in the plan, not a new persistent routing store or an implicit external change.
