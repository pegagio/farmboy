## Packaging and invocation

**Decision**: Add one optional repository skill, `.agents/skills/farmboy-diagram-work/SKILL.md`, with one adjacent `references/native-protocol.md` for the detailed command/field mapping. The agent routes ordinary operator intent using explicit project instructions and invokes `$farmboy-diagram-work` internally only when Diagram coordination is deliberately enabled, resolving project/feature, segment, selected existing store/config and authorized consumer context. The operator need not remember its name. Established standalone routing remains unchanged; missing/ambiguous routing asks targeted input, unavailable enabled routing stops without fallback. It composes the three existing external skills, or ordinary `speckit-clarify`; no fourth workflow implementation replaces them. A request for named/next work can consult the native queue within explicit operator selection scope, but cannot launch more than one selected feature/segment. Ambiguous selection stops.

**Rationale**: Farmboy already distributes agent-readable skills. One entry keeps Diagram authority outside generic core and removes manual claim/link/report toil while remaining operator-driven. The adjacent reference keeps the entry readable without hiding authority in a generic engine. No auto-installation, dispatcher, daemon, package manager dependency or new CLI is needed.

**Alternatives**: Documentation-only manual commands are smaller but leave the exact orchestration burden this feature addresses. Four segment-specific adapter skills duplicate ownership/report logic. A Python wrapper could type-check transport but cannot itself provide genuine human review/native agent execution and adds another executable lifecycle to maintain. A service/Spec Kit extension adds packaging and persistent machinery without a present need. Recommend the single optional skill; re-evaluate a helper only for demonstrated defects requiring it and renewed review.

## Project routing and external-software scope

**Decision**: Reuse the consumer project's existing `AGENTS.md` as an explicit instruction surface. Supply a copyable routing paragraph and standalone alternative in Farmboy's own `docs/diagram-adapter.md`; add no file format, setting parser, installer, hook or discovery engine. The operator applies the identified consumer guidance edit deliberately or separately authorizes that exact edit. The optional skill must already be accessible through existing supported mechanisms. No real consumer edit or enablement is selected here.

005 implementation MUST remain within Farmboy's optional adapter, minimal routing checks in its three own entries, its own documentation/guidance and focused acceptance fixtures. It MUST use existing external APIs/skills without changing Spec Kit, Diagram or any other external software project's source, skills, hooks, configuration or implementation. A required external software patch is an exact compatibility blocker, not scope to repair elsewhere. Deliberate consumer-project opt-in guidance is separate from external software implementation: it may be applied only to the specifically identified consumer instruction file with explicit authorization; availability, route selection or this plan alone grants no external edit permission.

**Rationale**: Existing agent instructions can select existing skills in response to ordinary intent, so the design does not require Spec Kit or Diagram changes. Routing is a prescribed response to a current user request, not background dispatch. Actual agent adherence and capability remain future independently observed acceptance, not an assumption of installed runtime behavior.

**Alternatives**: Requiring a named adapter invocation burdens the operator. A new Spec Kit hook/extension or Diagram modification violates the explicit scope condition. A routing parser/configuration framework is unnecessary. Recommend one bounded project instruction paragraph plus Farmboy-owned guide; stop on any incompatibility that would require an external patch.

## Direct-entry routing seam

**Decision**: Add one small route/return section to each of the three Farmboy-owned skills. Explicit standalone routing keeps its current body and no Diagram dependency; missing/ambiguous routing asks targeted input, unavailable enabled routing stops. Enabled direct entry hands off once to the adapter and propagates its result without executing twice. An inner invocation continues only with current verified project/feature/segment/owner/input/association context; historical/flag-only/foreign context is no authority. The adapter/reference performs existing native validation and owns full-segment report/release/Goal completion; the three skills do not acquire/report or prematurely complete the outer endpoint.

**Rationale**: Ordinary project guidance helps discovery but does not cover direct named skill use by itself. A concrete Diagram branch at a small seam keeps coordination protocol isolated and future concrete changes understandable. Existing invocation evidence plus native reads suffice; no new context store/schema, plugin interface, registration, discovery, hook catalog, second integration or service is needed. This is tested agent behavior, not a runtime interception guarantee.

**Alternatives**: AGENTS-only routing leaves direct-entry coverage unspecified. Existing Spec Kit before/after hooks bracket core commands: preparation skips full specify; planning/analyze and implement/converge can repeat; after-command hooks do not define full Farmboy closeout, error cleanup, human-wait or outer Goal boundaries. Installed1.0.10.dev0+pegagio.2 HookExecutor delegates execution to the agent. Do not add a Spec Kit extension/hook or patch to solve the different boundary; recommend minimal Farmboy-owned seams and actual independent direct-entry tests.

## Native transport and compatibility

**Decision**: Use the existing local `diagram` CLI and its bounded `--request-file` JSON transport, plus explicit read/operation inspection commands; no HTTP/RPC/MCP bridge or automatic legacy lane. Use action-specific native request objects directly, not an adapter envelope/schema. The agent serializes JSON with an already available runtime/tool, writes a temporary transport file only as explicitly authorized transport, parses strict success/error results and removes only its own disposable transport on ordinary successful cleanup. It preserves evidence of uncertain operations in existing feature notes and relies on Diagram operation inspection, not a new journal.

**Rationale**:029 establishes attributable report semantics and028 revises initial admission. Project2/Issue3 remain; accepted028 implements Feature6/schema16, superseding029 Feature5/schema15. Current accepted committed028 interfaces have been reconciled read-only against the upstream baseline at closeout HEAD `8c938d7273b7e5f648ff2c9b88871f7bd88691ff`; recheck actual compatibility/capability before dependent005 implementation. No production schema mutation, migration, fallback to enroll/Feature5, core probing of consumer paths or report-only verification fiction.

**Alternatives**: A network transport adds deployment/authentication and another authority path. A copied JSON adapter packet duplicates native validation and drifts. A version-probing compatibility engine expands scope. Recommend documented exact supported native operations and explicit compatibility stops, with existing read-only version/contract inspection only when authorized.

## Checkpoint permission

**Decision**: Keep Farmboy's local draft endpoint distinct from a Diagram accepted handoff. Native reports reference actual committed checkpoint/artifact roles. The adapter must inspect local files and immutable blobs/digests, then report only a real compatible checkpoint. It never makes an uncommitted draft look committed or reuses an old checkpoint for changed bytes. Explicitly launching one adapter segment includes disclosed authorization for necessary feature-scoped checkpoint commits with normal project hooks. Merely selecting or viewing a feature grants no commit authority. Explicit user restrictions/overrides remain controlling; this authority grants no merge or push. Stage only the selected feature changes: preserve unrelated staged, unstaged and untracked work, never sweep the entire workspace, and stop for targeted input if safe isolation cannot be established. Reconcile affected artifacts before committing. Verify the staged scope and resulting checkpoint without including or disturbing unrelated changes. If an explicit restriction prevents a required commit or safe isolation is unresolved, preserve the saved work and exact base/dirty state, report recording as incomplete, obtain supported current-owner release if possible and stop for targeted input. A normal hook/commit failure remains incomplete while authorized routine repair proceeds; unresolved failure is reported as the precise blocker, without bypassing hooks. Later continuation rechecks current authority/input and reuses intact work. This planning/editing task launches no adapter segment and authorizes no commit. Selected delivery retains its prescribed scoped local commit.

**Rationale**: This applies the settled segment-launch authority while preserving project rules, unrelated work and Diagram's committed-evidence requirement. It avoids repeated permission requests for prescribed checkpoints without broad Git authority. Rejected/uncertain recording stays incomplete. No receipt-only commit follows a result; native receipts remain in Diagram.

**Alternatives**: Asking again for every necessary scoped checkpoint adds redundant approval. Committing merely on feature selection or sweeping dirty workspace changes exceeds authority. Reporting changed bytes as an old commit is false. Changing Diagram to accept arbitrary dirty snapshots is out of scope. Use disclosed segment-launch authority with explicit restriction/isolation stops.

## Goal and handoff composition

**Decision**: No automatic Goal creation/restart and no inner native Goal. The selected adapter invocation owns its full bounded endpoint, including actual local result, coordination acceptance/uncertainty and release, as applicable. Existing Farmboy skills run ordinarily within it, with their original human gates; their segment return never permits an early native completion of a wider objective. If an active native Goal's whole objective is incompatible with the selected endpoint, preserve/report the mismatch rather than fake success. Once the complete matching endpoint is saved/read back, only supported native completion/readback may end it before human waiting.

**Rationale**: One run per selected segment and one human boundary at a time fits current skills and keeps successful automation distinct from feature outcome. Ordinary clarification is separately selected outside the completed preparation Goal. While genuine clarification questions are active, authority is retained between questions; at saved human-review handoff it is released. No live preparation Goal awaits answers. Exact current Diagram handoff operations normally release atomically; explicit run release covers an incomplete/failed reporting path, never a fabricated accepted handoff.

**Alternatives**: Nested Goals create competing completion authority. Keeping preparation alive for answers violates001. A new controller/state machine or retry counter hides authority and needs unsupported persistence. Recommend existing artifact/operation inspection and ordinary separate continuation; the adapter does not override any core command.

## Verification and acceptance

**Decision**: Add `tests/fixtures/diagram-adapter/cases.md` and use actual separate executing/evaluating native sessions with disposable real Git repositories and explicit disposable Diagram coordination state. No new harness/framework. Existing core skill fixtures are regression inputs, not acceptance evidence for005. Record observations in005 `validation/acceptance.md` and existing delivery notes only when actually run. Use the mandated skill-tools Python for scripts belonging to/validating skills; missing runtime/packages are reported before any environment change. Runtime application/json serialization may use existing appropriate tools without adding dependencies.

**Rationale**: Static prompt checks and consistent false reports cannot prove correct physical verification. One complete modest feature plus focused authority/input/replay/isolation cases is proportionate. Real ordinary clarification and explicit TEST ONLY human decisions must be observed, never preloaded as genuine project approvals. All three standalone entries regress without Diagram. Exact final005 delivery commit is independently inspected only after it exists, with the observation reported in the review conversation/external evaluator record; no recursive receipt commit is needed.

**Alternatives**: Simulations-only are cheaper but fail constitutional acceptance. A generalized agent-test platform or production integration trial exceeds scope. Recommend manual independent native observation with targeted disposable tests, automation only where an existing supported test-driver is available and separately authorized.
