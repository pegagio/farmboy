# Implement Requested Scope Contract

This prospective contract covers Story 7/FR-039–FR-048 and SC-017–SC-022. It separates trusted requested task scope, current execution eligibility and immutable correction proof in the existing Implement controller. It changes no approved lifecycle policy, consequential gate, native role, task ownership or five-pass limit. Current source observation and design decisions are in the [plan](../plan.md#requested-scope-and-eligibility-design).

## Authority and Request Snapshot

The main controller binds the actual operator request and validated active feature before delegating initial assessment. `request_kind: full-feature` includes all current unfinished task identities, including tasks waiting on dependencies, decisions or owner source access. `explicit-subset` includes exactly the supplied validated IDs; dependencies outside that subset do not silently become executable scope. Completed prerequisite records are referenced as evidence. Validate unique/current IDs, safe feature/task paths and unchanged input digests; resolve material ambiguity through the focused main-task decision before effect. A JSON role, request string, reviewer recommendation or eligible list does not establish trusted authority.

The immutable `RequestedTaskScope` from the [data model](../data-model.md#requested-scope-and-execution-history) includes exact task marker/descriptions, pointer/spec/task digests, actual request provenance, requested IDs and a canonical digest independently retained by the controller. Retain it even when every initial eligible task is done. Original request and original defect baseline are separate immutable records; successors never rewrite them. Do not repair a historical stopped run by retroactively enlarging its captured baseline. A separately requested current run may record the actual current request/history without claiming prior authorization or correction evidence.

## Eligibility and Execution Gate

A current assessment covers every scoped task exactly once as eligible, pending, blocked or completed-with-proof, with required dependency identities, actual decisions, owner route and evidence. `eligible_task_ids` must be a subset of requested unfinished tasks or validated in-scope defect derivatives. Record exact per-task blocker, global blocker and safe resume action separately. External ownership alone is neither scope exclusion nor permission.

Declare request establishment before initial Reviewer, full-scope baseline capture before correction, fresh eligibility after assessment/actual same-child answer/independent post-pass review and Tasker update, and a gate immediately before every Coder. Common checks are current readiness helper/Checker agreement, target/spec/task descriptions, source route and access, trusted authority, exact native assignment, current history and remaining budget. Missing global proof prevents coding; individually blocked work does not stop unrelated eligible work that meets all common guards. First `in-progress` write/verification remains before source coding when lifecycle delivery is available, as required by the unchanged approved contract.

State-specific routes use the declared integration below. First-source-execution is possible only while the independently retained history has **zero source attempts**, all common guards pass, and an eligible scoped source task exists. Administrative prerequisite fulfillment earns zero implementation-progress credit. Corrective re-entry after any source attempt additionally requires independently substantiated implementation progress against the actual prior task/defect assessment; a failed or question-stopped source attempt is still an attempt. Each modeled Coder session counts toward five, including administrative and question-stopped sessions; reassessment/input/eligibility never resets that count. An actual answer returns to that same child and pending node without a new session, then revalidates before effect. Assessments do not spend a Coder session or create an autonomous repeat-work loop.

Completion requires all required requested tasks/effects substantiated and no associated unresolved buildable finding. Exhaustion of initial eligible tasks with pending scoped work is blocked with actual reasons, never complete. No eligible work because of a missing common guard has that guard's exact reason. A scoped subset can complete while other feature tasks remain outside scope; report that boundary without calling the feature complete.

## Declared Routing and Budget Integration

The current generic `route_loop_assessment` requires a continuing post-pass assessment to resolve an ID in the prior `remaining_ids`; it has no administrative-preparation mode. Do not label an administrative completion as code resolution, manufacture a finding, replace the baseline with an empty object, pass iteration zero again, or use `assessment_only_first_pass` to evade that predicate. Implement a **new scoped adapter** `implementation-route` backed by `route_scoped_implementation_assessment` in the small scope module and a thin controller entry point. Add a reviewed Implement-only loop dispatch mode `implementation_scope` whose mandatory request/history/eligibility inputs select this adapter. Other workflows and existing generic callers retain the existing function, strict envelopes and predicates unchanged; unsupported controller/graph versions fail before dispatch. This is a prospective API/graph change owned by T069–T071, not an available shortcut in the current installation.

The exact YAML carrier is `controller_loop_mode: implementation_scope` on the existing `id: implementation-loop`, `type: do-while`, `max_iterations: 5` node, with the supported condition `{{ steps.route-scoped-execution.output.state == "continue" }}` and final nondelegated `type: prompt` node `route-scoped-execution` invoking `implementation-route` on JSON stdin. Keep existing supported prompt/switch/command shapes; do not misuse native-delegation `flow_kit` metadata. Specify `WorkflowDefinition` retains raw node mappings, and its current validator accepts this additive carrier. An author load-only check under tested Specify `1.0.10.dev0+pegagio.2` verified model construction, legacy-installed `WorkflowEngine.load_workflow`, and FlowKit `load_installed_definition` serialization preserve it; this is carrier evidence only, not delivered execution support. No Spec Kit core change is required or proposed. The FlowKit controller graph preflight must newly validate that the carrier is present only on this exact workflow/loop, equals its sole supported value, has cap five and the declared preparation/source/assessment nodes/order, and has neither generic first-assessment exemption flag. Reject unknown values, other workflow placement, missing adapter/version, loader loss or stale ownership digests before run effects. Default/absent carrier uses the unchanged generic protocol. Amend the shared controller protocol explicitly to select this adapter only for the validated carrier; arbitrary prompt text cannot disable generic routing.

Initial scope assessment and the first `route-scoped-execution` evaluation occur before the loop's first Coder body. Each entered body consumes exactly one new modeled Coder session in the selected branch; it ends with independent kind-specific assessment/tracking, fresh eligibility/readiness and the final scoped route. A same-child question suspends that entered body and does not enter another iteration. The outer loop iteration equals consumed Coder sessions; source-attempt ordinal is separately retained for the generic post-source comparison. Thus the ordinary five-body bound and the global session budget agree; no assessment-only loop pass is introduced. The initial and final route nodes must use unique declared IDs if both are materialized as prompts; the initial prompt is `route-scoped-entry`, and only the final in-body `route-scoped-execution` appears in the loop condition. Both call the same scoped adapter against actual history.

The rendered Implement graph declares the following order inside its single bounded `implementation-loop`; the main controller records actual history and invokes the scope adapter at `route-scoped-execution` rather than unconditionally calling the generic route-loop predicate before source work:

| Declared node / boundary | Required action and next boundary |
|---|---|
| `establish-requested-scope` → initial Reviewer → `capture-implementation-baseline` | Freeze the full actual request and all unfinished scoped task IDs/known defect before evidence before entering the loop; retain independently held digests |
| `reassess-scoped-eligibility` → current Checker/helper → `gate-scoped-execution` → `route-scoped-execution` | Revalidate common readiness, source/owner route for proposed effects, authority, exact assignment, task identity, immutable history and remaining global budget before choosing any Coder branch |
| `prepare-scoped-prerequisites` | Exact Coder may perform only scoped administrative requirements using permitted effect routes, or return a real question to the main controller; no source correction is permitted. Record the session start and consumed slot before dispatch. An unanswered question suspends this same node/child, with no automatic repeat. All actual answers remain evidence bound to the trusted main-task interaction |
| `assess-scoped-prerequisite-fulfillment` → ordinary exact Tasker tracking → `reassess-scoped-eligibility` | Exact independent Code Reviewer validates per-task administrative proof and absence of source effects. A further preparation session needs independently observed newly fulfilled prerequisite or a real answer that changes eligible preparation work; unchanged output/marker alone stops `preparation-no-progress`. No source-progress `resolved_ids` are generated. The same global budget applies |
| `capture-scoped-activation` → `record-scoped-source-attempt` → `implement-tasks` | For first or later source execution, freeze current task preimages after all guards, record both the new Coder session slot and source-attempt start **before dispatch**, then exact Coder executes core Implement on the validated scoped batch. An administrative/source mixed batch is a source attempt. Dispatch failure, question or no effect does not refund either counter or erase the attempt |
| independent code review → scoped progress validation → exact Tasker correction/tracking → readiness revalidation → eligibility reassessment → `route-scoped-execution` | Persist actual source-attempt result, substantive assessment and successor history; decide complete/blocked/corrective continuation using the generic predicate below. Reassessment cannot erase unresolved findings or reset an attempt to preparation |

At the initial route, and following administrative fulfillment only while `source_attempts_started == 0`, the scoped adapter validates the whole history, current scope accounting and available session budget. It returns an existing strict `continue` envelope to exactly one declared preparation or first-source node by ordinary `route_assessment` membership validation; **no generic source correction predicate is called at this pre-source boundary**. Preparation is not an unrestricted skip: missing actual authority, prerequisite proof, answered input, common guard or budget blocks, and repeated preparation with no newly substantiated prerequisite/input stops. The first source attempt uses the existing immutable original baseline plus a current source-progress projection that retains all unresolved findings and unfinished substantive task IDs. Administrative completion proof removes only independently fulfilled administrative tasks from requested-work accounting, never rewrites the original baseline or supplies a resolved implementation ID.

After any source-attempt start, including a failed dispatch, every proposed further source continuation calls the unchanged generic `route_loop_assessment` with `iteration = source_attempts_started`, `max_iterations = 5`, the actual current substantive assessment, and `previous_assessment` equal to the independently retained assessment immediately before that attempted source batch. Do not use either first-assessment exemption flag. Carry that genuine substantive assessment forward for later comparisons; administrative updates do not replace it. Thus continuation requires `prior.remaining_ids ∩ current.resolved_ids` to be nonempty, in addition to scoped task-to-substantive-proof validation. New findings, administrative IDs and newly eligible task identities cannot supply that intersection. Complete still requires all requested accounting fulfilled and no unresolved buildable findings; a source attempt without resolution and remaining work blocks `no-progress` even if another task is now eligible.

`coder_sessions_started` is the authoritative global budget across both branches, never a per-branch counter. It increases monotonically before each new modeled Coder session and is capped at five; a resumed same-child answer does not create another session. Before any continuing Coder dispatch, reject `coder_sessions_started >= 5` as `loop-cap-exhausted`, even when the generic source-attempt ordinal is less than five. A fifth session may still produce valid terminal completion; it cannot continue into a sixth. Preserve exact remaining work/partial effects and both counters in the terminal receipt. Prep repetition, eligibility refresh, failed dispatch, renamed finding and source-attempt reclassification cannot refund/reset/rewind history. History/dispatch facts are independently observed by the main controller; a child's labels, asserted role or JSON counter cannot establish them.

## Before Evidence and Progress

Freeze known unresolved defects before substantive correction with stable IDs, task owners, exact requirement/deficiency/correction and actual source preimages/digests. Capture all initially unfinished requested IDs even if blocked. The existing version 1.0 capture helper already accepts such IDs; retaining them is initially an orchestration change. New schema/history/task-specific proof checks require actual source implementation.

Before a newly eligible task's first source effect, capture `TaskActivationEvidence`: scope/eligibility/predecessor baseline digests, task requirements, current source before bytes or explicit absent-source state, current route/readiness references and iteration. The source map belongs to that activation record, not a retroactively amended defect record. For owner repositories, record logical component/repository-relative paths and source coordinates. Reject stale activation, substituted task, changed descriptions, unsafe paths, unobserved bytes and missing source coverage. A previously existing path uses its observed SHA-256; an absent planned file uses `{state: absent}` and no guessed digest.

Independent Code Reviewer supplies one result per prior finding with stable identity/task mapping and fresh proof of the actual recorded deficiency. A new finding is recorded separately and remains unresolved for its discovery pass; its source before evidence becomes a later correction boundary without changing earlier history. `completed-with-proof` means that the task's exact requirements are independently fulfilled using one of two exclusive `completion_kind` values, classified against the reviewed task description before execution:

| Completion kind | Required independent per-task proof | Accounting and progress |
|---|---|---|
| `administrative-prerequisite` | Task identity/description and requirement-by-requirement fulfillment; actual trusted operator request/answer where a decision is required; permitted effect route and actual before/after administrative state/digests or observed no-op; independent reviewer execution attribution and proof that source correction did not occur. For T050, substantiate the approved roadmap scope reconciliation and actual effect; for T051, substantiate the actual exact-contract approval and recorded receipt. JSON role metadata or a child-reported approval is insufficient | Discharge this requested task and dependency/subset accounting, eligible for exact Tasker tracking, but absent from implementation `resolved_ids` and `implementation_completed_task_ids`; `substantive_progress` remains false |
| `substantive-implementation` | Task identity/description, all requirements, frozen task activation/source preimages, actual attributable source delta/effects, relevant validation results and independent actual Code Reviewer assessment. A task with any required source correction uses this kind; it cannot be administratively reclassified to avoid coding/review | Discharge requested task and provide `task:<id>` resolution only when it was actually prior remaining substantive work and all proof validates; known defect resolution follows the existing stable prior-finding rule |

A decision/report that is itself the exact requirement of an administrative task can prove that administrative fulfillment; it never proves source implementation. A marker, arbitrary evidence path, byte churn, command success alone or renamed/omitted finding proves neither kind. Record unsupported or partial proof as pending/blocked, not completed. Ordinary tracking alone provides no additional completion or code credit.

Preserve each original and successor JSON/digest, known-defect before evidence, fresh task-activation preimages, reviews, partial effects and monotonic iteration count in existing run evidence. Validate append-only predecessor relationships, exact prior finding coverage, new ID uniqueness and proof-task mapping. New unresolved defects survive even when a prior one resolved. Retain the strict outcome envelope's namespaced `task:T052`/`finding:F020-R001` remaining/resolved IDs; no new scoring rule is added. No progress or final-pass continuation stops with truthful remaining work; discovering another eligible task does not override those stops.

Add `controllers/flow-kit/scripts/python/implementation_scope.py` and thin existing controller adapters; proposed commands below are implementation deliverables, not current available capabilities. All use JSON stdin/stdout, read-only validation and existing safe preflight; actual run evidence recording is done by the authorized controller. Extend existing progress operation additively for scoped callers rather than silently reinterpreting version 1.0. Pin the new graph to its supporting controller version.

| Planned operation | Required input | Ready result and validation |
|---|---|---|
| `implementation-scope` | validated feature, trusted-request attribution supplied by main context, `request_kind`, requested IDs, independently observed input digests | immutable scope object/digest; full-feature equality to current unfinished set; subset exact membership; origin independently established; no child-supplied authority |
| `implementation-eligibility` | original scope/digest, validated derivative history if any, current independent eligibility assessment, input digests, iteration/actual correction state | exact full requested accounting, current subset/pending/global blockers; validates membership/dependencies/evidence and prevents false scope exhaustion; no source effects |

| additive `implementation-progress` scope mode | frozen scope/history, prior baseline/digest, activation record, actual independent Code Reviewer result and task-specific evidence | exact completed/resolved/new/unresolved sets and append-only successor; administrative changes zero progress; frozen earlier bytes remain untouched |

## External Owner and Partial Effects

Before T052 source execution, inspect actual checkout/repository identity/revision/dirty-index state, owner AGENTS/guidance, access, permitted source-work route, actual task authority and safe effects. Record each observed requirement and decision with its component/source coordinates. Missing installed phase capability is T052's intended output, not a prerequisite to otherwise permitted source work. Installed runtime milestone consumers remain blocked until compatible reviewed delivery. This design neither claims that an owner checkout is now available nor authorizes arbitrary cross-repository edits.

Missing source/access/source-work route, conflicting guidance, an unresolved real permission requirement or unsafe proposed effect yields the actual owner-source blocker and safe action, without fallback, assumed exclusion, installed-copy edit or blanket authorization. Continue other eligible scoped tasks only if the gap is individual and common guards remain valid. Preserve successful source/task/evidence effects separately from later failed steps, uncertainty or blocked tasks; no automatic rollback and no overall completion from partial success. Any retry must revalidate current identity/rules/history, not recapture an old before record.

## Task Updates and Completion

Exact FlowKit-Tasker owns ordinary evidence-supported markers and all defect task revisions. Ordinary tracking has no fabricated finding/revision route and supplies zero progress credit. Existing frozen Tasker correction mapping/semantic/diff validation remains mandatory for reopening/adding necessary approved defect tasks. Persist an append-only derivative tied to those validated findings and unchanged spec scope, not a mutation of original request. Genuine new product/request scope requires focused trusted operator approval before effect; generated tasks cannot grant it.

Every boundary receipt distinguishes original requested IDs/provenance, current eligible/pending IDs, actual completed effects, independently completed implementation IDs, administrative prerequisites, outside IDs, unresolved findings, actual decisions, iteration count and exact stop/next route. No hidden loss of blocked tasks or finding owners is permitted. For a completed administrative-only request the declared final reporting branch says **Scoped prerequisites fulfilled**, with zero implementation progress and explicit outside/pending feature work; it must not emit **Feature Implemented** or write an implemented milestone. A completed substantive subset reports its exact scoped boundary, not full feature implementation. Full-feature implementation reporting still requires independent proof of its complete substantive scope and all existing lifecycle/convergence rules. Scoped invocation completion is not automatically convergence, implemented, verified, Git integration, publication or acceptance.
