# Data Model: Feature Identity, Preparation and Availability

The model uses ordinary JSON payloads and existing files. It introduces no database, authentication service or consumer-agent ownership tracking. Contracts define boundary schemas and examples.

## Operator Authorization and Selection

Authorization is context established by the main controller from a direct operator instruction; serialized fields preserve attribution, not trust by themselves.

| Entity | Fields | Validation/relationship |
|---|---|---|
| OperatorAuthorization | `operation`, `request_reference`, `target_reference`, `scope_summary`, `governing_contract`, `decision_state` | Operation activate/amend; decision granted/unsettled; main controller must independently establish trusted origin. No report/child can grant authority |
| RoadmapInventory | `roadmap_path`, `roadmap_sha256`, `entries`, `menu_order` | Source-contained path/digest, distinct entry IDs and inspected prerequisite closure; menu order is presentation only |
| FeatureEntry | `entry_id`, `title`, `status`, `feature_directory`, `dependency_ids`, `existing_spec` | ID zero-padded canonical number; exactly one mapping owner; status from existing vocabulary; safe normalized repository-relative directory; optional spec digest/state |
| SelectionResult | `state`, `selected_entry_id`, `match_method`, `candidate_ids`, `reason_code` | selected/ambiguous/missing/blocked; selected has one owner; competing ID/menu interpretations retain both; no mutation |
| ActivationProposal | `selected_entry_id`, `feature_directory`, `proposed_patch`, `feature_json`, `source_evidence`, `required_decision` | Preserve unrelated JSON fields; compare current roadmap/pointer/spec state immediately before effect; patch limited to authorized target |
| ActivationResult | `feature_directory`, `previous_feature_directory`, `changed`, `evidence` | Existing pointer helper semantics plus verification; no directory/spec creation. Partial roadmap success is reported separately |

Transitions: unresolved intent → focused decision → validated target → authorized proposal → fresh revalidation → pointer applied/no-op → independent verified result. Any incompatible state yields blocked before unsafe effect. Activation leaves lifecycle unchanged unless a separately authorized, documented roadmap delta is part of the operation; selection alone never advances it. Defer is a human choice, not a fallback feature.

## Preparation Obligations

Current feature-local classification and source evidence define readiness; a prior ready summary alone cannot authorize work.

| Entity | Fields | Validation/relationship |
|---|---|---|
| PreparationManifest | `schema_version`, `feature_directory`, `criteria` | Optional `preparation.json`; supported version 1.0; same active feature; one classification per stable criterion locator; all relevant mixed/legacy items covered |
| Criterion | `id`, `source_path`, `source_item`, `source_sha256`, `category`, `owner`, `due_phase`, `status`, `expected_evidence`, `evidence`, `review_requirement` | Category preparation-quality/preparation-review/implementation-evidence/human-acceptance/unresolved; owner explicit or null; pending/satisfied/blocked; null owner or unresolved category blocks readiness |
| ReviewVerdict | `criterion_id`, `reviewer_role`, `result`, `evidence`, `reviewed_inputs` | Independent reviewer differs from author where required; current input digests; read-only verdict; recorder cannot invent positive outcome |
| EvidenceReference | `path`, `sha256`, `kind` | Repository-relative contained path and SHA-256; kind quality-check/independent-review/test-result/operator-decision; no absolute host path/raw transcript/secret |
| ReadinessResult | `schema_version`, `feature_directory`, `state`, `reason_code`, `blocking_ids`, `pending_future_ids`, `criteria`, `source_evidence`, `resume_action` | ready/blocked; ready has no blocking IDs; future entries remain pending; unsupported/missing/stale evidence blocks; same FlowKit policy/helper report and fresh Checker assessment used by FlowKit Analyze/Implement |

Preparation pending → satisfied requires owner-authorized current quality/review evidence; required independent review cannot be supplied by the author. A source/review input change invalidates stale evidence until fresh assessment. Implementation-evidence and human-acceptance pending states remain nonblocking for startup only when their classification/ownership/due phase are established; their success is not implied. Unsupported or mixed classification yields blocked, never automatic exclusion.

ReadinessFinding fields: `id`, `source_path`, `source_item`, `missing_evidence`, `owner`, `correction_kind`, `authority_state`, `due_phase`, `evidence`. IDs remain stable across assessments. Only gaps with declared owners and authorized safe in-scope corrections enter the loop; unresolved ownership or consequential decisions block. Authoritative artifact findings and Checker readiness findings remain separate until the controller combines them for routing.

ObligationRelocation fields: `criterion_id`, `source_path`, `destination_path`, `before_sha256`, `after_sha256`, `classification_evidence`, `authorization`, `status`. The destination is outside `checklists/` within the same feature; status remains pending, original identity/text and prior provenance are preserved. Metadata or relocation alone earns zero resolved-gap progress.

Checkbox semantics remain those of the source checklist. Recording metadata does not check markers. Marker mutation requires the authorized owner/recorder and matching current evidence; custom quality review and built-in author quality remain different lifecycles. Native role settings are not a new per-copy hash ledger.

## Availability Evidence

Each context and exact role has its own observed result.

| Entity | Fields | Validation/relationship |
|---|---|---|
| PreparedContext | `context_id`, `kind`, `preparation`, `source_revision`, `components`, `definition_provenance`, `client`, `startup_observations` | Kind prepared-checkout-future-chat/prepared-worktree-future-chat/new-worktree-first-chat; logical portable identity; preparation present/absent/unknown with evidence |
| NativeLaunchResult | `case_id`, `context_id`, `requested_agent_type`, `state`, `evidence`, `error_summary`, `resume_action`, `effective_settings` | Exact original role or additive FlowKit-Readiness Checker; success/failed/not-tested; child response or sanitized native error; effective settings observed or unavailable, never inferred from TOML |
| PropagationProposal | `source_context`, `missing_paths`, `proposed_config_patch`, `authorization`, `preservation_evidence` | Exists only after reproduced supported gap; current Git/`.worktreeinclude` mechanisms; explicit config authority before alteration |

Context preparation/file presence and interface/native launch availability are independent axes. First-chat failure → later-chat success is a new case, not a rewrite to passed. Definition provenance uses package/source manifests and consumer version-control/config observations; no consumer-copy ownership digest or automatic customization merge is created.

## Feedback and Validation Results

Historical observation is immutable; Feature 020 current reassessment is separate.

ObservationAssessment fields: `observation_id`, `historical_component`, `current_component`, `disposition`, `requirement_ids`, `test_case_ids`, `evidence`, `gap`. Disposition is reproduced/not-reproduced/not-tested; not-tested requires exact gap. All five IDs from the consolidated report must occur once. Historical capacity failure can remain unresolved while future availability cases succeed.

ValidationCase fields: `case_id`, `area`, `requirements`, `context_id`, `expected`, `observed`, `result`, `component_provenance`, `evidence`, `limitations`. Result is passed/failed/not-tested. Per-area and combined sequence results remain separate. Portable evidence records local test/native launch/effective-settings/acceptance as distinct claims, with no inferred publication or adoption.

## Phase Lifecycle Evidence

The lifecycle amendment adds versioned JSON records to existing run recovery and feature validation storage. [phase-lifecycle.md](contracts/phase-lifecycle.md) defines concrete payloads and owner boundaries. It adds no database or authoritative second roadmap.

| Entity | Required fields | Validation and relationship |
|---|---|---|
| PhaseScopeSnapshot | `schema_version`, `feature_directory`, `entry_id`, `phase`, `workflow_id`, `workflow_version`, `run_id`, `current_status`, `source_map`, `dependency_states`, `scope_sha256`, `pending_future_ids` | Version 1.0; contained relative paths; exact active pointer and unique entry; source map includes constitution/roadmap/config/extension/workflow/spec plus relevant plan/tasks/evidence; dependency closure valid; no missing source values |
| MilestoneEvidence | `milestone`, `owning_phase`, `assessments`, `required_check_ids`, `satisfied_check_ids`, `unresolved_ids`, `artifact_digests`, `historical_activity`, `pending_future_ids` | milestones specced/in-progress/implemented; every due prerequisite covered; unresolved required IDs block; actual independent run node/child provenance verified externally; historical_activity is dated proof, never a transition event |
| TrustedPhaseDecision | `request_reference`, `operation`, `target`, `scope_sha256`, `contract_reference`, `decision_reference` | operation phase-milestone/reconcile-milestones; main controller binds trusted instruction and approved installed governing contract; any standalone JSON decision is untrusted evidence; material scope/authority/recovery conflict requires explicit separate resolution |
| LifecycleProposal | `schema_version`, `snapshot`, `milestone_evidence`, `decision`, `from_status`, `to_status`, `expected_roadmap_sha256`, `patch_sha256`, `effect_id`, `recovery` | Exactly one adjacent transition, no arbitrary status jump; `effect_id` binds run/node/target/edge/preimage; bounded allowed recovery ceiling; draft patch changes selected status/provenance and normal ledger amendment metadata only |
| LifecycleAssessment | `state`, `reason_code`, `required_effects`, `evidence`, `blocking_ids`, `question`, `resume_action` | state ready/no-op/blocked/question; ready has one permitted effect; no-op preserves equal/advanced state only with current valid proof; blocker has exact safe resumption; question is structured main-task request, never substituted for missing proof |
| LifecycleReceipt | Common envelope: `schema_version`, `feature_directory`, `entry_id`, `phase`, `scope_sha256`, `evidence`, `effect_state`, `record_state`; state-specific fields below | Discriminated outcome, not a universal transition event; effect_state applied/no-op/not-applied/indeterminate; record_state recorded/failed/recovered subject to the authoritative state policy in [phase-lifecycle.md](contracts/phase-lifecycle.md#apply-and-receipt-semantics). Omit unsupported optional fields; null is never a substitute for evidence |
| PhaseRecoveryState | `run_id`, `effects`, `last_verified_roadmap_sha256`, `pending_effects`, `phase_actions`, `outcome`, `resume_action` | Monotonic truthful per-edge outcomes; no automatic rollback; retain earlier work vs write vs later failure; retries rebuild current snapshot, not approve old bytes; at most three missing edges |

Receipt field policy follows the contract: applied requires actual `effect_id`, `owning_phase`, `from_status`, `to_status`, `occurred_at` and observed `roadmap_before_sha256`/`roadmap_after_sha256`. A recovered applied record retains that original event identity/time and adds `recovery_evidence`; it never assigns retry time as occurrence. No-op is an explicitly event-free assessment record requiring `assessment_id`, `retained_status` and equal observed before/after digests; it forbids transition identity/status/time and proposal fields. Definitely not-applied requires a prepared proposal's `proposed_effect_id`, `owning_phase`, `proposed_from_status`, `proposed_to_status`, `reason_code` and known preimage; its final digest is optional only when actually observed. Indeterminate uses the same proposed identity fields and preimage, requires `reason_code`, forbids a verified final digest and event identity/status/time, and may include a separately identified `observed_roadmap_sha256` only when actual readback exists. Not-applied likewise forbids actual event identity/status/time. For both unapplied/uncertain states, proposed identity never asserts an actual effect. Every failed recording requires `record_error`; `recovered` is permitted only for substantiated applied effects. No optional digest/time may be guessed, copied from a candidate or supplied as null.

Relationships: one snapshot anchors one proposal; each established applied effect has exactly one transition receipt and its independent post-effect verification; no-op assessment and unapplied/uncertain attempt outcomes are not transition events. Recovery holds an ordered list of separately substantiated effects. Specification_ready differs from the Complete header, preparation readiness differs from implementation outcome, and implemented differs from verified/accepted. Every evidence reference uses repository-relative path, current SHA-256, kind and relevant reviewed-input digest map; operator/native trust is verified in actual controller context rather than through role strings.

Validation states: assessed → prepared → revalidated → applied → independently verified; a prepare gap yields a blocked/question assessment, while established nonapplication of a prepared effect yields a not-applied attempt outcome. Commit followed by record/report failure yields applied with recording/later-action failure, or indeterminate if actual bytes cannot be established. No later edge or coding/debrief proceeds until the prior edge is verified. A repeat against an already applied receipt rebuilds the current snapshot and yields no-op only when current milestone evidence remains sufficient; material changes invalidate earlier proposal/decision scope and require fresh assessment. Pending acceptance/release remains pending in every state.

## Requested Scope and Execution History

These additive records implement the [scope contract](contracts/implementation-scope.md). They use existing recovery JSON files; they are not a second task authority or roadmap. JSON request provenance is evidence only: the main controller must establish the actual trusted operator instruction and native assignments independently.

| Entity | Required fields | Validation/relationship |
|---|---|---|
| RequestedTaskScope | `schema_version`, `run_id`, `feature_directory`, `request_reference`, `request_kind`, `requested_task_ids`, `task_records`, `input_digests`, `scope_sha256` | Version 1.0 additive record; kind full-feature/explicit-subset; exact current IDs/marker/descriptions; full-feature covers all existing unfinished tasks including pending ones; immutable record; digest independently retained; no child list grants authority |
| ScopeDerivative | `original_scope_sha256`, `predecessor_sha256`, `reason_code`, `added_task_ids`, `task_revision_evidence`, `decision_evidence`, `sha256` | Append-only narrowly validated defect-task derivative or actual material operator decision; preserve original request/history; no retroactive authorization; Tasker mapping/specification/diff validation before derivative |
| TaskEligibilityAssessment | `assessment_id`, `scope_sha256`, `predecessor_sha256`, `input_digests`, `task_states`, `eligible_task_ids`, `pending_task_ids`, `global_blockers`, `iteration`, `evidence` | Every requested ID covered once; each state eligible/pending/blocked/completed-with-proof; completed state references validated TaskFulfillmentProof and its kind; dependency and decision references with exact blocker/resume; eligible excludes global blockers; full scope is unchanged |
| TaskFulfillmentProof | `task_id`, `task_description_sha256`, `completion_kind`, `requirements`, `proof_evidence`, `review_evidence`, `scope_sha256` plus kind-specific fields below | Administrative-prerequisite or substantive-implementation, classified against the actual task before execution; covers every requirement with independent actual review attribution; completion can discharge accounting without earning code progress |
| ScopedExecutionHistoryEntry | `event_id`, `predecessor_sha256`, `scope_sha256`, `declared_node_id`, `execution_kind`, `coder_session_id`, `coder_sessions_started`, `source_attempts_started`, `occurred_at`, `evidence`, `sha256` | Append-only independently observed session/attempt-start/result/input events; execution kind preparation/first-source-execution/corrective-source-execution; before-dispatch start persists even on failure; no refunded count, erased attempt or metadata-manufactured trust |
| OwnerSourceAssessment | `task_id`, `component_id`, `source_identity`, `source_coordinates`, `access_state`, `guidance_evidence`, `source_route`, `authority_evidence`, `state`, `reason_code`, `resume_action` | Actual observed checkout/access/rules/route; distinct source-work and installed-consumption requirements; unknown is not passed; no personal host path; owner-role string is not native dispatch proof |
| TaskActivationEvidence | `activation_id`, `task_id`, `scope_sha256`, `eligibility_sha256`, `predecessor_baseline_sha256`, `occurred_at`, `requirements`, `source_preimages`, `route_evidence`, `readiness_evidence`, `iteration` | Captured before that task's coding, exact current content/digests and safe contained paths; source coordinates for owner repo; no recapture of earlier defect before bytes; absent/never-created planned source gets explicit preimage absent state rather than invented hash |
| CorrectionHistoryEntry | `iteration`, `before_baseline_sha256`, `activation_sha256`, `review_evidence`, `resolved_ids`, `new_finding_ids`, `unresolved_ids`, `after_baseline_sha256`, `substantive_progress` | Immutable predecessor chain; complete prior finding coverage/owners; only prior genuinely resolved defect or substantive task closure earns credit; administrative fulfillment absent from resolved_ids; new findings remain unresolved; no administrative budget reset |
| ScopedExecutionReceipt | `scope_sha256`, `eligibility_sha256`, `completed_task_ids`, `administrative_prerequisite_ids`, `implementation_completed_task_ids`, `fulfillment_proof_digests`, `remaining_task_ids`, `out_of_scope_task_ids`, `finding_ids`, `actual_effects`, `decisions`, `iterations_used`, `coder_sessions_started`, `source_attempts_started`, `execution_history_sha256`, `substantive_progress`, `state`, `reason_code`, `evidence` | completed_task_ids is disjoint-kind union of validated administrative and substantive fulfillment; iterations_used equals coder_sessions_started, <=5 across all branches; full requested accounting retained; continue targets declared node, blocked requires resume_action, complete forbids routing fields; administrative/subset completion is not full feature implementation; partial effect/failure explicit; no rollback/acceptance |

Administrative TaskFulfillmentProof adds `trusted_decision_references`, `permitted_effect_route`, `administrative_state_before`, `administrative_state_after`, `no_source_effect_evidence`; require the exact real decision where applicable, observed administrative state/digests and independently checked fulfillment/no source mutation. Substantive proof instead adds `activation_sha256`, `source_delta_evidence`, `validation_evidence`; require original preimages, actual source effects and validation. A proof with any source requirement cannot use the administrative kind. References to trusted answers require actual main-controller attribution, never child assertions or native-role strings alone. Both kinds support requested accounting and Tasker tracking; only substantive proof or stable actual defect resolution can populate progress resolved IDs. If a preparation branch actually mutates source, preserve the observed violation and block; it cannot erase that effect or claim a clean pre-source history.

The original version 1.0 progress baseline remains frozen proof, not the requested-scope record. A current successor baseline is an unresolved-work projection linked to the original record and predecessor history. Administrative requested accounting and substantive comparison projection remain separate; dropping fulfilled administrative work from current accounting never rewrites original before proof or adds a source resolution. Newly activated scoped tasks retain their original task identity and receive fresh pre-execution evidence; known defect original preimages never change. Tasker alone writes task text or tracking markers; the independent Code Reviewer binds both per-task completion kinds, while authorized recorder/controller stores records without inventing verdicts. All schemas reject duplicate/unknown fields, unsupported versions, unsafe paths, missing identity/evidence, fabricated trust and undeclared route values; no optional value is supplied as guessed null/hash.

States: trusted request/baseline frozen → independent eligibility → current readiness/route/budget gate → declared bounded preparation or first source branch. Preparation records the Coder session before dispatch, waits for actual input in the same child/node when necessary, obtains independent administrative proof/tracking and reassesses eligibility without code credit. Source branch freezes activation → records session and source-attempt start before dispatch → source execution → independent substantive assessment → validated successor/history → full-scope reassessment. The new scoped adapter uses ordinary route membership only while source_attempts_started is zero; afterward it must call the unchanged generic prior-remaining/resolved predicate against the actual pre-attempt substantive assessment. Both branches consume one common five-session counter; question resumption reuses the same child/session. No-progress after a source attempt, preparation stagnation or cap cannot be evaded by answers/eligibility/administrative tracking. Exact ordering and API compatibility are in the [declared routing contract](contracts/implementation-scope.md#declared-routing-and-budget-integration). Global blockers stop affected execution; individual blockers allow other authorized tasks only under common guards. Completion requires all scoped required work and findings discharged with independent evidence of the correct kind; out-of-scope work remains untouched.
