**Input**: Iterate and improve the agentic workflows through one bounded feature covering explicit operator intent and feature selection, Analyze/Implement checklist readiness, and exact named-agent availability in future chats and Codex-managed worktrees. Include deterministic activation/status-transition rules. The approved Feature 020 roadmap entry defines the scope.

This specification defines prospective outcomes for three independently testable improvement areas. Historical feedback supplies evidence to reassess, not proof that current versions reproduce every issue. It does not authorize bypassing installed gates, amending governing contracts, implementing changes, or accepting the feature.

## User Scenarios & Testing

The journeys preserve operator control while removing prompts that merely repeat already-settled instructions. Each area can be assessed independently; combined use must preserve the same boundaries.

### User Story 1 - Carry Clear Intent into Feature Activation (Priority: P1)

An operator explicitly names and asks to activate an eligible feature. FlowKit validates the request, dependencies, mapping, and current state, activates that exact feature, and reports the result without another feature-choice, routine lifecycle, or pointer-only approval question.

**Why this priority**: Repeatedly asking an operator to restate a settled choice obscures the decisions that actually require attention.

**Independent Test**: Exercise explicit selection and activation against a roadmap containing multiple entries and different menu ordering. Compare first activation, repeat activation, existing specification, and conflicting-state outcomes. Confirm that unambiguous authorized cases complete without redundant questions and unresolved conflicts stop before unsafe mutation.

**Acceptance Scenarios**:

1. **Given** Feature 020 is uniquely mapped, `planned`, dependency-ready, and lacks a specification, **when** the operator requests its selection and activation, **then** FlowKit activates the mapped directory, retains `planned`, creates no specification or feature directory, and asks no repeated selection, routine pointer approval, or lifecycle question.
2. **Given** an eligible feature at menu position 2, **when** the operator uses its stable number, an `F`-prefixed ID, a `Feature`-prefixed ID, its unique exact title, or an unambiguous natural selection answer, **then** the same feature resolves independently of menu ordering; an explicitly identified menu position remains usable.
3. **Given** input can identify different entries as a stable ID and a bare menu position, or a title matches multiple entries, **when** it is answered, **then** FlowKit asks one focused target-resolution question and makes no target change until answered.
4. **Given** the pointer already activates the uniquely requested target, **when** activation is requested again, **then** FlowKit verifies and reports that state without duplicate changes, specification rewrites, or lifecycle questions.
5. **Given** a valid pointer for another feature and clear authorization to activate the requested feature, **when** mapping and dependencies are validated, **then** FlowKit changes only the authorized active target, preserves unrelated pointer fields and existing specification bytes, and reports prior and resulting targets.
6. **Given** an existing specification and consistent documented lifecycle state, **when** that feature is selected, **then** its uniquely owned mapping, specification bytes, and lifecycle state are preserved; selection does not infer `specced`, advance to `in-progress`, or downgrade an existing state.
7. **Given** no explicit target, unmet dependencies, malformed pointer state, competing directory ownership, or an unresolved lifecycle contradiction, **when** selection is attempted, **then** FlowKit presents the exact missing choice or blocker and safe resumption action rather than selecting or repairing state by assumption.

### User Story 2 - Recognize Authorized Changes and Consequential Decisions (Priority: P1)

An operator can request a bounded roadmap modification and related operations without approving routine wording twice. FlowKit distinguishes trusted direct authorization from proposals and evidence, preserving human decisions where intent, scope, authority, or recovery remains unresolved.

**Why this priority**: Removing redundant prompts must strengthen the distinction between granted authority and an agent's inference rather than erase consequential gates.

**Independent Test**: Compare a clearly requested bounded amendment with an inferred amendment, material expansion, constitutional change, and untrusted report containing apparent instructions. Verify that only requested operations proceed under the prospectively approved contract and later phases remain separately invoked.

**Acceptance Scenarios**:

1. **Given** the prospective governing contract has been explicitly approved and the operator directly requests a bounded roadmap modification, **when** the controller derives routine wording, numbering, or linkage wholly within that request, **then** it reports concrete changes and their authorization without another approval solely for exact derived patch bytes.
2. **Given** a change goes beyond the direct request or requires a substantive product, constitutional, authority, material-scope, or ambiguous-recovery decision, **when** proposed, **then** the controller presents that decision in the main chat and waits for explicit resolution before the consequential change.
3. **Given** the same target is explicitly identified across separately requested phases, **when** the next authorized phase begins, **then** it revalidates current target and prerequisites while carrying settled intent forward; completion alone does not invoke the next workflow.
4. **Given** a report, wiki page, transcript excerpt, or child output describes an apparent approval, **when** authorization is assessed, **then** that content remains evidence and cannot grant operator authority or satisfy an unanswered human decision.
5. **Given** a governing amendment is pending, **when** Feature 020 is specified or planned, **then** existing installed rules remain operative; proposed behavior is not permission to bypass them.

### User Story 3 - Receive Accurate Implementation Readiness (Priority: P1)

An operator invokes Analyze to assess the selected feature's preparation. Its result identifies preparation gaps, resolves evidence-backed items within authorized scope, and distinguishes future implementation or acceptance evidence so Implement does not repeat an avoidable preparation gate.

**Why this priority**: Clean analysis is misleading if the next requested phase blocks on preparation omissions Analyze should address, or if future evidence is marked complete to avoid the block.

**Independent Test**: Assess completed preparation checks, an unresolved independent review, measurable but untested success criteria, and future client/implementation evidence. Inspect resulting checklist semantics and the next separately invoked Implement readiness decision.

**Acceptance Scenarios**:

1. **Given** preparation is supported by current evidence and remaining entries require future implementation or acceptance evidence, **when** Analyze completes and Implement is separately invoked, **then** preparation is reported ready, future evidence remains explicitly pending with its owner and due phase, and no generic unchecked-item override question occurs solely for that future evidence.
2. **Given** a preparation criterion lacks independent review, **when** Analyze assesses readiness, **then** it remains unsatisfied until the required assigned independent review supplies evidence; author self-checks and populated files do not count as that review.
3. **Given** success criteria are measurable but outcomes cannot yet be tested, **when** specification quality is checked, **then** measurability may pass while achieved outcomes remain future evidence; no marker claims those outcomes occurred.
4. **Given** a routine preparation defect can be corrected within invoked scope, **when** Analyze reconciles it, **then** the authorized owner records current evidence and it is reassessed before a ready result; unsupported corrections and consequential decisions stop with actionable blockers.
5. **Given** evidence is stale, ownership is unclear, or preparation review remains unavailable, **when** Analyze or Implement assesses readiness, **then** the result names the criterion, missing evidence, responsible role or unresolved ownership, and resumption action; clean analysis or command success cannot substitute for readiness.
6. **Given** the Readiness Checker identifies a gap with an available correction owner and a safe repair within the invoked workflow scope, **when** Analyze and Remediate routes the finding, **then** it executes the declared owner correction and reruns fresh artifact analysis and readiness assessment until both are clean or a bounded stop applies. Recording a report, changing a timestamp, or moving a marker alone does not resolve the finding.
7. **Given** an obligation requires future implementation or acceptance evidence, **when** its authorized owner reconciles a mixed checklist, **then** the obligation remains pending with its stable identity, provenance and destination outside `checklists/`; only preparation-quality and review items remain in the core startup gate, and standalone core behavior is unchanged.
8. **Given** Analyze has reported ready but relevant artifacts change before separately requested Implement, **when** FlowKit Implement revalidates, **then** stale preparation blocks before core Implement rather than relying on the saved ready result or silently starting another workflow.

### User Story 4 - Use Installed Agents in Future Chats and Worktrees (Priority: P2)

A consumer installs FlowKit once and can use its skills and exact named agents in future chats in that prepared checkout and prepared Codex-managed worktrees. Reports distinguish absent payloads, preserved consumer configuration, native availability, and client startup limitations.

**Why this priority**: Reinstalling per chat treats discovery failures as installation failures and risks overwriting consumer configuration without establishing the cause.

**Independent Test**: Use documented one-time preparation and existing Git and `.worktreeinclude` propagation. Observe exact launches in an existing prepared checkout, a prepared worktree, and the first chat created with a new Codex-managed worktree. Separately inspect preservation and unavailable-payload/native-dispatch outcomes.

**Acceptance Scenarios**:

1. **Given** an initialized project completes one supported FlowKit installation and documented preparation, **when** a future chat starts in that checkout, **then** its workflow skills and all eight reviewed agent identities are available for exact native dispatch without installation per chat or agent.
2. **Given** tracked definitions and installed payload propagate using existing supported mechanisms, **when** a prepared worktree opens in a future chat, **then** inventory agrees with selected component provenance and all eight exact launches are demonstrated or specific native availability gaps reported.
3. **Given** a new Codex-managed worktree is created from a prepared project, **when** its first chat begins, **then** validation records whether payload was present at initialization and all eight exact launches succeed; a startup ordering failure remains an explicit client limitation with a supported next action, not missing-installation speculation or passed validation.
4. **Given** consumer files, custom instructions/settings, unrelated agents, or propagation configuration, **when** preparation or supported gap correction is proposed, **then** existing consumer-owned content is preserved and any needed configuration change is visible and explicitly authorized before mutation.
5. **Given** definitions exist but the client cannot request an exact native agent, **when** preflight runs, **then** it distinguishes file presence from interface availability, reports the affected assignment, and stops before workflow work without generic fallback, capacity changes, or per-chat reinstall.
6. **Given** a fresh chat succeeds after earlier startup failure, **when** results are recorded, **then** later success does not erase the first-chat failure, establish its root cause, or prove effective model/effort settings.

### User Story 5 - Use the Improvements Sequentially (Priority: P2)

An operator progresses through separately invoked workflows using one selected feature in a prepared environment, with clear readiness and authorization evidence at each boundary.

**Why this priority**: Individually passing improvements can still conflict when identity, checklist state, and native availability meet in ordinary use.

**Independent Test**: Demonstrate explicit selection/activation, specification and preparation, Analyze readiness, and separately requested Implement startup against one feature. Preserve a blocked variant with an unresolved consequential decision or unavailable exact agent.

**Acceptance Scenarios**:

1. **Given** the three areas pass independent checks, **when** successive phases are separately requested, **then** feature identity stays constant, settled authorization is reused, preparation readiness reaches Implement without a redundant override question, and named assignments are confirmed without implying acceptance.
2. **Given** an unresolved consequential decision or unavailable exact assignment arises, **when** its boundary is reached, **then** the workflow stops with attributable partial-state evidence and safe resumption; earlier success grants no further authority and erases no blocker.

3. **Given** independent implementation review identifies a safely repairable in-scope defect with no eligible correction task, **when** Implement continues within its declared bound, **then** FlowKit-Tasker revises the task plan, the controller verifies the revision, and coding resumes without a routine reopening approval; completed work and consequential human gates remain preserved.

### User Story 6 - Record Evidence-Supported Phase Milestones (Priority: P1)

An operator invokes the phase that owns a feature milestone and receives an accurate roadmap state reflecting the current evidence. Routine milestone recording completes without a second approval for derived wording once its governing contract and installed workflow authorize it. Missing proof blocks the transition, and substantive uncertainty receives a focused decision. A stale earlier record can be reconciled without repeating adequately evidenced coding or pretending that historical transitions occurred.

**Why this priority**: A feature can finish its implementation yet remain blocked at Close Out when earlier phases leave its roadmap state behind. Repair must make phase ownership and evidence explicit while preserving independent verification and acceptance decisions.

**Independent Test**: Exercise each separately invoked owning phase against current reviewed evidence, missing and stale proof, equal and advanced states, and stale `planned` records. Observe transition order, fresh prerequisite checks, operator questions, preserved history and partial failures. Compare a successful implementation milestone with a separately proposed and explicitly approved verification patch.

**Acceptance Scenarios**:

1. **Given** a uniquely linked `planned` target with an authored or amended specification, satisfied author quality checks, resolved required clarification and independently assigned review/roadmap-brief findings, valid current prerequisites and no unapproved consequential decision, **when** the operator invokes Specify under the delivered lifecycle contract, **then** Specify records `specced`, exposes the evidence and authority, and asks no second approval solely for routine patch wording; pending implementation and future outcome proof do not prevent that milestone.
2. **Given** only a present file, a Complete label, an author self-check or a successful authoring command, or missing, stale or unresolved required specification review, **when** Specify assesses `planned` to `specced`, **then** it retains the state and reports the specific missing prerequisite and safe resumption; no independent review or implementation result is inferred.
3. **Given** a `specced` target with current reviewed specification, plan and tasks, satisfied dependencies and preparation readiness, and an eligible authorized implementation scope, **when** Implement begins, **then** it records `in-progress` after revalidation and before substantive coding, without claiming completion or verification.
4. **Given** missing or stale preparation/review evidence, unmet dependencies, no eligible authorized scope or an unavailable exact assignment, **when** Implement preflight blocks, **then** neither coding nor advancement to `in-progress` occurs and the exact blocker and safe resumption remain visible.
5. **Given** an `in-progress` target whose current attributable convergence/completion evidence and independently assigned review substantiate the full selected scope, required implementation validation is satisfied and no buildable implementation defect remains, **when** Close Out reaches its implementation milestone, **then** it records `implemented` before proposing `verified`; separately owned future human acceptance or post-closeout release obligations remain explicitly pending.
6. **Given** checked tasks, a Complete label, command success or historical convergence tied to older artifact contents, but absent or stale current completion evidence or an unresolved buildable defect, **when** Close Out assesses the implementation milestone, **then** it retains the state, reports the exact evidence gap and does not propose verification on the unsupported result.
7. **Given** an owning phase is reinvoked at its consistently equal or more advanced lifecycle state, **when** current identity, linkage and evidence are revalidated, **then** it retains that state without a downgrade, duplicate milestone event, redundant routine approval or reset of verification provenance; selection alone still changes only identity.
8. **Given** a stale `planned` entry with current evidence sufficient for all missing milestones and a declared authorized reconciliation path in the invoked phase, **when** that path runs, **then** each required milestone is separately substantiated and recorded in permitted order, each effect uses the actual present date, truthful earlier evidence remains attributable, and no substantive coding is repeated solely to repair the ledger.
9. **Given** stale earlier state but insufficient evidence for a missing milestone, **when** reconciliation is assessed, **then** no milestone is skipped based on a later label or completed tasks, and the exact missing proof and resumption action are reported.
10. **Given** contradictory identity, mapping, evidence or transition authority, or ambiguity about recovery, **when** reconciliation is assessed, **then** it stops before the disputed effect and presents one focused operator resolution rather than inventing history or a status repair.
11. **Given** the installed workflow lacks the necessary stale-state reconciliation route, **when** an owning phase encounters that condition, **then** it reports a delivery blocker and the specific safe resumption requirement; it does not invoke another workflow or treat this specification as runtime authority.
12. **Given** a deferred or abandoned target, a requested lifecycle regression, or a material product, scope, constitutional or authority change, **when** an owning phase encounters it, **then** the consequential decision requires explicit operator resolution before the affected mutation; earlier phase intent and ordinary milestone authority do not satisfy it.
13. **Given** a permitted lifecycle write succeeds but a following phase action fails, or earlier phase work succeeds but the write fails, **when** the phase reports, **then** it records the actual effects and failure separately with resumable evidence, performs no automatic rollback and makes no overall completion claim; a retry revalidates current state and proof.
14. **Given** roadmap, pointer, dependencies, governing state or relevant evidence changes after assessment or proposal, **when** a lifecycle effect is about to occur, **then** revalidation prevents use of the obsolete decision and reassesses the current conditions or requests focused resolution if the change is consequential; an earlier proposal or approval cannot authorize materially different effects.
15. **Given** `implemented` has been substantiated and recorded, **when** Close Out proceeds to roadmap debrief, **then** the existing debrief prerequisites and explicit verification gate still control `verified`; deferral or return preserves `implemented`, and no command success or milestone implies Git integration, publication or feature/The Diagram acceptance.

### User Story 7 - Continue Newly Eligible Work Within the Requested Scope (Priority: P1)

An operator requests implementation of the selected feature or an explicit task subset. FlowKit retains that requested scope while distinguishing tasks ready to execute from tasks waiting on dependencies or decisions. As those prerequisites are satisfied, it continues safe, newly eligible work in the same invocation without asking the operator to authorize an already requested task again.

**Why this priority**: Treating the initial eligible subset as the entire authorization creates an avoidable stop after prerequisite work and obscures genuine blockers. Continuation must preserve evidence, review, authority and bounded execution rather than treating administrative changes as coding progress.

**Independent Test**: Compare a full-feature invocation with an explicit task subset. Begin with blocked dependencies, then supply independently substantiated prerequisite completion or an actual operator answer. Observe scope retention, eligibility reassessment and first or continued authorized execution. Compare unchanged defects, newly discovered defects, stale readiness, external-owner limitations, partial failure and the iteration cap; retain the before evidence and exact stop or continuation reason.

**Acceptance Scenarios**:

1. **Given** an operator invokes Implement for the full selected feature without narrowing its task scope, **when** the requested scope is established, **then** all existing unfinished tasks are included, including dependency-blocked tasks; their initial eligibility and blocker reasons are recorded separately, and the eligible subset does not replace the authorized scope.
2. **Given** the full-feature scope includes T050, T051 and initially blocked T052, **when** T050/T051 prerequisite completion and the actual policy decision are substantiated and T052's source owner, access, applicable rules, permitted source-work route and remaining prerequisites are validated, **then** the same invocation reassesses and proceeds to T052 with zero renewed routine authorization or fresh-workflow requirement solely because T050/T051 exhausted the initial eligible subset; approval or recording alone earns no code-progress credit, and the missing installed owner capability that T052 is tasked to build is not treated as its own unmet prerequisite.
3. **Given** the operator explicitly requests only T050 and T051, **when** those tasks finish and T052 becomes eligible, **then** T052 remains outside the invocation scope and does not execute without a new trusted scope decision; completion of the requested subset is reported accurately.
4. **Given** a desired task or effect exceeds the trusted request, **when** it is proposed, **then** the controller presents the focused material-scope or authority decision and waits before the disputed effect; a child recommendation or generated eligible-task list cannot supply that decision.
5. **Given** a known in-scope defect and a dependency-blocked scoped task before coding, **when** correction and later task activation occur, **then** the original scope and known-defect evidence remain attributable and unchanged, the newly eligible task retains its existing identity, and independent review can compare correction against the actual before evidence rather than a rewritten baseline.
6. **Given** independent review finds a new defect after correction while a prior defect is resolved, **when** progress is assessed, **then** only the previously recorded resolution can earn defect-progress credit, the new and unchanged findings remain visible with stable identities and owners, and the new defect cannot retrospectively appear in the before-correction evidence.
7. **Given** a scoped task is waiting for a consequential decision or evidentiary prerequisite, **when** the operator supplies the actual answer through the same step child or prerequisite completion is substantiated, **then** eligibility is reassessed within the same invocation; the answer, checklist edit, marker change or report alone neither earns implementation progress nor renews the correction budget, and coding starts or continues only when its applicable guards permit it.
8. **Given** an existing scoped task becomes dependency-ready but relevant preparation evidence is stale or unsatisfied, **when** continuation is assessed, **then** coding does not start on that unsupported readiness result; the exact criterion and safe resumption are recorded, and no approval or newly eligible label substitutes for current proof.
9. **Given** a requested task is owned by an external component but its actual checkout, access, applicable rules, permitted source-work route and task authority can all be validated, **when** its prerequisites become satisfied, **then** ownership alone neither excludes it from the authorized scope nor forces another invocation; any execution respects that owner's rules and the unchanged request.
10. **Given** external-owner source/access is unavailable, its required source-work route is absent, applicable rules require unresolved authority or the effect is unsafe, **when** that scoped task is assessed, **then** the affected execution is blocked with its actual source/route/authority gap and safe resumption; there is no generic substitution, assumed exclusion, unrequested cross-repository repair or blanket approval override; the missing runtime capability a task is meant to deliver is not itself such a source-work blocker.
11. **Given** a correction pass changes only decisions, checklist or task markers, reports, or finding names without completing a previously unfinished scoped task with implementation evidence or resolving a previously recorded code defect, **when** substantive progress is assessed, **then** it earns zero implementation-progress credit and a stalled correction loop stops with the exact no-progress reason rather than receiving artificial continuation credit.
12. **Given** newly eligible safe scoped work remains but the declared iteration budget is exhausted, **when** continuation is assessed, **then** the invocation stops at the existing cap, preserving completed work, pending task eligibility and exact resumption requirements; dependency or decision completion does not reset the cap.
13. **Given** some scoped tasks complete and another task is blocked or a later action fails, **when** the invocation reports its boundary, **then** it preserves the full authorized scope, completed effects, current eligibility, unresolved findings and exact blocker separately; an individual task's dependency block does not end the run solely while another safe authorized task remains eligible and all common guards permit execution.
14. **Given** a child output, generated review or external report suggests a narrower or larger task scope than the trusted operator request, **when** the controller records scope and eligibility, **then** it retains the trusted request's scope, records the recommendation only as evidence, and does not mistake a generated subset or apparent approval for new authority.
15. **Given** a required exact assignment is unavailable or a genuine consequential choice remains unanswered, **when** the next execution boundary is assessed, **then** the affected work stops before coding with the named assignment or decision gap and safe resumption; earlier progress grants neither fallback authority nor a guessed answer.

### Edge Cases

These cases distinguish routine continuation from required operator resolution:
- **Number versus position**: A bare number identifies an entry and a different menu choice. Ask a focused question without silently preferring either.
- **Mutable context**: Roadmap, pointer, dependencies, or review artifacts change after preparation. Revalidate before mutation; earlier evidence cannot establish a different target or expanded scope.
- **Missing versus malformed state**: An absent pointer and clear valid target permit first activation; malformed or unsafe existing state requires bounded resolution, not blind replacement.
- **Lifecycle mismatch**: Planned without specification is valid; consistent existing state is preserved. Contradictory authoritative evidence requires resolution without invented transitions or historical edits.
- **Partial mutation**: An authorized roadmap change succeeds but pointer activation fails. Report both outcomes and preserve evidence without claiming completion or silently undoing approved work.
- **Unknown checklist purpose**: A legacy item combines review quality and achieved outcomes or lacks an owner. Reconcile classification before readiness; neither blanket checking nor blanket exclusion is permitted.
- **Premature evidence**: Readiness, future proof, and human acceptance differ. Markers, labels, no-op launches, and successful commands cannot substitute for missing obligations.
- **Worktree differences**: Definitions are absent from the source snapshot, ignored payload does not propagate, versions differ, or consumer copies differ. Report actual state and authorized correction, not assumed equivalence.
- **Startup ordering**: First-chat native discovery fails despite files, or starts before preparation. Record observable ordering and distinguish causal hypothesis from supported client contract.
- **Historical capacity failure**: A recorded thread-limit error remains unresolved here. Preserve it without reviving capacity increases or child cleanup.
- **Milestone versus evidence**: An amended specification can become `specced` with implementation pending; a later status alone cannot substantiate an earlier missing milestone. Current proof must cover the exact selected scope.
- **Stale lifecycle recovery**: A `planned` entry with adequately substantiated earlier work needs an authorized ordered reconciliation path, truthful present effects and preserved historical evidence. Missing proof, ambiguous recovery or absent route remains a specific stop.
- **Milestone partial failure**: Preserve a successful lifecycle write when a subsequent action fails, and preserve earlier successful work when the write fails. Report both without automatic rollback, fabricated completion or blind retry.
- **Advanced or inactive state**: Retain consistent equal/advanced state and verification provenance; deferred/abandoned reactivation and regression remain explicit decisions rather than ordinary advancement.
- **Eligibility versus scope**: Initially blocked tasks remain in a full-feature request; a narrow requested subset remains narrow. Dependency completion changes eligibility, not authority.
- **Input versus coding progress**: A settled decision can remove an eligibility blocker or permit first execution; it cannot itself resolve a code defect, extend a stalled correction loop or reset the iteration cap.
- **External ownership**: A separate component's actual source, access, rules and compatible route must be inspected. Ownership alone proves neither exclusion from requested work nor permission for additional effects; a task's own missing deliverable is not its prerequisite.
- **Baseline integrity**: Newly eligible tasks and new findings require current evidence without rewriting the original scope or earlier defect-before record; retrospective credit remains prohibited.

## Requirements

Requirements define user-visible contracts and evidence boundaries without selecting an implementation design. Area labels maintain traceability within one feature.

### Functional Requirements

- **FR-001 — Evidence reassessment**: Maintainers MUST reassess all five consolidated observations against current applicable components, retaining historical IDs, component versions/digests, and separate dispositions of reproduced, not reproduced, or not tested with an exact gap. Original observations MUST NOT be overwritten or treated as current proof. [Feedback evidence](#feedback-traceability-and-evidence-boundaries)
- **FR-002 — Intent recognition**: Selection MUST distinguish a direct trusted selection/activation request from an interest filter, discussion, proposal, or untrusted evidence. Valid unambiguous activation authority MUST proceed through required checks without another selection or pointer-only approval prompt. [Approved Feature 020](../../.specify/memory/roadmap.md#020--flowkit-workflow-iteration-and-improvements--status-planned)
- **FR-003 — Feature references**: Selection MUST accept uniquely resolving stable numbers, `F`-prefixed IDs, `Feature`-prefixed IDs, exact titles, unambiguous natural answers, and explicit menu choices. Reordering MUST NOT change stable ID meaning. Competing valid interpretations MUST require focused resolution before mutation.
- **FR-004 — Target validation**: Activation MUST revalidate unique entry-to-directory ownership, safe repository-relative mapping, dependency readiness, current pointer validity, and lifecycle consistency. Missing or competing authority MUST produce an exact blocker and safe resumption without substituting a target.
- **FR-005 — Planned activation**: Activating a `planned` entry without an authored specification MUST retain `planned` and create neither directory nor specification. Activation alone MUST NOT infer `specced` or `in-progress` or require a routine lifecycle decision.
- **FR-006 — Existing target preservation**: Repeat activation MUST verify/report without duplicate changes. Existing specification bytes, unique mapping, and consistent lifecycle state MUST be preserved. Authorized target switches MUST preserve unrelated pointer fields; genuine state conflicts require resolution rather than silent repair.
- **FR-007 — Direct amendment authority**: Under a prospectively approved governing contract, a directly requested bounded roadmap modification MUST NOT require reconfirmation solely because routine wording, numbering, or linkage was derived within the request. Resulting changes and trusted authorization MUST remain inspectable. Unrequested or unsettled consequential changes MUST retain explicit human decisions.
- **FR-008 — Governing reconciliation**: Necessary changes to authority for FR-002–FR-007 MUST identify affected governing contracts, rationale, historical supersession, and migration for active work and receive explicit human approval before implementation relies on them. Reviewed source and guidance MUST agree with the approved contract; this specification MUST NOT amend constitution or installed rules. [Current authority](../../.specify/memory/constitution.md#ii-human-directed-authority), [earlier exact gates, S021/S022](../../wiki/pages/feature-start-contract.md)
- **FR-009 — Separate invocations and gates**: Settled intent MAY carry across separately operator-requested phases after same-target revalidation. Completion MUST NOT invoke another FlowKit workflow or imply roadmap verification, Git integration, publication, or feature/The Diagram acceptance. Constitutional, authority, material-scope, substantive product, and ambiguous-recovery decisions MUST remain explicit in the main chat, with same-child relay where needed. [Authority, S001/S017/S020/S021](../../wiki/pages/project-authority-and-review-gates.md)
- **FR-010 — Preparation classification**: FlowKit Analyze and FlowKit Implement MUST use the same FlowKit-owned readiness contract without requiring Spec Kit core modifications and MUST share compatible readiness meanings distinguishing preparation-quality/review obligations from future implementation evidence and human acceptance. Every unresolved criterion MUST identify category, responsible role or unresolved ownership, expected evidence, and due phase.
- **FR-011 — Honest marker ownership**: Only an authorized maintainer MAY change checklist markers, using current supporting evidence. Built-in specification quality MUST assess clarity/completeness/measurability, not achieved outcomes. Self-checks MUST NOT substitute for independent review.
