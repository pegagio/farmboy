# FarmBoy Controller Protocol

This protocol is shared by the ten active direct Codex skills. The installed workflow definition is the source of prompts, commands, branches, and gates. Never copy those decisions into a skill or invoke `specify workflow run`.

## Feature 015 Named-Agent Dispatch Procedure

This procedure applies to the named-agent workflow packages. Every delegated executable step declares `farmboy.delegated: true` and its exact reviewed `farmboy.agent` name. An executable step without that metadata stays in the main task; an agent name never creates delegation by itself. Codex loads the consumer-owned custom agent configuration. For timing metrics metadata only, FarmBoy may passively read the consumer project's `.codex/agents/*.toml` files and use explicit `model` and `model_reasoning_effort` values from the uniquely matching exact `name`; unavailable or ambiguous values are null. This read does not control dispatch, verify effective runtime settings, resolve inherited or global settings, copy configuration, or supply spawn overrides.

1. Collect every delegated step and exact agent name from the complete installed graph, including untaken branches. Reject missing or unreviewed names before workflow work. Do not infer delegation, choose a default, or accept a per-run agent, model, or effort override.
2. Before workflow work, launch one no-work probe for each distinct agent name through the Codex app's native custom-agent selection. Pass the exact reviewed name as the native spawn request's `agent_type`; a task name or prompt mention alone is insufficient. Give the probe a visible activity label containing that name, such as `FarmBoy Roadmap Agent readiness probe` (or `roadmap_agent_readiness_probe` when the client accepts identifier-style task names). Each probe returns a fixed readiness token and performs no workflow work, skill invocation, tool call, or file inspection. A successful exact-`agent_type` spawn and the expected probe token confirm that the named agent can launch; the tool reply need not repeat the selected name. The label gives the operator a launch cue but is not native-agent identity proof. If the client cannot request the exact native `agent_type`, the child fails, or its token is wrong, stop before creating workflow state and name the affected agent and every step ID assigned to it; never substitute a generic child or another assignment. Do not reuse a probe child for workflow work.
3. Ask Codex directly to spawn each bounded workflow child with native `agent_type` set to the exact `name` from its step. Give the child a visible activity label containing both the reviewed agent name and step ID, such as `FarmBoy Reviewer analyze-artifacts` (or `reviewer_analyze_artifacts` for identifier-style task names). Check the rendered child label before treating native UI visibility as verified. A child title, copied instructions, or matching model alone does not establish native selection; the exact `agent_type` request does. Current Codex clients document direct requests to spawn subagents and identify custom agents by their TOML `name` field: [Codex subagent documentation](https://learn.chatgpt.com/docs/agent-configuration/subagents).
4. Use the custom agent's native configuration for instructions, model, and effort. Do not pass duplicate settings as spawn overrides. Codex may show model and effort in the child pane; missing setting details do not block an otherwise valid native assignment. Preserve bounded children, same-child interactive continuation, parent-owned gates, recovery, and stop behavior below.

The desktop screenshots recorded in the Feature 015 validation show this native path selecting project agent `Coder`, loading its distinctive instructions, inheriting the parent settings when model and effort are absent, and displaying the configured `gpt-6-luna`/`high` values when present. The current CLI and generic child-spawn tool probes did not confirm named selection; those paths are not substitutes for a successful native `agent_type` request. If an app or client cannot request the exact native agent type, stop and report that dispatch surface as unavailable.

## Preflight

1. Confirm the selected task is in the consumer project and the requested skill ID maps to the requested workflow ID in the installed `manifest.yml` and `skills-install.json`. Stop if either record is absent, incompatible, or inconsistent.
2. Gather the required workflow values from the invocation or ask for missing values in the main task. Pass each value as `--input name=value` to `bash .specify/farmboy/scripts/bootstrap.sh "$PWD" <workflow-id> <skill-id>`. The bootstrap locates and version-checks the active Specify runtime, loads the composed installed workflow read-only, and returns its graph, resolved inputs, and digest. Never run it from the FarmBoy source checkout on behalf of another consumer.
3. Read the JSON graph and resolved inputs. The helper applies declared defaults, rejects missing or blank required values and unknown input keys, and never prints the supplied values in an error message.
4. Check the graph and every switch branch and `do-while` body. Step IDs must be unique across the complete graph, including every loop body. A loop may not contain another `do-while`; it must declare one complete supported condition and a positive integer `max_iterations`. The condition is a single `steps.<assessment>.output.state == 'continue'` expression, and the referenced assessment must be in the loop body. Executable steps may delegate only with `farmboy: { delegated: true, agent: <reviewed-name> }`. Gates and switches remain in the main task. Reject unknown node types, concrete step models or efforts, malformed delegation metadata, unsupported template forms, workflow-level defaults, and unsupported command integrations before starting a step. Resolve prior-step output values only when the referenced step has completed.
5. Use the exact agent name on each delegated step. There is no workflow default or run-time assignment override. Show the validated step ID and name from `agent_assignments`; do not claim a model or effort unless Codex exposes it.
6. If an exact native `agent_type` request or required probe fails, stop without a run record or workflow state change. Report the affected step ID or IDs, agent name, and observed failure; distinguish a native selection failure from a confirmed file parse or model error. Do not require the tool reply to echo the requested type. Never substitute another agent or reuse a probe child for workflow work.
7. If a named agent becomes unavailable at a later step, preserve completed-step evidence, mark the active step incomplete, and stop without substituting another agent or starting a later workflow phase.
8. Capture the starting workflow digest and content/device/inode fingerprints for `.specify/bundle-records.json` and `.specify/farmboy/skills-install.json`. Create the compact run summary only after preflight succeeds.

## Metrics Turn Boundaries

After validated workflow inspection and before any native probe, create one `metrics_run_id` UUID for that workflow invocation and retain it in the main-task context across all probes, working turns, continuations and retries, including same-context resumption. Keep it separate from recovery identity and do not pass it to recovery creation or use it to name recovery state. A failed preflight may leave probe metrics without a workflow summary.

For every native no-work probe and delegated agent turn, prepare the metrics context before timing starts. Use `step_id=preflight` and `invocation_kind=probe` for a readiness probe. For modeled agent turns use the exact workflow step ID and `invocation_kind=execution`; use `continuation` for a same-child resumed turn and `retry` for a separately dispatched repeated attempt. Use only the exact agent, skill and workflow names from the validated assignment. Select `project_label` from an existing known nonpersonal logical project identity in the validated invocation context; FarmBoy may use `farmboy`. If no safe known identity is available, use `unspecified`; do not infer it from a basename, home/account name, path or remote URL.

The metric metadata allowlist is `schema_version`, `invocation_id`, `run_id`, `step_id`, `invocation_kind`, `agent_name`, `skill_id`, `workflow_id`, `project_label`, `started_at`, `finished_at`, `duration_ms`, `model` and `effort`. Read only explicit `model` and `model_reasoning_effort` values from the uniquely matching project agent TOML file by exact `name`, before timing starts; map them to `model` and `effort`. Missing, unreadable, malformed or ambiguous settings produce null values and do not prevent dispatch or collection. Do not resolve inherited or global settings or claim these file-declared values were verified at runtime. Do not include prompts, transcripts, secrets, personal details, absolute host paths, tokens or monetary cost. Human-answer waiting is excluded from timing.

Call the shared collector's begin helper immediately before issuing the native spawn or same-child continuation. Keep the returned timing token in the main-task context while the request is pending, including acknowledgement waits and polls. Call the finish helper immediately after observing the turn's ending, including a returned question, failure, rejection or interruption. Finish a question-producing turn before waiting for the operator; after the answer is relayed, begin a new turn for the continuation. Do not reuse a token across turns or include it in a child prompt or result. If no ending is observed, do not fabricate a finish or completed record.

Metrics are best-effort and must not change workflow behavior. If metadata preparation, the clock, the metrics helper, or its command launch fails, emit a concise warning and continue with the original native assignment, dispatch result, error handling, routing, and human gates. If begin fails, dispatch normally without a timing token and do not later invent a record. After an observed turn ends, finish the clock read before attempting persistence; warn and continue if the finish command is unavailable or reports `clock-unavailable`, `metadata-invalid`, `helper-unavailable`, `destination-unavailable`, `publication-collision`, or `storage-failed`. Do not retry a failed publication, replace an existing record, forward helper tracebacks as agent results, or treat a metrics warning as a workflow failure. If the turn remains pending or its ending was not observed, do not call finish or create a record.

## Execute the Installed Graph

Process nodes in order. Keep the run's current node, outputs, completed node IDs, child task IDs, and starting fingerprints in the main task context and summary. Before every new node, re-read the installed definition and compare its digest and both install-record fingerprints. After a child returns, compare them again. If any value changed, let that active node finish, record the stop, and do not start another node. A changed skill package is a refresh even if workflow YAML stayed the same.

- **Prompt node**: Render only `{{ inputs.name }}` and `{{ steps.id.output.path }}` references from available inputs and prior outputs. Stop on an unresolved or unsupported expression. For a delegated prompt, ask Codex to start one child using the declared agent name and rendered prompt. Otherwise perform the prompt in the main task. Capture a concise result for later references. Preserve edits if the node fails.
- **Close Out recovery attestation dispatch**: For `attest-recovery-start`, dispatch the exact declared FarmBoy Reviewer child first and wait until the native run summary records its actual child ID, role, step, workflow and run. The main task then captures an immutable copy of that summary, creates the exact dispatch witness from the captured entry, and relays only that witness path and digest to the same child before it constructs or returns the attestation. The child must wait if this main-retained reference is absent; it may not choose, create, or replace one. The main task validates the returned child identity and persists the returned attestation unchanged. Later operational summary updates do not replace or invalidate the captured witness; a missing or changed dispatch binding blocks the lifecycle request.
- **Command node**: Render its integration and YAML argument string. Only `codex` is supported. Resolve a project-installed command skill using the pinned naming rule (replace dots with hyphens), then verify its `SKILL.md` name and available ownership provenance. A recorded core Codex digest remains authoritative and must match; if the file is absent from the core manifest, accept an extension owner only when one enabled Codex registration uniquely matches a validated extension manifest hash, version, declared command source, and exact skill `metadata.source`. Reject malformed, stale, disabled, ambiguous, or unsafe ownership. Extension registration establishes ownership and the controller records observed command-source and installed-skill digests; it does not prove equality with a rendered skill body. Preserve the legacy unrecorded path only when no ownership record is available. For a delegated command, ask Codex to start one bounded child using the declared agent name; give it the installed command skill ID and rendered arguments, and require its result. For a nondelegated command, invoke the skill in the main task. For Closeout `ingest-curated-context`, also give the child the completed `prepare-wiki-refresh.refresh_findings` checklist as bounded correction context; retain the exact single source token as the command arguments. This context identifies supported corrections and does not replace the installed skill or expand source authority. The child must not invoke a `farmboy-*` skill, bootstrap a workflow, create a FarmBoy run summary, own a workflow gate, or dispatch another child to re-run this command node. The main task alone owns those controller actions. Never call native workflow execution or substitute a global skill, copied prompt, or similarly named command.
- **Gate node**: Render the installed message and options from completed prior-step outputs. Options may be a static list or a one-item list containing one exact `steps.<id>.output.<field>` reference to a JSON array of distinct nonempty strings. Expand that single referenced array into the gate options; mixed static options and arrays are invalid. Preserve a whole-reference list as a list, never parse a prose representation or invent choices. Missing, invalid, duplicate, or empty options stop before any choice or mutation. Freeze the rendered choices for that gate and validate the human answer against that exact rendered list. Present the rendered `message` and `options` to the human in the main task, with numbered choices and a custom response only when the workflow allows it. Wait for the human's explicit choice. Pass the rendered gate node and raw answer as JSON on stdin to `python3 .specify/farmboy/scripts/python/controller.py gate`; use only its validated `choice` as the gate output. A missing or invalid choice stops at the gate.
- **Switch node**: Evaluate its installed expression from inputs and captured step outputs. Pass the switch node and resolved choice as JSON on stdin to `python3 .specify/farmboy/scripts/python/controller.py branch`; follow only its returned `steps`. Stop if the expression cannot be resolved. Never execute more than the selected branch.
- **Do-while node**: Use the installed node's body, supported condition, and `max_iterations`; do not launch Specify's native workflow runner. If the workflow declares an assessment before the loop, run and validate it with `controller.py assessment`. A `complete` result exits the loop without a corrective pass. A `needs-human` result routes to its declared main-task gate when one exists; without a gate, stop for operator direction using its stable resumption action. A `blocked` result stops with its stable resumption action. Only `continue` enters that loop body. A workflow may instead start with a loop when its first command safely checks for work and finishes without changes when none is needed, as `speckit.clarify` does. Run the body steps in declaration order, honoring only selected switch branches and preserving main-task gates. Create a fresh named-agent child for each delegated step on every pass; if that child asks a question, relay it to the same child before continuing. Unless the loop declares `assessment_before_correction: true`, the final body step must produce a fresh assessment. Validate that assessment and call `controller.py route-loop` with the current iteration, cap, loop-body IDs, gate IDs, and previous assessment when one exists. Continue only when the result permits progress. Without a preceding assessment, the first post-session assessment must cite at least one resolved gap before another pass may start; later passes must resolve a prior `remaining_id`. A loop explicitly declaring `assessment_only_first_pass: true` instead uses its first body pass solely to establish an analysis baseline: skip every mutating command on that pass, run the declared read-only analysis and assessment, and pass `--assessment-only-first-pass` to `route-loop`. This permits continuation without resolved IDs only at iteration 1 with no previous assessment. Record and supply that baseline as the previous assessment on every later pass; those passes retain normal progress checks. The initial baseline counts toward `max_iterations`, so Analyze and Remediate uses six total passes for one baseline and at most five correction passes. End the loop for `needs-human`, `blocked`, no progress, repeated unresolved findings, invalid or stale evidence, or cap exhaustion; run only the declared outcome-reporting step or gate after that point, never another corrective command. A loop never turns a command's successful exit into a completed assessment.

A loop declaring `assessment_before_correction: true` instead has exactly three top-level body steps: the source command, its fresh assessment, and a switch over that assessment's state. Only the `continue` branch contains corrections; `complete` and `blocked` branches are empty. The compatible legacy form may also include an empty `needs-human` branch. After the assessment, validate its outcome and call `route-loop --assessment-before-correction` with the current one-based iteration, cap, and previous assessment before executing that switch. The first assessment establishes the baseline without requiring resolved IDs; later assessments must resolve a prior finding. A bounded stop overrides the raw continue state: exit to the declared outcome report without executing corrections. Save each validated assessment for the next comparison. Converge runs its append-only core command at the start of every pass, then performs the shared waterfall, task analysis, eligibility check, and implementation only when permitted. Its six assessments permit five correction passes plus a final confirmation; a clean sixth assessment completes, while a sixth continue blocks before another correction. Stop immediately on any intermediate needs-human or blocked eligibility outcome, failed command, or unresolved blocker or required question in an implementation report; run the outcome report instead of another convergence command. When implementation finishes without such a stop, return to the loop's source command for the next fresh assessment. This mode cannot be combined with `assessment_only_first_pass`.

The supported readiness-gated condition is limited to `{{ steps.<assessment>.output.state == 'continue' && steps.<gate>.output.readiness_gate.state == 'ready' }}` on an `assessment_before_correction` loop. Resolve both referenced step IDs in the validated graph and require the readiness gate to be inside the assessment's `continue` branch. The controller evaluates the ordinary assessment first; a non-continue result exits without requiring gate output. A continue result re-enters only when the gate is explicitly `ready`; missing, blocked, or stale readiness fails closed. This is not a general expression language. Implement places a fresh readiness check at startup and at the end of every continue route, after any Tasker revise/skip decision; a blocked re-entry gate takes precedence over the prior Code Reviewer continue verdict.

For Analyze and Remediate readiness, the deterministic FarmBoy helper and the exact read-only FarmBoy Readiness Checker supplement fresh `speckit.analyze`; neither replaces the substantive independent FarmBoy Reviewer. The controller routes repairable findings to the smallest authorized owner and repeats fresh analysis plus Checker assessment after correction. Only substantive resolution of a stable finding is progress. Main-task recording may persist only the exact current independent Reviewer verdict, apply its authorized custom-quality marker decisions, and move clearly future obligations into a pending feature-local ledger. Preserve those obligations outside checklist inputs. Implement reuses the exact helper and Checker before the unchanged Spec Kit core checklist gate and again before Coder re-entry. A task status marker-only change can retain readiness evidence when task IDs, text, order, line locations, and every non-marker byte are unchanged; changed wording, specification, plan, checklist, or independent evidence makes the prior review stale and routes to Analyze. The Checker is Luna/Medium read-only validation; its definition or assignment alone does not prove current native availability.

Implement task-plan repair remains inside that existing loop contract. After the independent Code Reviewer returns `continue`, the outcome switch may route to a second switch on the separate string enum `task_revision_action`: `skip` proceeds to the next bounded Coder pass using an already-open eligible task; `revise` first invokes the installed `task-revision-preflight` helper. That helper verifies the active pointer, lexical feature/task/spec paths, symlink-free parents, and physical selected-feature containment before reading task bytes; it freezes the task and selected specification text/digests. A blocked result stops before Tasker. After the main task freezes exact findings/corrections, eligible task IDs and owners, and exact `FarmBoy Tasker` append authority, an adjacent second preflight rechecks active identity and both digests immediately before invoking only that declared assignment through core `speckit.tasks`. The main controller then independently compares the actual task diff with that selected feature's frozen approved specification scope. Validate exact finding/task mappings, owner assignments, affirmative semantic review bound to the pre-Tasker scope digest, task history, and lexical and physical selected-feature containment before the next pass. The reusable command runs from the installed consumer package at `.specify/farmboy/scripts/python/controller.py`; source checkout paths are not valid consumer commands. Reopen/add needs no routine approval within the selected feature scope. Stale evidence, unsafe or out-of-scope edits, unavailable exact assignment, and invalid revision stop without fallback. Task edits earn no progress and resolve no findings; preserve the prior independent assessment for progress comparison and require fresh independent Code Reviewer evidence on the following pass. Complete and blocked outcomes skip Tasker entirely.

For example, a completed roadmap inventory may return `{"report": "026 is dependency-ready; 029 depends on 028, which depends on 026.", "selection_options": ["026 — Foundation", "030 — Independent feature", "defer"]}`. The selection gate declares `options: ["{{ steps.list-roadmap-options.output.selection_options }}"]`; rendering produces that exact string array. Numbered answers select positions in the frozen menu, while full identifiers select exact entries. Empty, duplicate, non-string, unresolved, and malformed option lists fail validation. An inventory with no safe candidates returns `["defer"]`, so no feature work can be selected. An unambiguous operator answer in an invoked Select Feature operation selects its target and authorizes routine activation after target, dependency, and governing-state revalidation. It does not authorize an inferred or unrequested roadmap modification. A direct trusted operator instruction may authorize a bounded roadmap modification or activation; routine derived patch wording does not require a second approval solely for exact bytes. Independently owned component behavior remains subject to its reviewed source and delivery authority.

The assessment envelope has exactly these fields where applicable: `state` (`complete`, `continue`, `needs-human`, or `blocked`), a stable `reason_code`, existing project-relative evidence paths with observed SHA-256 digests, `remaining_ids`, `resolved_ids`, and state-dependent routing fields. `complete` has no unresolved in-scope work and must omit `next_step_id`, `gate_step_id`, and `resume_action`. `continue` includes only an in-body `next_step_id` and names unresolved work. `blocked` includes only a stable `resume_action`. `needs-human` names a declared main-task gate when one exists; a workflow without a declared gate instead names a stable `resume_action` and stops for operator direction without taking the consequential action. Except for the explicitly declared initial baseline, each pass must resolve at least one prior finding or eligible task; changed bytes alone do not count as progress. The cap is checked after a fresh assessment, so a clean final allowed pass may complete; a final allowed pass that still requests continuation stops as `loop-cap-exhausted`.

Clarify, Plan, Tasks, Implement, Analyze and Remediate, Converge, and Closeout use `complete`, `continue`, and `blocked` assessments. Required operator input is a blocked reason with a stable `resume_action`; preserve the exact question and recovery action in the outcome report. The shared controller retains `needs-human` compatibility for declared human gates; current Closeout uses one explicit roadmap-patch approval gate and an automated commit-readiness report without stop-only defer/abort gates. This state simplification does not change question relay during an active command: the operator still answers through the same child.

When a child needs a human answer, it must return one structured request with `kind: question`, its `step_id`, question text, options, and whether a custom answer is allowed. Options may be short strings or objects with `id` and `description`; object descriptions are display text and answers resolve to their IDs. Pause that child; the current workflow node remains active through the answer relay. Validate the request by passing its JSON on stdin to `python3 .specify/farmboy/scripts/python/controller.py question --step-id <active-step-id>`; the helper normalizes `allow_custom`, `custom_allowed`, or `allow_custom_answer` to `allow_custom_answer` and rejects conflicting flags. Present the validated options in the main task as numbered choices plus a custom-answer option when allowed. After the human responds, pass `{"request": <validated-request>, "answer": <raw-human-answer>}` on stdin to `controller.py answer --child-id <original-child-id> --target-child-id <follow-up-target-id>`. Send only the validated answer as a follow-up to that same child task ID and wait for its continuation. Compare the starting fingerprints after continuation before any later node. Do not create a replacement child or answer on the human's behalf. If validation or continuation fails, stop and preserve its partial work. Do not put the raw question or answer in the recovery summary.

Questions and gate decisions must stay in the main task. Select Feature resolves a uniquely identified target supplied directly by the operator through the typed stable-ID/title/menu-position resolver and does not ask the operator to repeat that choice. Missing or ambiguous intent receives one focused main-task selection question; dependency questions remain separate. Serialized child or report fields never establish trusted intent. The activation snapshot identifies the pointer as explicitly absent or present with a digest, and the controller revalidates that state before effect; physical target identity determines mapping ownership. Select Feature patch branch states are strings compatible with `select_switch_branch`. Separately requested phases may retain only the settled same-target identity after current-state revalidation; a changed target requires a fresh selection, and carried identity does not authorize a newly proposed consequential roadmap change. Completion never invokes another phase or workflow. Completing one workflow never authorizes roadmap verification, Git integration, publication, merge, or feature acceptance.

## Recovery and Stop Rules

Use `.specify/farmboy-controllers/runs/<run-id>/summary.json` only after successful preflight. Create it by piping JSON containing `workflow`, `fingerprints`, `assignments`, and `preflight_passed: true` to `python3 .specify/farmboy/scripts/python/recovery.py create --project "$PWD"`. Update it atomically immediately before each child dispatch and after every step boundary by piping `{"changed_files": ["relative/path"]}` to `recovery.py step --summary <summary-path> --step-id <id> --status <pending|running|waiting_for_human|completed|incomplete>`. Append each loop pass through `recovery.py loop-pass` with its loop ID, 1-based iteration, repeated step IDs and statuses, validated outcome, and compact project-relative evidence. Use only a bounded blocker code: `child-unavailable`, `command-unavailable`, `human-input-missing`, `human-relay-failed`, `installation-changed`, `loop-cap-exhausted`, `main-task-interrupted`, `no-progress`, `operator-deferred`, `preflight-failed`, `step-failed`, `unsupported-workflow`, `unspecified-stop`, or `workflow-changed`. Pass that code in a step update or to `recovery.py stop --summary <summary-path> --blocker <code>` for a run-level stop; use `recovery.py interrupt --summary <summary-path>` after interruption. Explain the specific reason in the main task without placing child transcripts, secrets, absolute paths, or file contents in the record. Record the workflow ID, version, digest, starting install fingerprints, step ID and exact agent name assignments, per-iteration step statuses, repository-relative changed paths, outcome, and blocker code. A running step found after interruption becomes incomplete. When the operator resumes the same invocation, revalidate the workflow digest and install fingerprints before considering a safe resume; changed source or installation stops. Resume only from a fully recorded pass boundary. An interrupted mutating step has no automatic retry: first obtain a fresh assessment of current state, then continue only if it proves safe and in scope. Never roll back partial edits or start a later FarmBoy workflow. Report the summary path and stop reason in the main task.

If a runtime, workflow, input, command skill, named-agent dispatch, human relay, or installation ownership check is missing or uncertain, stop at the smallest affected boundary. A preflight rejection creates no run summary or native workflow run state.


## Selected feature activation

At the selection gate, answer the operator's dependency questions from the displayed inventory while keeping the gate pending; validate a verdict only after an explicit entry choice or defer. Once an unambiguous target is selected, apply only roadmap changes directly authorized by the trusted operator instruction, then perform routine activation when activation is the requested Select Feature operation. A no-op roadmap patch needs no patch-approval gate; a nonempty patch still follows the independently owned roadmap-write contract and any required explicit gate. Revalidate the current target, dependencies, lifecycle, pointer, and source digests immediately before effect. Preserve a focused gate for inferred or unrequested changes, material scope or authority changes, and ambiguous recovery. Select Feature reports the resulting roadmap and active-pointer state. Its reviewed activation helper validates the typed selection snapshot, then atomically updates only `.specify/feature.json`, preserving additional JSON fields and existing specification bytes. It rejects malformed or stale snapshots, unsafe or competing mappings, unmet prerequisites, lifecycle conflicts, and symlinked metadata/pointer state. Activation does not advance roadmap lifecycle; a planned target without a specification remains planned. The target directory may be absent; activation never creates it or a specification. A failed pointer update after a successful roadmap write is a partial state requiring an explicit recovery report, not implicit rollback.

Specify is separately invoked and requires that pointer and a unique matching roadmap entry. It passes `SPECIFY_FEATURE_DIRECTORY` explicitly to the core skill, preserving active identity and existing specification decisions. Completion does not invoke another workflow. The deprecated Start Feature source performs no work and is excluded from active bundle/controller bindings; refresh retires unchanged owned launcher files while preserving locally modified ones under the existing installer rules.


## Roadmap phase lifecycle

The lifecycle owner contract assigns `planned→specced` to Specify, `specced→in-progress` to Implement, and `in-progress→implemented` to Close Out. Each transition is adjacent and owned by its phase. Specify requires current authoring quality, clarification, independent review, a current authored-ready roadmap brief, unique linkage, valid dependencies, and no unsettled consequential decision. Implement requires current reviewed artifacts, verified dependency closure, eligible authorized scope, a fresh Readiness Checker result, and exact declared native assignments before the first Coder. Close Out requires attributable full-scope completion, current convergence, required validation, independent Code Reviewer assessment over immutable code/spec/plan/tasks/test-proof inputs, and no buildable unresolved defect before the first debrief. Exclude mutable roadmap-ledger digests from that assessment; snapshot ledger state separately at each owner edge. The existing explicit `verified` approval remains separate after `implemented`.

The FarmBoy `phase-lifecycle` controller collects and hashes current source inputs and evaluates them against its delivered `milestone_policy.py`. It uses only the roadmap extension's generic contained configuration API and declared command identities. Immediately before the generic amendment, preparation is repeated with the exact prior proposal and source snapshot. A ready result includes `roadmap_delta`, a complete explicit amendment for the assigned FarmBoy Roadmap Agent's ordinary `speckit.flow-roadmap.write` invocation. It names the configured ledger, exact entry/mapping, expected preimage digest, adjacent status change, authority reference and evidence paths. No phase-milestone token or extension lifecycle helper is involved.

A separate FarmBoy Reviewer independently invokes controller `phase-lifecycle` with `{"action":"verify-effect","proposal":<exact retained proposal>,"command_succeeded":true,"occurred_at":"<main-retained actual command effect time>"}`. The main task supplies the command result and timestamp from the current invocation; a child or stored packet cannot establish authority or reconstruct an occurrence. Readback permits only the selected status heading, one newly prepended standard Sync Impact Report and a PATCH version/amendment-date update. It preserves all prior reports byte-for-byte, requires the new report's exact authorization and complete evidence-path list, and compares amendment dates in UTC. It checks unchanged entry bytes, governing source/evidence, exact authorization/evidence provenance and current hashes, then records a strict workflow receipt with exclusive creation and independent byte readback. `applied` survives command failure, post-effect source drift or receipt persistence failure; any such failure blocks. `not-applied` requires the unchanged preimage, and other or unavailable bytes are `indeterminate`. Retry retains the original receipt/time and reassesses current state; it never blindly repeats a write.

For pre-brief authoring proof, controller `phase-lifecycle` accepts `{"action":"validate-specification-ready","packet_path":"specs/<selected>/validation/phase-lifecycle/specification-ready.json"}`. This local check owns author quality, clarification, linkage and exact independent Reviewer evidence. Only a ready result may reach the generic brief, which receives `--authoring-complete true`, the exact selected target and entry and current ledger status. The extension derives dependencies from its current ledger and receives no FarmBoy proof packet.
