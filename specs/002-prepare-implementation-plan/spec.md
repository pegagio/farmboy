## User Scenarios & Testing *(mandatory)*

The operator needs a second local workflow that turns approved intent into a coherent, inspectable implementation proposal. This feature builds on [Feature 001](../001-prepare-specification/spec.md), which prepares specifications; it does not amend that feature's draft/handoff boundary. A fresh analysis means an analysis of the latest affected artifacts after the last repair, rather than reuse of an earlier passing result. Full-plan review covers the complete plan, supporting design artifacts and ordered tasks, not only a summary.

### User Story 1 - Prepare reviewable work from approved intent (Priority: P1)

The operator selects an approved feature specification and starts the planning workflow. It prepares a plan and actionable tasks using existing project capabilities, with no repeated permission requests for prescribed routine steps, then presents the full proposal for human review.

**Why this priority**: The primary value is replacing manual command chaining while preserving the specification approval gate and implementation boundary.

**Independent Test**: Run the actual workflow on a bounded approved feature in a disposable Spec Kit project. Inspect the resulting plan/tasks and confirm it stops before implementation or inferred approval.

**Acceptance Scenarios**:

1. **Given** an identifiable approved specification with ready prerequisites, **When** the operator starts this workflow, **Then** it prepares the implementation plan, supporting design artifacts required by the existing planning capability, and dependency-ordered tasks for that feature alone.
2. **Given** an unresolved material question, missing approval evidence or uncertainty about approval after material changes, **When** preparation is requested, **Then** it explains the missing prerequisite and does not begin dependent planning or treat a completed preparation Goal or clarification answer as approval.
3. **Given** complete artifacts and a qualifying fresh analysis, **When** preparation finishes, **Then** it presents the complete proposal with an explicit Awaiting full-plan review handoff and begins neither implementation nor another workflow.
4. **Given** a material change to previously approved specification meaning is needed, **When** it is discovered, **Then** the affected work stops for explicit specification review rather than silently treating historical approval as approval of the change.
5. **Given** explicit approval of the current specification in the available conversation, **When** this separately selected workflow checks approval, **Then** it accepts that evidence without requiring a saved review note or repeated confirmation.
6. **Given** an applicable existing review note identifying the approved specification content and no material change making it uncertain, **When** this separately selected workflow checks approval, **Then** it accepts the note without requiring conversational approval again.
7. **Given** only answers to clarification questions, **When** approval is checked, **Then** it does not interpret those answers as specification approval.

### User Story 2 - Reconcile analysis findings within authority (Priority: P1)

The operator receives a plan whose requirements, design and tasks agree. Analysis identifies problems without changing files; a separate repair step, authorized by selection of the planning workflow, automatically fixes routine inconsistencies within its approved scope in the affected artifacts, and analysis runs again on the revised proposal.

**Why this priority**: Automating generation alone would leave the operator to discover and repair inconsistencies manually.

**Independent Test**: Introduce a missing task for a specified requirement, run the real analysis and authorized repair sequence, and inspect the revised artifacts and the later fresh analysis.

**Acceptance Scenarios**:

1. **Given** plan and tasks exist, **When** analysis runs, **Then** its findings identify relevant locations and coverage gaps while source artifacts remain unchanged by analysis itself.
2. **Given** the operator has selected the planning workflow and analysis identifies a routine inconsistency within its approved scope, **When** the separate repair step proceeds, **Then** it automatically reconciles all affected current-feature artifacts without another repair approval and repeats read-only analysis after the last edit.
3. **Given** a finding requires a product decision, constitutional amendment or scope expansion, **When** the workflow cannot resolve it within existing authority, **Then** it saves the finding and exact required input and stops dependent work without inventing an answer or weakening governance.
4. **Given** a fresh analysis identifies any actionable inconsistency or unmet requirement, **When** readiness is assessed, **Then** full-plan review handoff is blocked regardless of severity until the defect is resolved; routine defects are repaired automatically within approved scope, while required new decisions receive an input handoff. A defect must not be relabeled optional to pass.
5. **Given** repair is genuinely stuck, repeats unsuccessful approaches or needs a human decision, **When** continuation is assessed, **Then** it stops with a concise INCOMPLETE handoff explaining attempted approaches and remaining issues from existing analysis/spec/plan/tasks evidence. It does not claim a pass or wait for a numeric limit.
6. **Given** a fresh analysis finds zero actionable inconsistencies and zero unmet requirements but offers purely optional suggestions, **When** readiness is assessed, **Then** it discloses those suggestions and presents the full plan for human review without another polishing cycle.
7. **Given** an unmet requirement or inconsistency is labeled LOW severity or presented as optional, **When** the passing rule is applied, **Then** the underlying defect still blocks a passing result regardless of that label.
8. **Given** actionable findings remain and another useful authorized repair is available, **When** fresh read-only analysis informs continuation, **Then** it continues that repair without numeric cycle limits, counters, counter-reset semantics or progress scores. Edits alone do not prove progress or a passing result.
9. **Given** the stopping policy is exercised or reviewed, **When** its evidence is inspected, **Then** it uses existing analysis/spec/plan/tasks and a concise handoff without a separate persistent counter, state file, accounting service or equivalent machinery.

### User Story 3 - Understand and simplify the full proposal (Priority: P2)

The operator can judge the complete proposal, including any new infrastructure or subsystem, and choose approval, simplification or further clarification without losing current work.

**Why this priority**: A technically consistent plan can still add unnecessary complexity; the human needs a concrete basis for the decision.

**Independent Test**: Present a proposal containing an added subsystem and inspect its rationale, simpler alternatives, recommendation and explicit review stop; return a simplification request and verify affected artifacts are reconciled and freshly analyzed before review again.

**Acceptance Scenarios**:

1. **Given** a proposal adds infrastructure or a subsystem, **When** it is presented, **Then** the report names its responsibility, concrete current need or observed failure, simpler alternatives, tradeoffs and the agent's recommendation; it explicitly says when no addition is proposed. For Feature 002's own full-plan review, it also explains how the no-progress instruction is met with existing capabilities and evidence, without the machinery prohibited by FR-007.
2. **Given** a clarification or simplification request, **When** the operator separately authorizes continuation, **Then** accepted changes flow through affected artifacts and fresh analysis precedes the next review handoff.
3. **Given** interruption with partial artifacts, changed answers or a pending input/review handoff, **When** this workflow is invoked again, **Then** it inspects current identity, approval and artifacts, preserves accepted decisions, and resumes only needed authorized work without duplicate setup or overwriting pending input.
4. **Given** native Goal completion or a passing analysis, **When** the handoff is reported, **Then** neither is represented as human full-plan approval or permission to implement.
5. **Given** a separately selected native automation Goal explicitly bounded to review-ready OR saved INCOMPLETE-for-human-input handoff and an actual required question, **When** that input boundary is reached, **Then** the workflow saves and inspects the INCOMPLETE outcome, exact input and artifact references, completes the matching Goal with supported controls and native readback before waiting, and later incorporates an actual answer ordinarily outside that completed Goal without automatic creation/reactivation. An unmet clean-proposal objective, unavailable controls or unrelated technical failure must not be marked successful.

### Edge Cases

- An explicit feature and active pointer disagree: stop before writing to the wrong feature and report the identity conflict.
- Required templates, helpers or analysis inputs are missing: report the exact capability/prerequisite and preserve saved work; do not install tools or invent a replacement controller.
- A required planning question appears before tasks can be generated: save the question and current progress; do not guess merely to keep automation running.
- A pending review already exists: present the current stage rather than regenerating artifacts or reviving a completed Goal to wait.
- Artifacts change after analysis: the earlier pass cannot establish current readiness; analyze the updated proposal again.
- A suggestion labeled optional still describes an inconsistency or unmet requirement: classify it by the underlying issue, preserve it as actionable and do not claim a pass. A purely optional improvement identifies neither; disclose it without extending the repair loop.
- A bounded human-input handoff objective can finish while the planning outcome remains INCOMPLETE; the saved question alone never passes analysis or satisfies an overscoped clean-proposal objective.
- Native Goal behavior cannot establish the required stop/completion: disclose the compatibility limitation and saved next action rather than infer success from prose or a waiting state.
- A rejected repair must not be applied. An unanswered request for a new decision, scope change or material change to approved intent stops dependent work; silence grants no additional authority. Routine repairs already authorized by the selected workflow need no additional response.
- A merged historical feature needs changed meaning: describe the change in the current feature with a reference, preserving the historical record.
- After interruption, inspect actual resolved and remaining actionable findings in existing analysis/spec/plan/tasks evidence without creating or reconstructing counters or separate state. Edits alone do not prove progress. If that evidence cannot establish the needed continuation decision, report the evidence gap and current remaining work plainly.

### Key Entities

- **Approved specification**: Current feature intent with explicit human approval evidenced in the available conversation OR an applicable existing review note identifying the approved content. Either suffices; an old approval does not authorize changed meaning, and a clarification answer is not approval.
- **Implementation proposal**: The full plan, necessary supporting design artifacts and ordered tasks for one feature.
- **Actionable inconsistency or unmet requirement**: A defect in artifact agreement or satisfaction of required behavior/governing constraints; it blocks a fresh pass regardless of severity.
- **Purely optional suggestion**: An improvement that identifies neither an actionable inconsistency nor an unmet requirement; it may accompany review without becoming a repair prerequisite.
- **Analysis finding and authorized repair**: A located issue, its severity and correction. Selection of the planning workflow authorizes separate routine repair within approved scope; findings do not authorize new decisions, scope changes or material changes to approved intent.
- **Preparation handoff**: Saved proposal/progress, actual quality result, unresolved input and next human action. It confers neither approval nor implementation authority.
