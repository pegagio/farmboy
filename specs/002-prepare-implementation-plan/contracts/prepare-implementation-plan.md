# Operator contract: Prepare implementation plan

This is the human-facing contract for the implemented `$farmboy-prepare-implementation-plan` Markdown skill, not an API schema or controller. It was designed before implementation and has now been actually executed; [evidence and native limitations](../validation/acceptance.md) distinguish observed behavior from unaccepted claims.

## Invocation and prerequisites

Example future input: “Use $farmboy-prepare-implementation-plan for the active approved feature; prepare the full proposal and stop for review.” Optional explicit feature paths constrain the same selected feature as the existing pointer; they do not authorize activation of another feature. Read current project guidance and declared prerequisites. Missing capability, unready prerequisites, identity disagreement or uncertain approval stops affected work before mutation. Accept explicit current-meaning approval in available conversation OR an applicable existing review note, without requiring both or a new registry.

Required installed capabilities are `speckit-plan`, `speckit-tasks`, `speckit-analyze` and their supported helpers/templates. Resolve actual installation/hooks at execution time. Each invoked command's actual requirements and required input stops apply; no alias or emitted command label stands in for execution. Do not install missing tools.

## Effects and human boundaries

The selected composition authorizes ordered plan/design creation, tasks, read-only analysis and separate routine current-scope repair followed by fresh analysis. Optional hooks are presented according to their installed contract; they are not silently auto-selected. Mandatory enabled unconditional hooks execute through the actual command before continuing; conditional hooks remain with the supported executor. A hook or command outside authority/required capability creates a concrete stop, never permission to improvise a replacement.

Analysis output itself does not mutate files. Separate repair can correct inconsistencies without another human OK when already inside approved scope. A new product decision, scope expansion or material change to approved intent requires human input and affected review before dependent work. An applicable historical approval is not approval of changed meaning. No core skill is patched to bypass its standalone manual-remediation behavior.

## Outputs and examples

Outputs are ordinary plan.md, supporting research/data-model/contracts/quickstart as required, tasks.md and a structured analysis in conversation. Existing spec/plan notes may save a concise handoff. No new runtime file format is required.

Example successful handoff: “Awaiting full-plan review. Complete proposal: plan.md, research.md, data-model.md, contracts/, quickstart.md and tasks.md. Fresh analysis: zero actionable inconsistencies, zero unmet requirements. Optional suggestions: none. Proposed machinery: one skill plus guide/fixtures; existing artifact inspection handles repair/resume, with no tracking service. Please review the full proposal; no implementation is authorized.”

Example incomplete handoff: “INCOMPLETE: attempted to resolve the missing acceptance-task coverage and reanalyzed the revised artifacts; the remaining requirement conflicts with the approved cancellation policy. Current plan/tasks are saved. A human policy decision and affected specification review are needed. No passing result, plan approval or implementation is claimed.” This is illustrative, not an observation.

Genuinely optional suggestions can accompany successful review. An unmet requirement or inconsistency blocks regardless of severity. Stop when genuinely stuck, repeating unsuccessful approaches or needing a human decision; explain attempts and remaining issues concisely using existing artifacts. No numeric cycle limit, counters/reset semantics, progress scores, new persistence, accounting/tracking framework, controller or renamed equivalent. Edits alone prove neither progress nor passing.

## Resume and native compatibility

Inspect current identity, evidence and artifacts. Preserve changed answers, task IDs/completion evidence and pending questions/review; rerun only affected preparation steps. A current full-plan review handoff is presented rather than rebuilt unless revision is requested. Material spec changes return to review. No duplicate feature/directory/branch or automatic roadmap lifecycle mutation is introduced.

For a separately operator-selected automation Goal whose actual entire objective is a saved review-ready OR INCOMPLETE-for-human-input handoff, durably save the INCOMPLETE planning outcome, exact required input, current artifact references, attempted work/remaining issues and next ordinary action in existing spec/plan notes; inspect that saved handoff, then complete the matching automation Goal through actually exposed supported controls and verify native readback BEFORE waiting for a person. This is successful handoff-objective completion only: it is neither passing analysis, a review-ready plan, plan approval nor implementation authority. After an actual answer, continue by separately operator-started ordinary interaction outside the completed Goal; never create or reactivate a Goal automatically. An overscoped unmet clean-proposal objective, unavailable native controls, arbitrary helper failure or unknown technical failure does not qualify for this human-input endpoint. Preserve the exact limitation without fabricating success, answers or controls. Do not automatically create Goals or reactivate the completed specification Goal. Do not claim saving a question suspends a live Goal or that ordinary resume proves native resume; preserve unsupported observations and use no native-file mutation or continuation controller.

## Review boundary

Full-plan review exposes the whole proposal and each proposed subsystem's need, alternatives, tradeoffs and recommendation. Explicitly explain compliance with the approved minimality constraint using existing capabilities. The workflow does not approve, implement, commit, merge, push or invoke delivery, even if the operator subsequently approves the plan. Implementation is a separately selected workflow. Core skill completion and a passing analysis are not human approval.
