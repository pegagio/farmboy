# Return-consumption semantic contract

This describes ordinary same-session instructions and existing evidence references, not a new request schema, packet, runtime API or loader dependency.

## Shared entry and evidence

The operator selects one existing feature and the next workflow. The caller supplies or resolves the actual return disposition, committed full report and reviewed candidate references plus existing resolution evidence. Before affected proposal/spec edits or setup, verify identity, integrity and applicability and read the full required report set. Wrong feature/candidate/route, altered or unreadable bytes, unsupported lookup, ambiguous current resolution or foreign owner stops affected work precisely. Report-free ordinary initial planning/clarification remains ordinary; do not impose a new report obligation when no return/review evidence applies. A known return cannot be labeled report-free to avoid its obligations.

## Planning consumer

After applicable spec approval and native/current authority checks, consume findings before `speckit-plan` setup or repair. Preserve existing task IDs, completed evidence and accepted decisions. Repair required planning/task/design/analysis issues within approved meaning as the existing composite prescribes; analyze strictly read-only, then separately repair and freshly reassess. Record traceable finding dispositions in affected existing plan/tasks/analysis notes. Optional advice is voluntary with adopted/declined reasons. Current required defects at any priority block complete review-ready output. Material product change stops for separately selected specification clarification/review. Return the complete coherent proposal for full-plan review; no plan approval or implementation follows.

## Specification consumer

On an actual specification escalation, the existing Farmboy continuation guidance directs the separately selected ordinary clarification/revision path, not initial preparation. Supply committed return/report/candidate references and actual product questions as normal invocation context. Ordinary `speckit-clarify` remains unchanged and performs genuine question/answer integration on the existing spec. The executing session must read the supplied report, relate answers/remaining questions to each required finding and reconcile the existing requirements-quality checklist. Native clarify authority precedes edits and remains held between genuine questions; save/release at review or truthful incomplete stop. A historical spec approval, answer or green checklist is not revised-spec approval. The adapter locates evidence and owns native admission/checkpoint/handoff/release only; it supplies no product answer or semantic approval.

Standalone uses equivalent caller-supplied current return/report/candidate evidence under its governance; no Diagram dependency or fixed transport is added. Core clarify/plan/tasks/analyze bodies and hooks are unchanged.

## Resume and subsequent evidence

Record the originating accepted operation/handoff plus exact report/candidate refs and disposition in existing spec or plan notes while they are available. Use these known references with supported inspection after later handoffs; no history-search service or ledger. Read current native/context and current artifacts again before resumed effects. Reuse applicable completed dispositions without duplicate notes; changed relevant input triggers only affected reassessment. Unverifiable history is a precise stop, never guessed resolution. Reviewer remains stopped after its own result and never repairs or launches the consumer.
