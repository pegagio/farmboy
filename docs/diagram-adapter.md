# Optional Diagram routing for Farmboy

Farmboy's optional `farmboy-diagram-work` skill coordinates one selected feature segment using the existing Diagram CLI and existing Farmboy external entries. It is operator-driven agent composition, not a background service or an integration executor. Diagram stores coordination authority/report consistency; the consuming agent verifies actual repository, Git, workspace and artifacts. Source availability and the examples here do not establish runtime acceptance; see [005 evidence](../specs/005-optional-diagram-adapter/validation/acceptance.md).

## Deliberate project setup

Make the optional skill and its native-protocol reference available through your existing supported project/host skill mechanism.005 adds no installer. A compatible Diagram binary/store is required only for enabled projects: Feature6/schema16, independent Project/Repository2 and affectedIssue3. An old PATH binary may expose project commands yet lack Feature coordination; identify the actual compatible executable rather than assuming the name proves capability. Do not migrate/reset a store or patch external software to make this route work.

Enable the route with a bounded paragraph in the consumer's existing `AGENTS.md`, applied by its operator or an agent explicitly authorized to edit that named file. Replace illustrative values with actual selected project/binary/store/configuration. This documentation grants no real consumer edit authority.

> For this consumer project, use Farmboy for ordinary feature requests. Diagram coordination is deliberately enabled for project PROJECT using the existing selected Diagram configuration/store STORE and compatible executable BINARY. Resolve the feature and exactly one segment from the request/current context: “start feature12” selects specification preparation; “clarify this feature,” “plan this feature” and “deliver this feature” select only that segment. Internally use the optional farmboy-diagram-work skill; the operator need not name it. Ask only for missing/ambiguous routing or selection, preserving genuine product questions and explicit reviews. Obtain current native authority before effects. Missing enabled-route capability is a blocker, not permission to install, patch software or fall back. Disclose that explicit segment launch includes necessary feature-scoped checkpoint commits with normal hooks, subject to explicit restrictions and safe feature-only staging; no merge/push. Preserve the whole-adapter Goal endpoint and all human gates.

For standalone projects, explicitly instruct: “Use standalone Farmboy for ordinary feature requests; no Diagram route is enabled.” An explicit operator-selected standalone invocation likewise resolves its route. Tool availability alone enables nothing. Missing/conflicting routing asks targeted input before effects. Opt-in grants no segment launch, product approval, ownership, automatic Goal or arbitrary external edit.

## Ordinary and direct entry

After enabled setup, request “start feature12,” then separately “clarify this feature,” “plan this feature,” or “deliver this feature” as appropriate. Direct named invocation of any of the three Farmboy entries follows the same route check. First enabled entry invokes the adapter once and propagates its return without executing the body again. A verified current adapter invocation continues only the selected external body, without recursive wrapping, duplicate claim/report or early release/Goal completion. Stale/foreign context or an “inside adapter” flag alone stops before effects.

The three Farmboy-owned entries contain only the route/return seam. Diagram native commands, field/authority verification and report semantics live in the optional skill/reference. There is no generic registry/plugin API or command-hook catalog. Actual agent behavior must be independently tested; this guidance is not an absolute interception guarantee.

## Checkpoint scope

Launching a segment discloses and authorizes only necessary feature-scoped checkpoint commits with normal project hooks, subject to explicit restrictions. Viewing/selecting alone commits nothing. The agent inspects index/worktree and exact selected scope, reconciles feature artifacts and verifies actual committed bytes before reporting. It must preserve unrelated staged/unstaged/untracked work. It never stages the workspace wholesale, disturbs unrelated index entries, stashes/resets work or fabricates cleanliness to satisfy native admission/review. Restriction or inseparable edits produce a targeted saved input handoff; failed hooks/commits are technical blockers. No receipt-only tail commit, merge or push.

## Human handoffs and continuation

Initial native claim grants setup only; the consumer prepares/verifies its workspace and link admits a full initial draft run, without an extra acquire. The existing preparation skill returns actual draft/checklist/context findings, then the adapter reports actual checkpoint outcome and verifies release before human clarification/review. Ordinary clarification is separately selected and acquires current clarify/clarification authority before edits, holding it between active genuine questions and releasing at saved review. Resolved questions are not approval.

Explicit whole-spec approval gates planning; full-plan approval gates delivery; the committed delivered candidate stops for human result review. Accepted reports, checks, Goal completion and silence approve nothing. Integration remains separately authorized under real target/branch/check/instruction policy and required destination-policy review, executed elsewhere. Diagram owns serialized integration records/receipts; adapter execution grants no push or integration.

Only an explicitly selected matching whole-adapter native Goal may complete, after saved artifacts and actual coordination/release are read back. Inner entries return local outcomes without completing the wider Goal. A precise saved genuine input handoff can satisfy only a matching bounded objective; technical/unsupported-control/overscoped failures remain incomplete. No automatic Goal creation/restart after answers.

## Failures and limits

Lost responses use existing operation inspection, then current authority before new writes; historical replay grants nothing and repeats no external effects. Changed input/approval/binding gets affected reassessment and review where meaning changed. Preserve answers, tasks and intact pending handoffs. Existing recovery needs explicit stopped-writer/preservation/fencing; no timeout takeover or cleanup framework. One active owner per feature, independent features in isolated workspaces.

An enabled route with missing capability stops precisely rather than reverting to standalone. Required changes to Spec Kit, Diagram or other external software are compatibility blockers, never005 repair scope. Consumer paths in reports are data; core cannot independently detect consistent false physical assertions. Acceptance therefore requires actual separate native executing/evaluating sessions, disposable real Git/coordination, all three external entries plus ordinary clarification, all three standalone regressions and truthful observed/simulated/unobserved limits.
