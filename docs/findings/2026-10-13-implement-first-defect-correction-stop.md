# Implement First-Defect Correction Stop

The first Feature 023 implementation pass exposed an existing Implement continuation defect: a newly discovered eligible source defect stops before its first ordinary correction when no whole task or prior finding has been resolved. This report supplies evidence for the already planned Feature 024 fix; it does not change controller policy, task scope, dependencies, or roadmap state.

## Observation

Run `9a496f02-51c0-4ac0-87fd-a2b92f3a93d0` selected the immutable full Feature 023 scope, T001–T021. T001 was the only eligible task. The first source session added 31 declarative scenarios, preserving historical SI001–SI015. Independent Code Reviewer found F023-T001-R001: a fresh-child negative retained genuine substantive progress but expected blocking merely because child identity changed. Fresh corrective sessions after completed sessions are allowed; same-child restrictions govern pending answer relay.

The fixture error is a legitimate T001 source defect. The separate workflow defect is that it cannot receive an ordinary first correction under the current progress rule. No whole task was complete and no previously retained finding was resolved, so `implementation-progress` returned `substantive_progress: false`, Code Reviewer reported `no-substantive-progress`, and scoped routing returned blocked. The run stopped after one source attempt and one Coder session, with four sessions still available. No task marker changed and no task or finding received retrospective progress credit.

This was neither an exhausted budget nor a changed scope, missing assignment, unanswered product decision, or stale preparation input. The operator had to explicitly request a T001 correction and resumption.

The repeated operator prompting is part of this defect. Ordinary independently identified in-scope corrections repeatedly require the operator to send another fix-and-resume instruction, although scope, authority, retained evidence and remaining budget are unchanged. The observed stops at passes 1, 11, 17, 21, 23, 25, 27, 29 and 30 demonstrate that continuing within a larger budget does not resolve the missing first-correction path. Feature 024 must address this operator burden under finite reviewed correction accounting while preserving genuine scope, authority, prerequisite, evidence and acceptance gates.

## Cause and Existing Follow-Up

The installed Implement graph requires substantive completion or prior-finding resolution after source work. [The controller](../../controllers/farmboy/scripts/python/controller.py), `route_loop_assessment`, lines 651–656, blocks when that intersection is empty. [The scoped adapter](../../controllers/farmboy/scripts/python/implementation_scope.py), `route_scoped_implementation_assessment`, lines 994–999, applies the generic predicate after an attempt. A newly discovered finding has no prior identity eligible for resolution credit in the first pass.

Code Reviewer recognized that boundary and returned a blocked envelope before correction. The scoped adapter preserved it. The guard operates as currently written; its lack of a bounded first-correction path is the workflow defect.

This matches WR-04 in [the workflow-reliability handoff](2026-10-12-workflow-reliability-handoff.md#feature-024-continuation-and-correction-accounting) and [roadmap Feature 024](../../.specify/memory/roadmap.md), Implement Continuation and Correction Accounting. Its later specification must settle finite accounting and first-correction rules. No arbitrary replacement cap, unlimited retry, authority bypass, or new dependency is selected here.

## Expected Behavior and Regression Cases

One authorized invocation should permit a defined first correction of a newly discovered eligible source defect under a finite reviewed policy, while discovery and administrative updates earn zero substantive resolution credit.

- **First eligible defect**: A first source attempt leaves one independently identified in-scope defect and no whole task complete; the invocation retains the exact finding baseline and permits its defined first correction without a restart question.
- **Actual correction**: Fresh independent review proves resolution against that retained preimage; only then may the finding earn progress credit.
- **Ineffective correction**: Repeating the defect or changing only reports, markers, answers, timestamps, or child identity earns no progress and stops under the reviewed finite policy.
- **Unchanged bounds**: Histories remain append-only, failed attempts count, and neither a new baseline nor a resumed child resets consumed counters.
- **Authority and safety**: Unavailable assignments, stale inputs, changed scope, and consequential decisions still block. Ordinary new corrective sessions remain distinct from replacing a child with a pending answer.
- **No duplicate owner effect**: Recovery retains the original lifecycle proposal, receipt and occurrence time and performs no repeated roadmap write.
