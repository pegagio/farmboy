# Completed-work finalization v1

DIAG-31 source capability, requiring matched schema29/Feature9 and `finalization_contract:1`. Availability is not installation, human approval, opt-in, action permission or budget. Native core checks reported consistency; the consuming adapter owns physical Git/process/effect inspection and semantic completion. It does not authenticate consent or inspect a consuming repository.

## One continuation family

An optional `mode: finalization` extends the existing continuation policy, successor origin and immutable run/operation history. Absent mode remains ordinary execution. Fixed mode/stage/purpose slots cannot overwrite execution holds or consumed allowances. There is no new table, mutable attempt counter, scheduler, handler registry or parallel ledger.

Supported completed work: specification draft/flowback, integration of already-recorded clarification answers, coherent plan/tasks/analysis, fully evidenced delivery, and an already-rendered independent-plan-review verdict. Each retains its normal stage endpoint. Missing human answers/approvals/result acceptance/instruction adoption, missing implementation or mandatory live evidence, semantic replay, released integration/merge replay and terminal history reopening remain excluded. Active-owner resume/replace and released-incomplete execution remain separate.

## Frozen output and bounded authority

Existing continuation show/record transports explicit actual authority and exact current revisions, input/handoff/approvals, predecessor run/epoch, role outcome, original producer and completion/check citations. A `PreparedContent` report is an actual base plus unique relative path/digest manifest and exact index/dirty/untracked findings. Its output role manifests are artifact-only and strictly reject a commit field; a normal committed Checkpoint is constructed only after an actual consumer-observed checkpoint. It is not a claim that staged bytes exist in the base commit. Unknown effects or changed content block readiness.

A finalization mandate uses `authorize-bounded-finalization`; deliberate readiness uses `continue-bounded-finalization`. Actual denied action/target requires new applicable `permit-denied-finalization-action` permission and confirmed nonexecution. Platform approval and normal hooks remain in force. One admitted finalizer consumes one allowance even on failure; explicit renewal names the prior allowance and preserves history. Withdrawal blocks admission and requires fresh renewal. Holds, revocation, opt-outs and separate external budgets remain binding.

The original semantic input, rendered actor/verdict/report and consumed review grant remain immutable. The new administrative run has a separately attributed `FinalizationOrigin`. Original reviewer and finisher must both be nonauthors. Active-owner replacement preserves the origin and deduplicated admission consumption; a released failure cannot be disguised as an active replacement.

## Maintained entry and terminal

`feature continuation acquire-finalization` resolves recorded readiness and constructs the existing successor operation from exact feature/revision/queue/handoff/stage/purpose/allowance/binding/owner/session/HEAD/repository/instance/worktree pins. Actual consumer rationale/evidence/conditions are recorded independently of the original coordinator report. Failed preparation has no admission or consumption. No agent-generated acquisition envelope is necessary.

The finalize-only adapter verifies current content/effects/authority and commits only the exact authorized still-missing snapshot with normal hooks. A present commit is never repeated; changed hooks/content invalidate readiness rather than permitting repair. `apply-finalization` resolves the frozen normal terminal under current fencing, checks actual committed clean HEAD/report and role references, then reuses existing stage validation/persistence. The original semantic actor stays the decision actor; the finisher is separately attributable. Exact operation replay is historical completion, never current ownership; a conflicting outcome is refused.

Successful terminal recording completes/releases the new run and restores ordinary guarded forward discovery while retaining the old released predecessor. Future work still needs its real gate and controls. Existing operation/current-state inspection reconciles lost commit/native responses before any permitted retry.

## Ordinary poller and compatibility

The originating existing workflow toggle governs finalization (clarification output uses specification). OFF preserves readiness without consumption; OFF after admission does not cancel the child. A pending/held finalization blocks conflicting same-feature fallback. Ordinary polling can discover readiness in the same process, launches one child, verifies origin/terminal/release and visibly stops on unresolved failure. No semantic Farmboy workflow body is called by finalization submode.

The explicit28→29 upgrade changes version metadata only after schema validation and no-active-authority checks; current27→28 continues to target frozen28. Prior rows/JSON/receipts/grants/holds/allowances/revision intents/opt-outs are preserved, without legacy enrollment. Matching old snapshots/tools are required for rollback without discarding intervening writes; no in-place downgrade is provided. Only separately authorized cutover may alter the installed runtime or live store.

Private tests exercise four-family native outcomes/refusals, races/replays/renewal/revocation/withdrawal, owner replacement, response loss, preserving migration/restore and real CLI/Git/poller processes with controlled semantic actors/permissions. They do not prove live model/platform permission recognition or production BGG recovery.
