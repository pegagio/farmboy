# Deliver an approved plan

Use `$farmboy-deliver-approved-plan` for the currently selected feature after explicit specification and full-plan approval. It composes installed implementation, verification, convergence/repair and local documentation closeout, then stops **Awaiting result review**. It uses the current session model/effort and delegates no runtime steps. The [operator contract](../specs/003-deliver-approved-plan/contracts/deliver-approved-plan.md) defines the interface; [actual evidence](../specs/003-deliver-approved-plan/validation/acceptance.md) distinguishes observations from limits.

It does not require/recreate a retired local roadmap/wiki, run local queue-status writes or update Diagram. Applicable configured wiki maintenance remains; standalone local closeout is preserved.

Standalone entry retains the existing local selection/context, verified-ledger prerequisites, helpers/hooks and review stops described below. External entry is explicit caller selection, not a fourth selector or bridge. Existing Git constitution/direction/feature artifacts govern rules/context; accessible relevant references identify work/input revisions or current working state as needed. Ask for specific material stale/conflicting/missing input before dependent work, without invented answers, fixed packets or a provenance register. Core helper workspace/pointer/environment association must agree before effects; do not silently retarget it or add another activation.

See [workflow handoffs](workflow-handoffs.md) for all three examples, checkpoint/resume and coordinator-owned sequential ownership. No Diagram ownership service is needed for standalone use. A returned outcome is not handoff acceptance, approval, integration authority or permission for a next workflow. ## Entry and scope

Example: “Use $farmboy-deliver-approved-plan for the active approved feature; deliver and close out locally, then stop for result review.” Explicit and active-pointer identity must agree; paths stay contained and roadmap prerequisites must be verified. Conversational approval or an applicable existing content-identifying review note suffices. Changed material meaning requires affected human review; a checklist, answer, passing test, fixture approval or completed Goal is not approval.

The selected composition authorizes its routine implementation→verification→convergence→follow-up implementation/repair without repeated OKs, plus actual delivery documentation/debrief/wiki ingestion/lint, the narrow implemented update and final scoped local commit. Core commands retain real checklist/input/hook rules. A missing command or mandatory hook is an exact stop, not an installation/substitution opportunity. Existing unrelated staged/unstaged work must be preserved and excluded from the delivery commit.

## Repair and closeout

Converge runs after actual implementation and only appends follow-up tasks. Separate authorized repair reconciles affected current spec/plan/tasks and implementation; then implement/check/reassess until zero actionable gaps and zero unmet requirements. No required defect may be relabeled optional by severity. Optional suggestions are separate; they cannot cause endless polishing. Continue useful repairs from actual findings and outcomes, stopping for genuine required input, material decisions or lack of a useful authorized resolution. No numeric attempt limits, counters/reset semantics, scores or new persistence/accounting/controller machinery are introduced.

Complete coherent delivery documentation, an actual attributable roadmap debrief and relevant one-source-at-a-time wiki ingestion/lint. Debrief recommendations never authorize roadmap amendments. After all required work/checks, include only the selected entry's implemented update with ALL scoped durable delivery artifacts in the final LOCAL commit, using ordinary installed roadmap-write and normal Git settings/hooks. Report actual commit success before claiming successful delivery; report an ordinary Git error honestly. No hypothetical failure machinery or receipt-only commit is needed.

Successful local delivery records implemented and hands off Awaiting result review; only subsequent explicit applicable human result acceptance separately authorizes verified. Delivery itself never performs that later transition. Incomplete/Goal handoffs cannot claim successfully recorded delivery. No integration, declaration integrated/complete, merge, push, undefined final feature-completion operation or bridge/adapter transport implementation is included or required. Human final-result/UAT review must explicitly authorize later integration under project branch/target/check policy. Diagram owns serialization and database-only integration receipts; missing/conflicting policy is surfaced, no executor placement is selected and no receipt-only project commit is added.

## Handoff and resume

Result review receives actual commit/artifact/evidence links, debrief/wiki outcomes, limitations and optional suggestions. Resume inspects current artifacts/Git/roadmap/approval applicability, preserves accepted answers/task identities and checked evidence, performs missing/affected work only and presents a valid pending review without duplicate effects. Material changes return to affected human review; merged feature history is not rewritten.

A required-input handoff saves INCOMPLETE delivery, exact question, current artifacts, actual work/remaining issues and ordinary next action. For a separately operator-selected matching bounded Goal, durable save/readback→supported completion→native complete readback occurs BEFORE asking/waiting. This completes only the handoff objective, not delivery or approval. After an actual answer, separately selected ordinary interaction continues outside the completed Goal; no automatic Goal restart/create. An unmet delivery-only objective, unknown helper failure or unavailable control never becomes a successful input handoff. Use actual supported controls, not host DB mutation or invented receipts.
