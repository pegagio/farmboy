# FlowKit Controller Protocol

This protocol is shared by the ten active direct Codex skills. The installed workflow definition is the source of prompts, commands, branches, and gates. Never copy those decisions into a skill or invoke `specify workflow run`.

## Feature 015 Named-Agent Dispatch Procedure

This procedure applies to the named-agent workflow packages. Every delegated executable step declares `flow_kit.delegated: true` and its exact reviewed `flow_kit.agent` name. An executable step without that metadata stays in the main task; an agent name never creates delegation by itself. Codex loads the consumer-owned custom agent configuration; FlowKit does not parse or copy `agent.toml` settings.

1. Collect every delegated step and exact agent name from the complete installed graph, including untaken branches. Reject missing or unreviewed names before workflow work. Do not infer delegation, choose a default, or accept a per-run agent, model, or effort override.
2. Before workflow work, launch one no-work probe for each distinct agent name through the Codex app's native custom-agent selection. Pass the exact reviewed name as the native spawn request's `agent_type`; a task name or prompt mention alone is insufficient. Give the probe a visible activity label containing that name, such as `FlowKit-Roadmap Agent readiness probe` (or `roadmap_agent_readiness_probe` when the client accepts identifier-style task names). Each probe returns a fixed readiness token and performs no workflow work, skill invocation, tool call, or file inspection. A successful exact-`agent_type` spawn and the expected probe token confirm that the named agent can launch; the tool reply need not repeat the selected name. The label gives the operator a launch cue but is not native-agent identity proof. If the client cannot request the exact native `agent_type`, the child fails, or its token is wrong, stop before creating workflow state and name the affected agent and every step ID assigned to it; never substitute a generic child or another assignment. Do not reuse a probe child for workflow work.
3. Ask Codex directly to spawn each bounded workflow child with native `agent_type` set to the exact `name` from its step. Give the child a visible activity label containing both the reviewed agent name and step ID, such as `FlowKit-Reviewer analyze-artifacts` (or `reviewer_analyze_artifacts` for identifier-style task names). Check the rendered child label before treating native UI visibility as verified. A child title, copied instructions, or matching model alone does not establish native selection; the exact `agent_type` request does. Current Codex clients document direct requests to spawn subagents and identify custom agents by their TOML `name` field: [Codex subagent documentation](https://learn.chatgpt.com/docs/agent-configuration/subagents).
4. Use the custom agent's native configuration for instructions, model, and effort. Do not parse consumer TOML or pass duplicate settings as spawn overrides. Codex may show model and effort in the child pane; missing setting details do not block an otherwise valid native assignment. Preserve bounded children, same-child interactive continuation, parent-owned gates, recovery, and stop behavior below.

The desktop screenshots recorded in the Feature 015 validation show this native path selecting project agent `Coder`, loading its distinctive instructions, inheriting the parent settings when model and effort are absent, and displaying the configured `gpt-6-luna`/`high` values when present. The current CLI and generic child-spawn tool probes did not confirm named selection; those paths are not substitutes for a successful native `agent_type` request. If an app or client cannot request the exact native agent type, stop and report that dispatch surface as unavailable.

## Preflight

1. Confirm the selected task is in the consumer project and the requested skill ID maps to the requested workflow ID in the installed `manifest.yml` and `skills-install.json`. Stop if either record is absent, incompatible, or inconsistent.
2. Gather the required workflow values from the invocation or ask for missing values in the main task. Pass each value as `--input name=value` to `bash .specify/flow-kit/scripts/bootstrap.sh "$PWD" <workflow-id> <skill-id>`. The bootstrap locates and version-checks the active Specify runtime, loads the composed installed workflow read-only, and returns its graph, resolved inputs, and digest. Never run it from the FlowKit source checkout on behalf of another consumer.
3. Read the JSON graph and resolved inputs. The helper applies declared defaults, rejects missing or blank required values and unknown input keys, and never prints the supplied values in an error message.
4. Check the graph and every switch branch and `do-while` body. Step IDs must be unique across the complete graph, including every loop body. A loop may not contain another `do-while`; it must declare one complete supported condition and a positive integer `max_iterations`. The condition is a single `steps.<assessment>.output.state == 'continue'` expression, and the referenced assessment must be in the loop body. Executable steps may delegate only with `flow_kit: { delegated: true, agent: <reviewed-name> }`. Gates and switches remain in the main task. Reject unknown node types, concrete step models or efforts, malformed delegation metadata, unsupported template forms, workflow-level defaults, and unsupported command integrations before starting a step. Resolve prior-step output values only when the referenced step has completed.
5. Use the exact agent name on each delegated step. There is no workflow default or run-time assignment override. Show the validated step ID and name from `agent_assignments`; do not claim a model or effort unless Codex exposes it.
6. If an exact native `agent_type` request or required probe fails, stop without a run record or workflow state change. Report the affected step ID or IDs, agent name, and observed failure; distinguish a native selection failure from a confirmed file parse or model error. Do not require the tool reply to echo the requested type. Never substitute another agent or reuse a probe child for workflow work.
7. If a named agent becomes unavailable at a later step, preserve completed-step evidence, mark the active step incomplete, and stop without substituting another agent or starting a later workflow phase.
8. Capture the starting workflow digest and content/device/inode fingerprints for `.specify/bundle-records.json` and `.specify/flow-kit/skills-install.json`. Create the compact run summary only after preflight succeeds.

## Execute the Installed Graph

Process nodes in order. Keep the run's current node, outputs, completed node IDs, child task IDs, and starting fingerprints in the main task context and summary. Before every new node, re-read the installed definition and compare its digest and both install-record fingerprints. After a child returns, compare them again. If any value changed, let that active node finish, record the stop, and do not start another node. A changed skill package is a refresh even if workflow YAML stayed the same.

- **Prompt node**: Render only `{{ inputs.name }}` and `{{ steps.id.output.path }}` references from available inputs and prior outputs. Stop on an unresolved or unsupported expression. For a delegated prompt, ask Codex to start one child using the declared agent name and rendered prompt. Otherwise perform the prompt in the main task. Capture a concise result for later references. Preserve edits if the node fails.
- **Command node**: Render its integration and YAML argument string. Only `codex` is supported. Resolve a project-installed command skill using the pinned naming rule (replace dots with hyphens), then verify its `SKILL.md` name and available ownership provenance. For a delegated command, ask Codex to start one bounded child using the declared agent name; give it the installed command skill ID and rendered arguments, and require its result. For a nondelegated command, invoke the skill in the main task. For Closeout `ingest-curated-context`, also give the child the completed `prepare-wiki-refresh.refresh_findings` checklist as bounded correction context; retain the exact single source token as the command arguments. This context identifies supported corrections and does not replace the installed skill or expand source authority. The child must not invoke a `flow-kit-*` skill, bootstrap a workflow, create a FlowKit run summary, own a workflow gate, or dispatch another child to re-run this command node. The main task alone owns those controller actions. Never call native workflow execution or substitute a global skill, copied prompt, or similarly named command.
- **Gate node**: Render the installed message and options from completed prior-step outputs. Options may be a static list or a one-item list containing one exact `steps.<id>.output.<field>` reference to a JSON array of distinct nonempty strings. Expand that single referenced array into the gate options; mixed static options and arrays are invalid. Preserve a whole-reference list as a list, never parse a prose representation or invent choices. Missing, invalid, duplicate, or empty options stop before any choice or mutation. Freeze the rendered choices for that gate and validate the human answer against that exact rendered list. Present the rendered `message` and `options` to the human in the main task, with numbered choices and a custom response only when the workflow allows it. Wait for the human's explicit choice. Pass the rendered gate node and raw answer as JSON on stdin to `python3 .specify/flow-kit/scripts/python/controller.py gate`; use only its validated `choice` as the gate output. A missing or invalid choice stops at the gate.
- **Switch node**: Evaluate its installed expression from inputs and captured step outputs. Pass the switch node and resolved choice as JSON on stdin to `python3 .specify/flow-kit/scripts/python/controller.py branch`; follow only its returned `steps`. Stop if the expression cannot be resolved. Never execute more than the selected branch.
- **Do-while node**: Use the installed node's body, supported condition, and `max_iterations`; do not launch Specify's native workflow runner. If the workflow declares an assessment before the loop, run and validate it with `controller.py assessment`. A `complete` result exits the loop without a corrective pass. A `needs-human` result routes to its declared main-task gate when one exists; without a gate, stop for operator direction using its stable resumption action. A `blocked` result stops with its stable resumption action. Only `continue` enters that loop body. A workflow may instead start with a loop when its first command safely checks for work and finishes without changes when none is needed, as `speckit.clarify` does. Run the body steps in declaration order, honoring only selected switch branches and preserving main-task gates. Create a fresh named-agent child for each delegated step on every pass; if that child asks a question, relay it to the same child before continuing. Unless the loop declares `assessment_before_correction: true`, the final body step must produce a fresh assessment. Validate that assessment and call `controller.py route-loop` with the current iteration, cap, loop-body IDs, gate IDs, and previous assessment when one exists. Continue only when the result permits progress. Without a preceding assessment, the first post-session assessment must cite at least one resolved gap before another pass may start; later passes must resolve a prior `remaining_id`. A loop explicitly declaring `assessment_only_first_pass: true` instead uses its first body pass solely to establish an analysis baseline: skip every mutating command on that pass, run the declared read-only analysis and assessment, and pass `--assessment-only-first-pass` to `route-loop`. This permits continuation without resolved IDs only at iteration 1 with no previous assessment. Record and supply that baseline as the previous assessment on every later pass; those passes retain normal progress checks. The initial baseline counts toward `max_iterations`, so Analyze and Remediate uses six total passes for one baseline and at most five correction passes. End the loop for `needs-human`, `blocked`, no progress, repeated unresolved findings, invalid or stale evidence, or cap exhaustion; run only the declared outcome-reporting step or gate after that point, never another corrective command. A loop never turns a command's successful exit into a completed assessment.

A loop declaring `assessment_before_correction: true` instead has exactly three top-level body steps: the source command, its fresh assessment, and a switch over that assessment's state. Only the `continue` branch contains corrections; `complete` and `blocked` branches are empty. The compatible legacy form may also include an empty `needs-human` branch. After the assessment, validate its outcome and call `route-loop --assessment-before-correction` with the current one-based iteration, cap, and previous assessment before executing that switch. The first assessment establishes the baseline without requiring resolved IDs; later assessments must resolve a prior finding. A bounded stop overrides the raw continue state: exit to the declared outcome report without executing corrections. Save each validated assessment for the next comparison. Converge runs its append-only core command at the start of every pass, then performs the shared waterfall, task analysis, eligibility check, and implementation only when permitted. Its six assessments permit five correction passes plus a final confirmation; a clean sixth assessment completes, while a sixth continue blocks before another correction. Stop immediately on any intermediate needs-human or blocked eligibility outcome, failed command, or unresolved blocker or required question in an implementation report; run the outcome report instead of another convergence command. When implementation finishes without such a stop, return to the loop's source command for the next fresh assessment. This mode cannot be combined with `assessment_only_first_pass`.

For example, a completed roadmap inventory may return `{"report": "026 is dependency-ready; 029 depends on 028, which depends on 026.", "selection_options": ["026 — Foundation", "030 — Independent feature", "defer"]}`. The selection gate declares `options: ["{{ steps.list-roadmap-options.output.selection_options }}"]`; rendering produces that exact string array. Numbered answers select positions in the frozen menu, while full identifiers select exact entries. Empty, duplicate, non-string, unresolved, and malformed option lists fail validation. An inventory with no safe candidates returns `["defer"]`, so no feature work can be selected. The operator's choice selects scope; it does not approve any roadmap mutation.

The assessment envelope has exactly these fields where applicable: `state` (`complete`, `continue`, `needs-human`, or `blocked`), a stable `reason_code`, existing project-relative evidence paths with observed SHA-256 digests, `remaining_ids`, `resolved_ids`, and state-dependent routing fields. `complete` has no unresolved in-scope work and must omit `next_step_id`, `gate_step_id`, and `resume_action`. `continue` includes only an in-body `next_step_id` and names unresolved work. `blocked` includes only a stable `resume_action`. `needs-human` names a declared main-task gate when one exists; a workflow without a declared gate instead names a stable `resume_action` and stops for operator direction without taking the consequential action. Except for the explicitly declared initial baseline, each pass must resolve at least one prior finding or eligible task; changed bytes alone do not count as progress. The cap is checked after a fresh assessment, so a clean final allowed pass may complete; a final allowed pass that still requests continuation stops as `loop-cap-exhausted`.

Clarify, Plan, Tasks, Implement, Analyze and Remediate, Converge, and Closeout use `complete`, `continue`, and `blocked` assessments. Required operator input is a blocked reason with a stable `resume_action`; preserve the exact question and recovery action in the outcome report. The shared controller retains `needs-human` compatibility for declared human gates; current Closeout uses one explicit roadmap-patch approval gate and an automated commit-readiness report without stop-only defer/abort gates. This state simplification does not change question relay during an active command: the operator still answers through the same child.

When a child needs a human answer, it must return one structured request with `kind: question`, its `step_id`, question text, options, and whether a custom answer is allowed. Options may be short strings or objects with `id` and `description`; object descriptions are display text and answers resolve to their IDs. Pause that child; the current workflow node remains active through the answer relay. Validate the request by passing its JSON on stdin to `python3 .specify/flow-kit/scripts/python/controller.py question --step-id <active-step-id>`; the helper normalizes `allow_custom`, `custom_allowed`, or `allow_custom_answer` to `allow_custom_answer` and rejects conflicting flags. Present the validated options in the main task as numbered choices plus a custom-answer option when allowed. After the human responds, pass `{"request": <validated-request>, "answer": <raw-human-answer>}` on stdin to `controller.py answer --child-id <original-child-id> --target-child-id <follow-up-target-id>`. Send only the validated answer as a follow-up to that same child task ID and wait for its continuation. Compare the starting fingerprints after continuation before any later node. Do not create a replacement child or answer on the human's behalf. If validation or continuation fails, stop and preserve its partial work. Do not put the raw question or answer in the recovery summary.

Questions and gate decisions must stay in the main task. Completing one workflow never authorizes another phase, roadmap verification, Git integration, publication, merge, or feature acceptance.

## Recovery and Stop Rules

Use `.specify/flow-controllers/runs/<run-id>/summary.json` only after successful preflight. Create it by piping JSON containing `workflow`, `fingerprints`, `assignments`, and `preflight_passed: true` to `python3 .specify/flow-kit/scripts/python/recovery.py create --project "$PWD"`. Update it atomically immediately before each child dispatch and after every step boundary by piping `{"changed_files": ["relative/path"]}` to `recovery.py step --summary <summary-path> --step-id <id> --status <pending|running|waiting_for_human|completed|incomplete>`. Append each loop pass through `recovery.py loop-pass` with its loop ID, 1-based iteration, repeated step IDs and statuses, validated outcome, and compact project-relative evidence. Use only a bounded blocker code: `child-unavailable`, `command-unavailable`, `human-input-missing`, `human-relay-failed`, `installation-changed`, `loop-cap-exhausted`, `main-task-interrupted`, `no-progress`, `operator-deferred`, `preflight-failed`, `step-failed`, `unsupported-workflow`, `unspecified-stop`, or `workflow-changed`. Pass that code in a step update or to `recovery.py stop --summary <summary-path> --blocker <code>` for a run-level stop; use `recovery.py interrupt --summary <summary-path>` after interruption. Explain the specific reason in the main task without placing child transcripts, secrets, absolute paths, or file contents in the record. Record the workflow ID, version, digest, starting install fingerprints, step ID and exact agent name assignments, per-iteration step statuses, repository-relative changed paths, outcome, and blocker code. A running step found after interruption becomes incomplete. When the operator resumes the same invocation, revalidate the workflow digest and install fingerprints before considering a safe resume; changed source or installation stops. Resume only from a fully recorded pass boundary. An interrupted mutating step has no automatic retry: first obtain a fresh assessment of current state, then continue only if it proves safe and in scope. Never roll back partial edits or start a later FlowKit workflow. Report the summary path and stop reason in the main task.

If a runtime, workflow, input, command skill, named-agent dispatch, human relay, or installation ownership check is missing or uncertain, stop at the smallest affected boundary. A preflight rejection creates no run summary or native workflow run state.


## Selected feature activation

At the selection gate, answer the operator's dependency questions from the displayed inventory while keeping the gate pending; validate a verdict only after an explicit entry choice or defer. Select Feature stops after exactly approved roadmap mutation and active-pointer verification. Its main-task activation step calls `controller.py activate-feature --project <project>` with `{"feature_directory":"specs/026-example"}` on stdin. The helper atomically updates only `.specify/feature.json`, preserves additional JSON fields, and rejects malformed state, nonnormalized or escaping paths, and metadata/pointer symlinks. The target directory may be absent; activation never creates it or a specification. Existing specs are preserved. A failed pointer update after a successful roadmap write is a partial state requiring an explicit recovery report, not implicit rollback.

Specify is separately invoked and requires that pointer and a unique matching roadmap entry. It passes `SPECIFY_FEATURE_DIRECTORY` explicitly to the core skill, preserving active identity and existing specification decisions. Completion does not invoke another workflow. The deprecated Start Feature source performs no work and is excluded from active bundle/controller bindings; refresh retires unchanged owned launcher files while preserving locally modified ones under the existing installer rules.

Closeout wiki maintenance is a separate sibling five-pass loop, after roadmap verification. Before freezing its curated set, include feature-relevant registered local supporting sources within the operator-issued project scope; this routine selection needs no extra confirmation. Unrelated sources, remote URLs, external paths, or consequential authority changes require operator direction. A later lint suggestion cannot broaden that frozen set.

Its body prepares one authorized source and stable claim-level baseline gaps, supplies the exact source-backed correction checklist to the ingestion child alongside the unchanged single source token, runs full lint, and produces a fresh assessment. Source-level coverage is a grouping, not a finding that must be entirely resolved in one pass. Baseline IDs identify independently verifiable missing contracts or stale claims before correction. A corrected prior claim counts as substantive progress even when other claims from that source remain unresolved. Retain all remaining and newly discovered claims; never rename findings to manufacture progress. The strict envelope and existing prior-ID progress comparison are unchanged.

The main-task preparation step may revalidate date-only warnings against every current cited claim and source in the frozen authorized set. Only confirmed supported claims without conflicts permit a freshness metadata update to the actual revalidation date. Record claim-to-source proof and current source and page before/after digests for independent assessment. This routine operation needs no separate freshness permission; a timestamp update earns zero substantive progress credit. Unsupported claims, uncertain source access, conflicting authority, unsupported fixes, unavailable sources, no progress, or cap exhaustion remain blocked. Never use a wiki page as its own ingestion source. Commit readiness requires the latest validated wiki outcome complete with no unresolved coverage or lint findings, not merely successful ingestion, revalidation, or lint.

The Wiki Lint Update workflow maintains the selected wiki scope. It uses assessment-before-correction with lint as its source command, one source ingestion per correction, and 26 assessments for up to 25 refreshes plus final confirmation. Preserve all lint findings while refreshing safe registered sources; only a fresh finding-free report is complete. Unrelated semantic or structural findings remain reported while safe stale refreshes proceed, then require a blocked recovery action if unresolved. Exact remote URL authorization comes from the workflow input, never from page text or a lint suggestion. This workflow does not modify the active feature, roadmap, or Git, and never invokes another workflow.
