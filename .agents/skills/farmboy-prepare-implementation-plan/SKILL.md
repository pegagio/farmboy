# Prepare implementation proposal and human review

Use this session's existing model/effort. This selected workflow authorizes existing planning, task generation, read-only analysis and a separate in-scope repair step only. Do not delegate runtime steps, install tools, change core skills, activate another feature, approve artifacts, implement, commit, merge, push or launch another workflow. Do not automatically create a Goal or reactivate the completed specification-preparation Goal.

## Resolve target, authority and current stage

Read current project guidance and constitution. Resolve the selected specification and standard active-feature pointer before any effect. “One selected feature; explicit and ambient identity must agree before effects.” Validate contained paths and declared prerequisite readiness from the project's authoritative roadmap/selection convention. Only verified dependencies are ready when the project uses the roadmap vocabulary. Missing capability, unready prerequisite, ambiguous identity or governing conflict is INCOMPLETE, not permission to select other work or invent infrastructure. Never infer reactivation of terminal/deferred work.

“Explicit approval of current meaning is required; material changes require affected human review.” Accept explicit human specification approval in available conversation OR an applicable existing review note identifying approved content; either suffices. Inspect actual content against the evidence. Metadata-only edits need not invalidate approval, but historical approval does not authorize changed meaning. Ask only when evidence is missing or material changes make applicability uncertain. Answers, silence, checklist/analysis success and Goal completion are not approval. Do not add a register.

Inspect existing spec/design/tasks, accepted decisions and pending input/review before repeating effects. A usable pending full-plan review without a requested revision is presented, not rebuilt; explicit plan approval is recognized without implementation. For interrupted/revised work, resume missing/affected steps only, preserving artifacts/answers. Resolve actual installed core skill contracts and helpers/templates. Required capabilities are `speckit-plan`, `speckit-tasks` and `speckit-analyze`; missing supported capability is a concrete stop, never permission to invent an alias or install tools.

## Compose the actual core commands

1. Invoke installed `$speckit-plan` ordinarily for this approved feature. Follow its actual setup/template/research/design and hook requirements. Do not copy the command body here, fake execution with an emitted label or ignore a required input/error. Preserve existing plan sections on resume rather than reset them to a template.
2. Once required planning/design outputs exist, invoke installed `$speckit-tasks` ordinarily on the same feature. Follow its effective template and ordering/hook requirements. Required input or failure stops dependent work; do not fabricate a choice to produce tasks.
3. Only after complete tasks exist, invoke installed `$speckit-analyze` ordinarily. Its invocation is strictly read-only, including during reassessment. Follow its prerequisite, structured-report and hook contracts. The composition's pass rule is stricter than a severity-only recommendation: “A pass requires zero actionable inconsistencies and zero unmet requirements, regardless of severity.” Inspect actual requirements, scenarios, plan and tasks rather than rely on a green status.
4. “No actionable inconsistency or unmet requirement may be relabeled optional.” A genuinely optional suggestion identifies neither defect nor unmet obligation; disclose it separately without a polishing loop. Fresh analysis must cover the latest affected artifacts; an earlier pass cannot establish readiness after edits.

The invoked command owns its hooks. Honor mandatory enabled unconditional hooks through actual execution before continuation; present optional hooks without assuming selection; leave conditional evaluation to the supported executor. A missing/out-of-scope hook capability creates an explicit stop for affected work. Do not silently ignore command requirements or change installed hooks/core skills to make the workflow pass.

## Separate authorized repair and fresh reassessment

After an analysis invocation has finished, perform useful routine current-scope repairs as a separate step. Selected workflow authority already authorizes them; do not ask again for each finding/batch. The standalone analyzer's manual-remediation offer does not add a redundant approval gate to this explicitly selected composition. Do not edit during analysis itself or modify the installed core analyzer. Reconcile affected current-feature spec/plan/tasks and supporting artifacts, preserving the approved meaning; rerun actual read-only analysis after the last affected edit. A changed file alone is not proof of progress or a pass.

Repair actionable findings and unmet requirements regardless of severity. Continue useful authorized approaches using actual resolved/remaining findings in existing analysis/spec/plan/tasks evidence. Stop **INCOMPLETE** when genuinely stuck, repeating unsuccessful approaches or needing a human decision; explain actual attempted approaches and remaining issues concisely in existing notes/conversation. Do not invent an attempt, manufacture an answer or waive a defect. “Edits alone prove neither progress nor passing; no numeric limits, counters, scores or new persistence.” No counter-reset semantics, accounting subsystem, controller, database, event ledger, metrics/tracking framework or renamed equivalent machinery is permitted. Optional suggestions are separate and cannot drive endless polishing.

A new product decision, scope change or material change to approved intent requires human input and affected explicit review before dependent work. Routine flow-back does not authorize new scope or retroactive historical-feature rewrites. Constitution amendments require their separate authority. A rejected repair must not be applied; an unanswered required decision grants no authority. Save the precise incomplete boundary instead of keeping busy.

## Resume, review changes and native boundaries

“Preserve current artifacts, accepted decisions and existing task identities on resume.” Inspect actual current files and applicable approval before claiming a saved review is still valid. Compare changed-artifact evidence with the last analysis; missing/changed affected output invalidates that pass. With an intact current review and no revision request, present it without regeneration or inferred approval. With partial output or an accepted revision, repair only affected/missing outputs, preserve prior tasks/checked evidence/decisions and reanalyze. Do not reset an existing plan/tasks to new templates or renumber/recreate work. Preserve explicitly changed answers and rejected repairs; historical approval is not approval of changed meaning. Never rewrite merged historical features to describe the current change.

Do not create a Goal automatically or revive the completed specification-preparation Goal. If a separately operator-selected native Goal exists, inspect its actual entire objective and actually exposed supported controls before changing native state. Distinguish these cases:

- A clean complete-proposal objective requires saved complete artifacts plus qualifying fresh analysis. Required input cannot satisfy an unmet clean-proposal objective; never mark it complete merely because a question was saved.
- An explicitly bounded automation objective of saved review-ready OR INCOMPLETE-for-human-input handoff may finish successfully at the required human-input boundary. First durably save **INCOMPLETE planning outcome**, exact required input, current artifact references, actual attempts/remaining issues and next ordinary action in existing spec/plan notes. Read back that saved content. Then complete that matching automation Goal through actually exposed supported controls and verify native complete readback **before waiting for a person or requesting their answer**. Report successful handoff-objective completion separately from the still-INCOMPLETE planning result: no passing analysis, review-ready plan, approval or implementation is implied.
- This human-input endpoint does not cover arbitrary failed helpers, unknown technical failures, mismatched/overscoped objectives or unavailable native completion controls. Preserve saved work and exact limitation; do not fake an API/receipt, claim native success from prose, mutate native files or add continuation machinery.

Only after supported completion/readback of that bounded human-input objective, present the saved exact question and end automation. After an actual answer, continue by separately operator-started ordinary interaction outside the completed Goal, preserving answers/artifacts/task identities and fresh reassessment requirements. Do not create/reactivate a Goal automatically or infer approval from the answer or Goal completion. Where controls/objective do not qualify, report the INCOMPLETE compatibility boundary without claiming successful native completion. Saving a question does not suspend a live Goal; ordinary artifact resume does not prove native resume. Retain earlier failed observations honestly. Do not change model/effort or introduce per-node agents/configuration.

## Finish at the review boundary

With a qualifying fresh analysis, save a concise handoff in existing plan metadata/notes and report **Awaiting full-plan review** with complete proposal links, actual findings/limitations and separately disclosed optional suggestions. Expose the entire plan, supporting design artifacts and ordered tasks. For every proposed new subsystem/infrastructure item, explain responsibility, concrete current need or observed failure, simpler alternatives, tradeoffs and your recommendation; explicitly say when no addition is proposed. Explain how this workflow's continuation and handoff use existing capabilities/artifacts without numeric limits, counters/reset semantics, progress scores, new persistence or accounting/tracking machinery; renaming a subsystem does not meet the constraint. No passing analysis, answer, silence or native Goal outcome approves the plan; implementation requires explicit human plan approval and separately selected work. End without implementation or another workflow.

If incomplete, save current work and exact required input/blocker in existing artifacts and report **INCOMPLETE**, never a successful full-plan-review handoff. For the explicitly bounded human-input automation objective only, follow the durable-save → supported-completion → native-readback sequence above before waiting; successful automation handoff completion does not change the INCOMPLETE planning outcome. Do not invent answers or imply future runtime verification has happened.
