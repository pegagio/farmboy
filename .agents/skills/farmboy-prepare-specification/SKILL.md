# Prepare specification draft and handoff

Use this session’s existing model/effort. This invocation authorizes feature selection, bounded context discovery, draft preparation and a saved handoff only. It does not authorize interactive clarification, approval, planning/tasks, implementation, convergence, closeout, commit or publication. Do not delegate steps, install tools or add a controller/state store.

## Entry mode, context and returned authority

Choose the entry mode from the actual request before effects. **Standalone** preserves this skill's configured local roadmap selection/mapping, verified-prerequisite and context conventions. **Externally selected** means the caller has already selected one feature and this segment; use its identity, intent, accessible authoritative Git context and artifact references. Do not select again, re-adjudicate queue eligibility/dependencies, activate a roadmap entry or switch branches. An ambiguous mode or unsupported segment is a specific required-input/scope stop, not permission to choose another workflow.

For external execution, existing Git constitution, direction and feature artifacts govern project rules/context. Check the selected request against those documents; identify work/input revisions or current working state when needed. Materially stale, conflicting or missing required context requires the specific missing input or resolution before dependent effects. Do not invent answers, fetch unauthorized references, require a fixed packet, new fit brief/register/provenance subsystem or reapproval of unchanged applicable work.

For external execution, use the caller's existing contained feature-directory/workspace association. Explicit identity, any existing standard `.specify/feature.json` pointer and effective `SPECIFY_FEATURE_DIRECTORY` must resolve to that same feature before helpers run. Missing required association asks the caller for conventional workspace preparation; mismatch stops without silent retargeting. Helper-dependent external execution requires the caller-established standard pointer. Normal core helpers may persist an environment directory using its lexical spelling, even when equivalent paths resolve identically. Before invoking them, inspect the actual helper persistence convention and require that its would-be stored value already equals the existing pointer value, so no pointer write occurs. Equivalent aliases/trailing separators or a missing pointer that would cause creation are a specific caller-preparation input before dependent helpers; do not normalize/overwrite the pointer or silently alter caller environment. This preserves read-only assessments and pointer bytes. No temporary pointer overwrite/restoration, new feature number/directory, queue activation or core-tool patch is allowed on this path.

For externally coordinated work, Diagram owns queue/eligibility/dependency decisions, ownership, approvals and accepted handoff records. Consume applicable supplied execution authority; absent/conflicting active-owner authority stops for coordinator input rather than an assumed transfer. One active agent per feature permits sequential owners after authorized handoff; independent features require isolated workspaces. A saved draft return enables coordinator-governed release; later ordinary clarification needs separately acquired authority retained while active. Farmboy never acquires/releases/transfers ownership or writes a local ownership service. Standalone execution needs no Diagram ownership record or service. Git stays canonical for spec/plan/tasks/code/evidence.

Both modes return the selected feature/request/segment association, actual outcome, artifact/evidence references, checkpoint state, remaining work/input/blockers and next review or ordinary action in existing notes. Distinguish successful, incomplete, blocked and interrupted outcomes. A committed checkpoint reference must identify an actual Git revision; uncommitted artifacts disclose base revision and current working state, without an automatic checkpoint commit. Keep historical reviewed checkpoint distinct from latest accepted handoff and current artifacts. Routine in-scope flow-back preserves historical approval; material changes require affected review, while unchanged applicable work is not reapproved. Inspect current artifacts/answers/performed work and pending review on resume; present a valid pending handoff without duplicate effects and reassess only missing/affected work. Neither return data nor native completion accepts a handoff, approves artifacts or authorizes another segment.

## Prepare a usable saved draft

1. In standalone mode use installed roadmap-write to activate/link only the selected eligible entry. In external mode skip this local selection/activation step entirely and preserve the caller association. For standalone linkage use its general amendment path when absent; a status-only helper cannot create that mapping. Preserve unrelated entries and governing state.
2. In standalone mode query only relevant authorized wiki context through installed wiki-query. In external mode check the selected request against existing Git constitution/direction/feature references; query relevant wiki context only if present and authorized, without recreating an absent wiki/queue. Keep citations and disclose gaps. Context access does not authorize external reads. Unresolved governing conflicts block dependent drafting; ordinary product choices may remain explicit draft questions.
3. Resolve the effective `spec-template` using the supported project resolution stack (in the baseline, `specify preset resolve spec-template`). In standalone mode use existing feature setup/pointer conventions to create or update the selected feature’s `spec.md`; preserve existing identity and settled intent. In external mode create only a missing `spec.md` from that resolved template in the caller-associated directory, or update its existing draft; do not run create-new-feature, allocate a number/directory or mutate the pointer. Verify supported template capability before writing. Do not require optional branch hooks or recreate an existing feature. Inspect helper interfaces before using them; missing supported drafting capability is a blocker, not permission to install or build another tool.
4. Author the draft’s intent, scenarios, requirements, success criteria and assumptions. Preserve meaningful rationale and all material unknowns as unresolved topics. Do not fabricate answers or conduct a clarification question/answer loop here. Use the project’s existing specification-quality criteria to produce/update its checklist, reporting incomplete criteria honestly. This is draft authoring/assessment, not a claim that the full interactive specify command ran or a complete specification was approved.
5. In standalone mode use the installed roadmap-brief capability on the saved draft. In external mode record request-versus-authoritative-document fit findings in existing spec notes instead; no local roadmap brief or replacement fit artifact is required. Reconcile routine in-scope drafting corrections. Product questions and resulting incomplete quality findings may support a clarification handoff; disclose them rather than mark them passing. A governing/scope conflict, unusable draft or failed required helper remains a blocker, not a successful handoff. Refresh a brief made stale by a draft change through the responsible capability.

## Finish automation at the handoff

Save a concise note in existing spec metadata/notes and give artifact links, actual findings/limitations and the applicable next step:

- **Needs clarification:** A usable draft has material product questions. List unresolved topics and name ordinary `$speckit-clarify` as the next operator-started step. Do not present an interactive choice and leave the preparation Goal pursuing its answer.
- **Awaiting spec review:** No material question remains. Present human review; do not manufacture questions. Review depth is the operator’s choice, but approval must be explicit before planning.
- **Blocked/incomplete:** Identify the failed prerequisite/conflict/capability and preserved work. A partial draft or stopped Goal is not successful preparation.

These are readable handoff labels in existing artifacts, not new roadmap lifecycle values, Diagram storage, approval registers or ownership machinery. Diagram integration must follow its own governing ownership/handoff rules; no local release/acquisition API is added here.

If a native Goal is active, its entire objective must be a usable saved draft plus this explicit handoff, not answered questions or approval. At either successful handoff, use only an actually exposed supported native completion mechanism and evidence of the saved result. Do not invent a tool/API, mutate host state, or claim native completion solely from prose. If the objective extends through human answers/review, report that mismatch rather than mark an unfinished objective complete. If completion cannot be established, report the concrete compatibility limitation; stalled, paused, interrupted and budget-limited states are not success. Do not keep the Goal alive waiting for answers, start another Goal or manufacture busywork. Then end this skill.

## Ordinary interactive continuation and approval boundary

After successful automated handoff, the operator separately invokes existing `$speckit-clarify` ordinarily, outside the completed preparation Goal. That command owns actual questions, genuine answer waits, supported rounds/limits, early termination and answer integration. Do not resume the completed Goal to do clarification or add another Farmboy clarification skill. Current artifacts and responsible existing capabilities support reconciliation and any necessary brief refresh afterward.

Clarification resolved leads to **Awaiting spec review**, never automatic approval. Review may return to **Needs clarification**. Only explicit human specification approval establishes **Ready for planning**; Goal completion, answers, passing checks and silence do not. These labels explain the handoff, not a local Diagram implementation. Even after approval, this skill does not invoke planning; it only recognizes the prerequisite for a separately selected next workflow.
