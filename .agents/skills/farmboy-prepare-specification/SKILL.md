# Prepare specification draft and handoff

Use this session’s existing model/effort. This invocation authorizes feature selection, bounded context discovery, draft preparation and a saved handoff only. It does not authorize interactive clarification, approval, planning/tasks, implementation, convergence, closeout, commit or publication. Do not delegate steps, install tools or add a controller/state store.

## Resolve current target and stage

Read current project guidance and constitution. Resolve the named or next eligible feature from the configured roadmap, dependencies, established ordering and standard active-feature pointer. Missing capability, unready prerequisites, ambiguous selection, no eligible work or unresolved governing conflict is a concrete stop, not permission to choose other work or invent infrastructure. Do not reactivate deferred/terminal work by inference.

Before repeating effects, inspect current roadmap/pointer/spec identity, accepted answers and pending handoff/input/review. Resume interrupted drafting without duplicate activation or another directory. Preserve changed answers/artifacts; ask about consequential unresolved conflicts. If a usable handoff already exists, present its current next stage rather than restart drafting or revive a completed Goal. If already explicitly approved with no revision requested, report that boundary; do not enter planning.

Resolve actual installed capabilities and current templates/helpers. The inspected baseline provides `$speckit-flow-roadmap-write`, `$speckit-flow-wiki-query`, `$speckit-flow-roadmap-brief`, the `spec-template` resolution path and standard feature setup/pointer helpers. Existing `$speckit-specify` describes feature artifacts and quality criteria; it is not invoked as a whole by this automated drafting skill, because it can require interactive answers before completion. `$speckit-clarify` is the later ordinary interactive entry point. Do not invent aliases or ignore command requirements after invoking a command.

## Prepare a usable saved draft

1. Use installed roadmap-write to activate/link only the selected eligible entry. Use its general amendment path when linkage is absent; a status-only helper cannot create that mapping. Preserve unrelated entries and governing state.
2. Query only relevant authorized wiki context through installed wiki-query. Keep citations and disclose gaps. Context access does not authorize external reads. Unresolved governing conflicts block dependent drafting; ordinary product choices may remain explicit draft questions.
3. Resolve the effective `spec-template` using the supported project resolution stack (in the baseline, `specify preset resolve spec-template`). Use existing feature setup/pointer conventions to create or update the selected feature’s `spec.md`; preserve existing identity and settled intent. Do not require optional branch hooks or recreate an existing feature. Inspect helper interfaces before using them; missing supported drafting capability is a blocker, not permission to install or build another tool.
4. Author the draft’s intent, scenarios, requirements, success criteria and assumptions. Preserve meaningful rationale and all material unknowns as unresolved topics. Do not fabricate answers or conduct a clarification question/answer loop here. Use the project’s existing specification-quality criteria to produce/update its checklist, reporting incomplete criteria honestly. This is draft authoring/assessment, not a claim that the full interactive specify command ran or a complete specification was approved.
5. Use the installed roadmap-brief capability on the saved draft. Reconcile routine in-scope drafting corrections. Product questions and resulting incomplete quality findings may support a clarification handoff; disclose them rather than mark them passing. A governing/scope conflict, unusable draft or failed required helper remains a blocker, not a successful handoff. Refresh a brief made stale by a draft change through the responsible capability.

## Finish automation at the handoff

Save a concise note in existing spec metadata/notes and give artifact links, actual findings/limitations and the applicable next step:

- **Needs clarification:** A usable draft has material product questions. List unresolved topics and name ordinary `$speckit-clarify` as the next operator-started step. Do not present an interactive choice and leave the preparation Goal pursuing its answer.
- **Awaiting spec review:** No material question remains. Present human review; do not manufacture questions. Review depth is the operator’s choice, but approval must be explicit before planning.
- **Blocked/incomplete:** Identify the failed prerequisite/conflict/capability and preserved work. A partial draft or stopped Goal is not successful preparation.

These are readable handoff labels in existing artifacts, not new roadmap lifecycle values, Diagram storage, approval registers or ownership machinery. Diagram integration must follow its own governing ownership/handoff rules; no local release/acquisition API is added here.

If a native Goal is active, its entire objective must be a usable saved draft plus this explicit handoff, not answered questions or approval. At either successful handoff, use only an actually exposed supported native completion mechanism and evidence of the saved result. Do not invent a tool/API, mutate host state, or claim native completion solely from prose. If the objective extends through human answers/review, report that mismatch rather than mark an unfinished objective complete. If completion cannot be established, report the concrete compatibility limitation; stalled, paused, interrupted and budget-limited states are not success. Do not keep the Goal alive waiting for answers, start another Goal or manufacture busywork. Then end this skill.

## Ordinary interactive continuation and approval boundary

After successful automated handoff, the operator separately invokes existing `$speckit-clarify` ordinarily, outside the completed preparation Goal. That command owns actual questions, genuine answer waits, supported rounds/limits, early termination and answer integration. Do not resume the completed Goal to do clarification or add another Farmboy clarification skill. Current artifacts and responsible existing capabilities support reconciliation and any necessary brief refresh afterward.

Clarification resolved leads to **Awaiting spec review**, never automatic approval. Review may return to **Needs clarification**. Only explicit human specification approval establishes **Ready for planning**; Goal completion, answers, passing checks and silence do not. These labels explain the handoff, not a local Diagram implementation. Even after approval, this skill does not invoke planning; it only recognizes the prerequisite for a separately selected next workflow.
