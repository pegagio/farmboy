# Review one implementation proposal independently

Use one independent continuous session and its current model/effort. Review only the selected whole-plan candidate under actual bounded human authorization. Do not delegate steps, install tools, select another feature, create a Goal or launch another workflow.

## Resolve route and existing caller context before effects

An operator asking the selecting or authoring session to arrange independent review uses `farmboy-request-plan-review` before becoming the semantic reviewer. Invoke that caller entry once and propagate its collected result; do not execute this body as well. An already dispatched independent reviewer, or an explicitly selected separate standalone reviewer with actual mandate and independence, continues this existing body directly. Verify real caller/session evidence rather than a wrapper Boolean; never route an already dispatched independent reviewer back into dispatch or infer independence from labels alone.

Standalone use follows the current project's governing rules and explicit selected feature/review mandate, without Diagram lookup, roadmap activation or another ownership service. Use existing accessible Git/spec/plan/tasks/checklist/design/analysis and architecture context. Missing required selection or association is specific input, not permission to create/change a feature, branch or pointer.

For a deliberately Diagram-enabled route without a current adapter invocation, invoke farmboy-diagram-work once for this same review segment. Propagate its actual result and end this outer entry without also executing the body below. For a claimed verified current adapter context, verify current selected feature/review segment, whole endpoint, caller association and current authority/grant/input facts through the adapter's adjacent native-protocol check. A wrapper flag, available tool or historical receipt alone is insufficient. Reuse verified current authority without acquiring again or recursively wrapping. Stale/foreign/missing context stops dependent work; no automatic takeover/reacquisition.

The semantic body and adapter compose in the same session. Only the adapter owns native lifecycle, report checkpointing, finalization and release/readback. This body returns local review data once and never performs those effects or completes a wider coordinator Goal. Its return is ordinary named content defined below, not a new API, subprocess transport, packet or store.

## Verify actual bounded authority and independence

Require actual human authorization for this reviewer, candidate and whole-plan approval role, including protected intent, expected UX, constraints and any required independent evidence. No material authorship of the candidate is allowed for this reviewer. Verify a separate reviewer session and actual independence; labels/digests provide attribution, not identity authentication. Known holds/revocation stop substantive review.

Access, startup flags, silence, fixtures or structural acceptance are not a semantic mandate. Do not fabricate human evidence, substitute reviewers, silently repin stale scope or ask redundant confirmation of already established explicit permission. Missing/ambiguous/conflicting/revoked authority or independence returns incomplete with the precise missing input, not a decision.

## Assess the read-only proposal

Verify actual candidate/artifact identities and applicability of approved intent: specification, whole plan/tasks/checklist, supporting design/fresh consistency analysis and relevant actual architecture. Identify immutable commit/path/digest references or truthful base plus uncommitted content digests. Unknown material evidence or changed/uncertain proposal bytes stops dependent review. Do not edit the proposal, run planning/tasking/analysis repair or redesign it.

Independently answer these exact questions with rationale and evidence:

1. Are they reasonable for the scope of the feature?
2. Do they add unnecessary machinery or ceremony?
3. Do they align with the feature's intent?
4. Is the architecture sound?
5. Can the plan and/or tasks be tightened without redesigning?
6. Is the execution checklist appropriate, or is it overly elaborate?

Assess real need, ongoing burden, architecture, simpler alternatives and checklist proportionality. Approval requires no unresolved blocker or unmet obligation. Minor optional suggestions may coexist with approval only when explicitly non-blocking and identifying no defect/unmet requirement. Never turn those into required corrections, approval conditions or an automatic polishing cycle.

## Save and return once

Save the report at the selected contained feature's `validation/plan-review.md`. Preserve proposal bytes and unrelated work. Include six answers/rationale, exact reviewed references, actual reviewer/human mandate/constraints/independence evidence, findings and disposition. Record a delegated decision truthfully, never as the human's personal review. Do not commit merely because this body was invoked.

Return these minimum named content fields, using the report as the detailed evidence rather than a duplicate register:

- `report_reference`: contained selected-feature path and actual SHA-256 of saved bytes.
- `reviewed_candidate`: exact selected feature and approved-spec/proposal/checklist/design/analysis/architecture references, with current committed/uncommitted status.
- `reviewer_mandate`: actual reviewer, human authorization reference/semantic bounds and independence evidence.
- `findings`: blocking versus optional items and their report locations; each blocking request identifies artifact/problem/reason/expected correction.
- `disposition`: approve, planning-return or specification-escalation, only on complete substantive review.
- `incomplete`: on technical/missing-input failure, no substantive disposition; precise error/missing/uncertain input, preserved report/work/effects and next ordinary action.

Approve has no blocking requests/questions or unmet obligation. Planning-return requests in-scope planning/tasking/consistency correction, preserving approved specification meaning. Specification-escalation identifies actual product questions; it neither revises nor approves the specification, and historical human approval remains intact. See [usage and return guide](../../../docs/review-implementation-plan.md) for the same boundary and caller validation.

In a coordinated invocation return these fields to the current adapter and stop the body. Standalone returns them to its selecting caller and stops. Missing/invalid/contradictory/unreadable output is incomplete, never inferred approval. The receiving adapter must check actual report/candidate/current authority before native effects. Neither local report, native receipt nor approval grants implementation, specification approval, result acceptance, integration or publication. No repair, re-review, next child, scheduler, timer, lease, standing mandate service or recovery controller follows automatically.
