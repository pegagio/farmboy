# Bounded released-planning continuation (DIAG-21 source capability)

Source schema24/Feature9 adds a typed optional policy on the existing Feature context. Existing installed schema23 tools cannot use it. Source availability is not installation or permission to migrate; select a matched binary/store explicitly. No admission upgrades a store. Existing historical deployment records remain historical.

The operator's actual planning-execution mandate must explicitly cover recovery. The assisting coordinator records that existing authority; the operator need not create JSON or issue a fresh per-predecessor decision. Approval, project/workflow switches, generic polling permission, one-shot scope or absence of a pause never supplies a missing mandate. A source/API action denial remains governed by its actual permission and retry policy.

## Existing command composition

- `feature planning recovery show --feature ID`: inspect policy, exact original input/authority, reported stop, hold and successor-derived consumed-by IDs/remaining allowance. This is native coordination, not physical/source observation or admission permission.
- `feature planning recovery record --feature ID --operation OP --request-file FILE`: strict Feature9 metadata with expected revision/queue/dependencies, pinned handoff, accepted-spec checkpoint, applicable approval_id and Assessment with approval/conditions. `recovery_policy` selects `authorize`, `renew`, `hold`, `clear-hold` or `assess-stop`.
- `authorize` includes `mandate`, an actual human Review decision `authorize-bounded-planning`, actor/provenance/outcome/approach and nonblank conditions binding this accepted input and one continuation. `renew` also names `previous_allowance`; it is an explicit current operator decision, never a renamed coordinator request. Neither can clear a hold or denied/paused disposition. Input changes alone grant nothing.
- `hold`/`clear-hold` use top-level Review decisions `hold-planning-recovery`/`clear-planning-recovery-hold` with actual operator scope/provenance. A hold can be recorded before any allowance. Clear leaves stop unknown and grants no mandate or allowance. Clearing a recorded denial requires genuine applicable operator resolution under unchanged action-time policy, not a coordinator diagnosis. No retry is executed by this metadata operation.
- `assess-stop` includes `stop:{run_id,epoch,disposition,assessment}` for the exact latest released incomplete planning predecessor. Dispositions are recoverable/paused/denied/unknown. Coordinator diagnosis cannot clear a hold or prior paused/denied restriction. The stop assessment has applicable historical approval and conditions evidence. A recorded release with unknown reason is not retroactively relabeled.

The current command caller reports truthful authority; labels are attribution, not authentication. The native store validates roles, typed structure, exact native references and exclusive admission. The coordinator alone judges source applicability and physical facts. Policy updates use the existing operation receipt table and advance current revision; a hold prevents future admission but does not pretend to cancel a child. Current writers must inspect fresh context before handoff/release.

## One existing successor path

Keep `feature run recover`, `recovery.action:successor`, exact predecessor/input/identity/HEAD/epoch reports and preservation checks. Manual `review.decision:authorize-successor` is unchanged. Automatic continuation adds `planning_recovery:{allowance_operation,resolution:{actor,failed,changed,evidence,unverified}}` and distinct coordinator Review decision `continue-bounded-planning` under the prior recorded human mandate. Evidence is nonempty, descriptions nonblank, unknowns explicitly listed (empty only when an attributable inspection says none remain). Unrelated fields and null automatic authority refuse. Native does not certify relevance from a URL or infer semantic resolution from shape acceptance.

Admission atomically checks current input/approval, exact recoverable predecessor classification, no hold/denial/unknown, active writer exclusion, current project+plan controls, supplied evidence and zero admitted successors for this allowance from existing run origins. One admitted successor consumes the allowance even if startup fails or work releases incomplete. Exact replay returns old receipt, not current ownership. New request/agent/process/failure/input alone never renews it; unreadable history refuses.

The selecting coordinator invokes existing `diagram-launch --recover-feature ID --recovery-request-file FILE`. Automatic selection shares the existing same-store repeat guard for preflight, one child, process exit and attributable native terminal observation, and checks other automated owners. Busy/stale guards and unknown outcomes stop visibly; no removal, takeover, retry loop, scheduler, lease or Terminal/service restart is added. Normal discovery does not select released work. Manual recovery remains unchanged. The child enters the optional adapter once, reuses the admitted successor and existing Farmboy planning body, preserves drafts/task IDs, runs actual checks and normal-hook checkpoint, then stops at genuine plan review. Missing handoff is incomplete even after exit0.

This is planning only. No BGG2 pause clearance, BGG11 recovery, permission/API-budget refresh, review grant, later-phase approval or host-process lifetime authority follows from deployment or this document. Controlled private fixtures are not real sandbox/model/live API proof.
